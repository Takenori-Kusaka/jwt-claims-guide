# 共通規約と完了の定義

設計書テンプレート一式（#11）を作る issue のすべてに共通する規約です。各 issue の完了基準は、ここにある「完了の定義」を満たしたうえでの追加条件とします。issue ごとに書き方がぶれて、完了基準に抜け道が生まれるのを防ぐためです（#13）。

この文書を変えるときは、PR で変え、`templates/CHANGELOG.md` に書きます。

- 1. 根拠の種類と書式
- 2. 完了の定義（全 issue に適用）
- 3. 点検者についての取り決め（当面）
- 4. 公開物の取り扱い
- 5. 題材

## 1. 根拠の種類と書式

根拠は次の 7 種類のどれかに分けて書きます。#13 の本文は 6 種類としていますが、ガイドの根拠には論文（Zanzibar）や技術記事もあり、6 種類のどれにも入らないため、`research` を足しました。どれにも当てはまらないものは、根拠として書きません。

| 種類 | 意味 | ID の書き方 | 例 |
| --- | --- | --- | --- |
| `spec` | 仕様。RFC、IETF の草案、OpenID Foundation の仕様、IANA の登録簿、ほかの標準化団体の仕様、業界の属性語彙（SCIM・eduPerson など）、IdP・製品の公式文書 | 版と節を書く。RFC は `RFC 番号 §節`、草案は版番号つきの名前と節、製品の文書は製品の版と文書名と節の名前 | `RFC 8693 §4.1`、`draft-ietf-oauth-transaction-tokens-11 §12.2`、`OpenID Connect Core 1.0 §5.1`、`IANA JWT Claims registry`、`Keycloak Server Administration Guide（26.8）「Lightweight access token」` |
| `guidance` | 公的な指針。NIST、OWASP、デジタル庁、CSRB など公的機関・標準化団体の指針 | 規格名と版と項目の番号を書く | `ASVS v5.0.0-8.3.2`、`NIST IR 8587 §5.3.1.7` |
| `research` | 論文と技術記事（公的機関の指針でないもの） | 著者または発行元、題名、年、節 | `Pang et al.「Zanzibar: Google's Consistent, Global Authorization System」（USENIX ATC 2019）§2` |
| `book` | 書籍 | 書名・出版社・年と、章（節）と印刷ページだけを書く。本文は引用しない | `『実践 Keycloak』（オライリー・ジャパン 2022）13.5 節 p.276` |
| `incident` | 事故の事例 | CVE の番号、または公的な報告書の名前と項目 | `CVE-2025-55241`、`CSRB 報告書（Storm-0558）勧告 6` |
| `guide-slide` | 本ガイドのスライド | スライドの固定 ID（#15）。スライド番号では書かない | `p06-narrow-downstream` |
| `author-proposal` | 筆者の提案 | 提案の要旨と、裏付けを探す追跡 issue の番号 | `関門 1 の基準「Lite の記入が 4 時間以内」`（`tracking: "#16"`） |

### 書き方の決まり

- **版を必ず書く**。草案は版で中身が変わります。`draft-ietf-oauth-transaction-tokens §12.2` のように版のない書き方はしません。ASVS も `8.3.2` だけでは版が分かりません。
- **確かめた日は `verified_on` に書く**。日付は ID に含めず、`verified_on`（`YYYY-MM-DD`）の欄に書きます。文書が予告なく変わる `spec`（製品の文書・IANA の登録簿）と `research` の技術記事では必須です。
- **ASVS の書き場所は 1 か所**。台帳（#3）では ASVS を `asvs_ids` の列に書き、`refs` には書きません。`asvs_ids` の列のない成果物（カタログ・設計書の本文）では、`refs` に `guidance` として `ASVS v5.0.0-8.3.2` の形で書きます。
- **スライドは固定 ID で指す**。番号はスライドを足すとずれ、黙って別のスライドを指すようになるためです（2026-11-18 に 149 枚から 152 枚になったときにずれました）。#15 で ID が付くまでは、番号と調査日を併記し（`スライド 81（2026-11-18 時点）`）、#15 の後に ID に置き換えます。
- **書籍は場所を指すだけ**。章・節・ページで指し、本文は写しません。要約も、根拠の行には書きません。
- **`author-proposal` は正式な根拠として認める**。一次資料に裏付けのない判断を、こじつけた根拠で飾るより、提案だと明示するほうを優先します（ガイドの「筆者の推奨」「筆者の提案」の書き方に合わせます）。
  - テンプレートや表の上では「筆者の提案」と表示します。
  - `tracking` に追跡 issue の番号を必ず書きます。番号のない `author-proposal` は不可です。
  - 追跡 issue の本文には、提案ごとに 1 項目を設けます。issue は開いたままにするか、項目ごとに結論（裏付けあり・裏付けなし）を書いてから閉じます。結論のないまま閉じた issue は、追跡 issue として使えません。
- **ケーススタディの実測は根拠の種類に入れない**。実測は「何が起きたか」の記録で、台帳では `evidence`（検証の記録）の列に書きます（#3）。書き方は `jwt-claims-casestudy@<コミット>:<ケース ID>`（例：`jwt-claims-casestudy@080b8da:B9`）です。

### 機械で読む形の例

台帳やカタログでは、根拠を次の形で書きます（列の名前と型は #3 のスキーマで確定します）。

```yaml
refs:
  - kind: spec
    id: "RFC 8693 §4.1"
    url: https://www.rfc-editor.org/rfc/rfc8693#section-4.1
  - kind: spec
    id: "Keycloak Server Administration Guide（26.8）「Lightweight access token」"
    url: https://www.keycloak.org/docs/latest/server_admin/
    verified_on: 2026-11-17   # 日付は例
  - kind: guide-slide
    id: "p06-narrow-downstream"
  - kind: author-proposal
    id: "関門 1 の基準「Lite の記入が 4 時間以内」"
    tracking: "#16"
asvs_ids: ["v5.0.0-8.3.2"]   # 台帳では ASVS はここだけに書く
evidence:
  - "jwt-claims-casestudy@080b8da:C5"
```

## 2. 完了の定義（全 issue に適用）

各 issue の完了基準に加えて、次のすべてを満たしたときに issue を閉じます。issue を閉じるコメントに、この一覧を写して埋めてください。

```markdown
### 完了の定義（#13）
- [ ] 完了基準ごとに、証拠（コミット・PR・実行ログ・`research/reviews/` の記録）へのリンクを issue のコメントに残している
- [ ] 成果物は PR でマージしている
- [ ] 成果物に含まれる事実（仕様の節・IdP の値・上限・版）を全件点検し、`research/reviews/<対象>-<日付>.md` に既存と同じ区分（誤り・過大・不一致・曖昧）で記録している。記録に「点検した件数／全件数」がある
- [ ] 指摘ごとに、反映したか、反映しない理由を記録している。反映しない指摘は、理由を別の点検で確かめている
- [ ] 根拠の ID（`refs`・`asvs_ids`・`evidence`）の実在を、機械で全件確かめている（ツールができるまでは手で全件）
- [ ] 根拠の中身（その根拠が主張を支えるか）を、根拠の 10%（10 件未満なら全件、最低 10 件）抜き取って点検している
- [ ] 「対象外」「扱わない」の行を無作為に 5 件（5 件未満なら全件）抜き取り、前提と崩れる条件が妥当かを点検している
- [ ] error の重大度の規則に対する抑止と、error からの重大度の引き下げが 0 件である。warning の抑止は、行ごとの理由が lint の出力に出て、件数と一覧を完了のコメントに書いている
- [ ] 「対象外」「扱わない」で閉じた行には、「起きない前提」と「その前提が崩れる条件」の両方が書かれている。対象外の件数と割合を成果物の冒頭に載せている
- [ ] 「漏れゼロ」を約束する表現がない
- 点検の方法：（例）別の LLM のセッションで点検し、作成者が 1 日以上空けて見直した。人による点検は未実施（#20）
```

### 各項目の補足

**証拠のリンク**。完了基準 1 つにつき、証拠を 1 つ以上書きます。例：

```markdown
- [x] 152 枚すべてに一意の ID があり、重複が 0 件である
  - 証拠：PR #NN、`tools/slide-ids --check` の実行ログ（Actions の run へのリンク）
```

**事実の点検の範囲**。新しく作った成果物、または変更した箇所に含まれる事実は、全件を点検します。抜き取りでよいのは、この一覧で抜き取りと書いた 2 項目（根拠の中身、対象外の行）だけです。全件の点検が現実的でない量（例：数百行のカタログ）になる場合は、issue の完了基準で範囲を決めてから作業を始めます。

**点検の記録**。ファイル名は `research/reviews/<対象>-<日付>.md` です（例：`research/reviews/registry-v1-2026-12-05.md`）。区分は既存の記録（`research/reviews/factcheck-2026-11-17.md`）と同じです。

| 区分 | 意味 |
| --- | --- |
| 誤り | 必ず直す |
| 過大 | 原典より強い言い方 |
| 不一致 | 成果物の間、または成果物とスライドの間の食い違い |
| 曖昧 | 読み違えやすい |

記録の表は「対象・区分・指摘・直し方」の 4 列にします。記録には、次も書きます。

- 点検した件数／全件数（事実、根拠の中身、対象外の行のそれぞれ）
- 抜き取りの選び方（乱数の種、または選んだ行の ID の一覧）
- 反映しない指摘の理由と、その理由を確かめた点検（別の LLM のセッション、または作成者が 1 日以上空けた見直し）の結果

理由のない未反映と、確かめていない理由での未反映は、完了の定義を満たしません。

**抜き取りの数**。根拠の中身の 10%（最低 10 件）と、対象外の行の 5 件は、筆者の提案です（追跡 #20：人による点検の結果と比べて見直す）。

**lint の抑止**。error の規則は抑止できません。error の規則が成果物に合わない場合は、規則を直す PR を別に出します。warning の抑止は、行ごとに理由を書き、その理由が lint の出力に出るようにします。

**「対象外」の書き方**。次の 3 つをそろえます。列の名前は #2・#3 のスキーマで決めます。下は #2 のカタログの行の例で、列の名前は仮のものです。台帳の `status`（定義の寿命）とは別の列です。

```yaml
- id: I07                 # ID は例
  name: ROPC（Resource Owner Password Credentials）での発行
  coverage: 対象外        # 仮の列名
  assumption: 組織のクライアントは ROPC を使わない（RFC 9700 §2.4 が使用を禁じている）
  breaks_when: ROPC でしか動かない旧システムを接続する場合。その場合は対象に戻し、発行イベントとして扱う   # 仮の列名
```

成果物の冒頭には、`対象外 12 件／全 85 件（14%）` のように件数と割合を書きます。

**「漏れゼロ」を約束しない**。想定漏れが一切ないことは原理的に証明できません（#11 の「約束の範囲」）。「漏れなく」「すべての想定を網羅」「漏れゼロ」とは書かず、何の内側で何を検出するかを書きます。

- 書かない：「このカタログで発行の場面を漏れなく洗い出せる」
- 書く：「種になる一覧（IANA OAuth Parameters など）の全項目が、カタログの行か『対象外』にひもづく。一覧の外の場面は、カタログ外を問う質問で探す」

## 3. 点検者についての取り決め（当面）

人の協力者は当面確保できません。そこで、作成者以外による点検を次の手順で代えます。

1. **別の LLM のセッションで点検する**。作成に使ったものとは別のセッション（会話の履歴を引き継がないもの）で点検します。
   - 渡すもの：成果物、その issue の本文（完了基準を含む）、成果物が引いている一次資料（RFC・仕様・公式文書の該当箇所、ケーススタディのファイル）。
   - 渡さないもの：作成者の結論、仮説、「正しいことを確かめて」のような答えを前提にした指示。点検が追認になるのを防ぐためです。
   - 記録に残すもの：日付と使ったモデルの名前、渡した資料（ファイルのパスとコミット、URL）、渡した指示の全文、出力（指摘の一覧）。
   - 指摘が 0 件のときは、確かめた項目の一覧を記録に残します。一覧のない「指摘なし」は、点検したことになりません。
2. **作成者が 1 日以上空けてから見直す**。点検の指摘と成果物を、作成から 1 日以上空けて読み直し、指摘ごとに直すか、直さない理由を書きます。記録には、作成の日付と見直しの日付の両方を書きます。
3. **「人による点検は未実施」と明記する**。この方法で閉じた issue のコメントと、成果物の README の「点検状況」に、次の文をそのまま書きます。

   > 人による点検は未実施。作成とは別の LLM のセッションで点検し、作成者が 1 日以上空けて見直した（記録：`research/reviews/<対象>-<日付>.md`）。

   1. と 2. のうち 1. だけが終わっている間は、次の文を書きます。2. が終わったら上の文に置き換えます。

   > 人による点検は未実施。作成とは別の LLM のセッションで点検した。作成者の 1 日以上空けた見直しは未実施（記録：`research/reviews/<対象>-<日付>.md`）。

   「人で検証済み」「レビュー済み」とだけ書くことはしません。人による点検は、協力者が見つかったときに #20 で行い、終えたものから表示を外します。

### レビューの記録がある設計書を変えるとき（#50）

`templates/examples/scenario-b/review.yaml` のように、レビューの記録（`review.yaml`）とそこから生成したレポートがある設計書を変える PR では、CI の 3 つの検査が次のように反応します。どれも、記録を書き換えて合わせるのではなく、記録した時のものを残したまま直します。

| 変えたもの | CI の反応 | 直し方 |
| --- | --- | --- |
| 確認済みにした行の値（台帳・目録・ホップ・カタログの行） | `review_record.py check` は stale を一覧に出し、PR の画面に `::warning` を出す（失敗にはしない。最後の提出の判定が承認なら「古い承認」も出す）。`report --check` は失敗する（9. の「今の行との対応」が変わる） | `python tools/review_record.py report <dir>/review.yaml --design <dir> -o <dir>/review-report-<日付>.md` で作り直す。差分に「前回の確認から変更あり」が出る。再レビューするなら、エディターで変わった行を確認済みにして、もう一度提出する |
| 却下の行（足す・消す・ID や内容を変える） | `check` は「抜き取りの母集団が変わった」を warn にする（失敗にはしない）。`report --check` は失敗することがある | 作り直す（上と同じ）。抜き取りを引き直すなら `python tools/review_record.py sample <dir> --reseed --reason "<理由>" --file <dir>/review.yaml --reviewer "<名前>"`（前の抜き取りは `sampling.previous` に残る。新しく選ばれた行は採点し直す） |
| 教材（`templates/review/perspectives.md`・`report_template.md` の版や問い） | `check` は、今の観点書に無い問いへの回答を warn にする。`report --check` は失敗する（1. に今の教材の版が並ぶ） | 作り直す。レポートの「使った教材の版」は review.yaml の `materials`（レビューした時の版）のままで、今の版が違うことを並べて書く |

`--fail-on-stale` は、記入例の CI には付けません。記入例の記録は 2026-11-23 の LLM の一次スクリーニングで、止めると、台帳を変えるたびに LLM で承認し直すか、記録を消すかを強いることになるためです（PR #52 の点検）。

## 4. 公開物の取り扱い

### ライセンス

| 対象 | ライセンス |
| --- | --- |
| `templates/` の全ファイル | CC0 1.0（`templates/LICENSE`） |
| ガイド本体（スライド・文章・調査メモ） | CC BY 4.0 |
| コード（`deck/`・`tools/`） | MIT |

`templates/` を CC0 にするのは、利用者が表示の義務なしに、社内の設計書へそのままコピーできるようにするためです。

- **筆者自身の文章**（ガイド、ケーススタディ）は、`templates/` に入れてよいものとします。入れた部分は、著作者である筆者が CC0 1.0 で提供し直します（`LICENSE-CONTENT.md` に明記）。例えば、台帳の問いの文言はスライドの文言と一致させます（#3）。ただし、ケーススタディの一覧表と判定の文章は、二重管理を避けるために写さず、ID で参照します（`templates/casestudy-mapping.md`）。
- **他者が権利を持つ文章**（各社の文書、書籍、記事、仕様の本文）は入れません。
- **実行するコード**は `tools/` に置き、MIT とします。

### IANA の登録値や IdP の値

事実の列挙と出典の URL だけを載せ、各社の文書の文章は写しません。

| 書いてよい | 書かない |
| --- | --- |
| `Cognito の Pre token generation の契機の値：TokenGeneration_RefreshTokens など`（出典 URL と `verified_on`） | 文書の説明文を訳したもの、言い換えただけのもの |
| 値の名前、上限の数値、版、既定値 | 文書の手順や注意書きの文章 |

### 版の管理

テンプレート一式は semver で版を管理します。

- タグ：`templates-vX.Y.Z`（例：`templates-v1.0.0`）。最初の公開版は `templates-v1.0.0` です（#11）。それまでは `0.y.z` です。
- 変更の記録：`templates/CHANGELOG.md`。タグを付ける PR で、「未リリース」の節を版の節に移します。
- 各ファイルの先頭に `template_version` を書きます。未リリースの間は、次に付ける版を書きます。

| 形式 | 書き方 |
| --- | --- |
| Markdown | 1 行目に HTML のコメント `<!-- template_version: 0.1.0 -->`。前付け（front matter）は使わない |
| YAML | 1 行目にコメント `# template_version: 0.1.0`。キーにはしない。エディタの検証のために yaml-language-server の modeline（`# yaml-language-server: $schema=./claims.schema.json`）を置く場合は、2 行目以降の先頭のコメントの中、最初のキーより前に置く。yaml-language-server は、最初の YAML の内容より前のコメントからしか modeline を読まないため（コミット 416ede2 以降）。キーにしないのは、1 行目をキーにすると modeline を置けなくなること、データの列にするとスキーマ側で許可が要ること、Markdown（コメント）と書き方が揃うことによる |
| JSON Schema | `$id` に版を入れ（例：`https://.../claims.schema.json/v0.1.0`）、最上位の `$comment` に `"template_version: 0.1.0"`。独自のキーワードは置かない（Ajv の strict モードがエラーにするため） |
| JSON（スキーマ以外のデータ） | 最上位に `"template_version": "0.1.0"`。スキーマ側でこのキーを許可する |

`LICENSE` と `CHANGELOG.md` には書きません。

| 上げる桁 | 変更の例 |
| --- | --- |
| メジャー（X） | 列の削除・改名、列の意味や列挙値の変更、任意の列を必須にする。既存の設計書が検査を通らなくなる変更 |
| マイナー（Y） | 任意の列・モジュール・lint の規則（warning）の追加。既存の設計書がそのまま通る変更 |
| パッチ（Z） | 文言の修正、例の修正、根拠の版の更新（中身の判断が変わらないもの） |

lint の規則を error で足すと既存の設計書が通らなくなるので、メジャーとして扱います。

カタログ（`templates/catalog/`）にイベントを足すと、それまでの設計書に回答が無く、R2 が error にします。マイナーの版でイベントを足すときは、行を末尾に足し、`asked_from` に台帳の版（`templates/registry/*.schema.json` の `template_version`。版の軸はこれ 1 つ）を書き、ファイルの `_added` にその版で載せます。猶予は**マイナーの版 1 つ**です。台帳のマイナーの版が `asked_from` と同じ間は、回答が無いことを warn にとどめ、次のマイナーの版から error にします（コードで版を比べる。`tools/claim_lint/RULES.md` の R2。#63）。回答を問わないのは、変えられない記録として `tools/claim_lint/frozen_designs.yaml` に PR で載せた設計書だけです（パス・`catalog_answers.yaml` の sha256・理由）。

### 作成方法の開示

各成果物の README に、ガイドと同じ書き方で作成方法を書きます。

> 本資料は生成AI（Claude）を使って作成し、筆者が確認して公開しています。

あわせて「点検状況」の節を設け、3. の文を書きます。

### 秘密情報の検出

本リポジトリの CI に secret scan を入れます（CI の土台は #16 で作ります）。

- PR と main への push で動かし、検出したら失敗させます。
- 見本のトークンは、試験用の鍵で署名したものだけを置きます。鍵そのもの（秘密鍵・クライアントシークレット）はリポジトリに入れません。ケーススタディも、鍵を `keys/` に置いてリポジトリから外しています。
- 見本のトークンが検出に掛かる場合の除外は、ファイルごとに理由を書きます。

### 意図的に誤りを含む教材

誤りを埋め込んだ設計書（#12）やレビュー教材の演習（#5）には、次の 3 つをすべて付けます。コピーされて設計に使われるのを防ぐためです。

1. ファイル名に `.broken` を入れる（例：`design-a.broken.md`、`claims.broken.yaml`、`sample-at.broken.jwt`）
2. 置き場所のディレクトリの README に「意図的に誤りを含む教材。設計に使わない」と書く
3. 書ける形式では、ファイルの中にも書く

| 形式 | ファイルの中の書き方 |
| --- | --- |
| Markdown | `template_version` の行の次にある最初の見出しの直後に `> **意図的に誤りを含む教材。設計に使わない**` |
| YAML | `template_version` の次の行に `# 意図的に誤りを含む教材。設計に使わない` |
| JSON | 最上位に `"_warning": "意図的に誤りを含む教材。設計に使わない"` |
| JSON Schema | 最上位の `$comment` の先頭に同じ文 |
| 見本のトークン | ペイロードに `"_warning"` のクレームを入れる。入れられない場合（実物の IdP が発行したものなど）は、1. と 2. だけでよい |

## 5. 題材

題材は、ケーススタディ（https://github.com/Takenori-Kusaka/jwt-claims-casestudy）のシナリオ A・B・C とします。新しい題材は作りません。実測の結果があり、記入例の判断を実験で裏付けられるためです。

ケーススタディは A・B・C を「ケース」と呼びます。本計画では A・B・C を「シナリオ」と呼び、「ケース」は A1・B9 などの個々の試験だけを指します。

| シナリオ | 名前 | IdP（実験環境） | 本計画での使い道 |
| --- | --- | --- | --- |
| A | マルチテナント SaaS | Keycloak 26.8.0（実物）。レルム t1・t2 をテナントとし、Postgres 16 の行単位の制御（RLS）と組み合わせる | 縦の一本（#16）、台帳の記入例（#3） |
| B | 社内業務システム | Keycloak 26.8.0 のレルム corp（実物）と、Entra ID・Okta・Cognito・Auth0 の形を再現した模擬。入口（ゲートウェイ）で内部トークンに交換する | 台帳の記入例（#3）、パイロット（#9） |
| C | AI エージェントの委任 | 組織のトークン発行サービスの模擬（時刻を進めるため）。MCP 風のツールサーバーを経て請求書の API を呼ぶ。別に、Keycloak 26.8 の標準トークン交換を実測している | パイロット（#9） |

「シナリオ A（Keycloak）」と書くときは、Keycloak だけで閉じているシナリオ A を指します。B も Keycloak を使いますが、ほかの 4 つの IdP の模擬を含みます。

ケーススタディの `catalog/catalog.json`・`SCHEMA.md`・`DECISION_POLICY.md`・`decisions/` と、本計画の台帳（#3）・カタログ（#2）との対応と、どちらを正とするかは、[`casestudy-mapping.md`](casestudy-mapping.md) にあります。要点は次のとおりです。

- 805 行のクレームの一覧表（ORG 行の名前と型を含む）と、シナリオ A・B・C ごとの判定は、ケーススタディを正とします。`templates/` には写さず、ID で参照します。
- 台帳の行の設計判断（理由・データ源・寿命と鮮度など）と、発行・利用イベントのカタログは、`templates/` を正とします。
- 記入例でケーススタディと違う判定にするときは、`templates/casestudy-deviations.yaml` に理由とともに載せます（ケーススタディは変えません）。
