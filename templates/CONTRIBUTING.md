# 共通規約と完了の定義

設計書テンプレート一式（#11）を作る issue のすべてに共通する規約です。各 issue の完了基準は、ここにある「完了の定義」を満たしたうえでの追加条件とします。issue ごとに書き方がぶれて、完了基準に抜け道が生まれるのを防ぐためです（#13）。

この文書を変えるときは、PR で変え、`templates/CHANGELOG.md` に書きます。

- 1. 根拠の種類と書式
- 2. 完了の定義（全 issue に適用）
- 3. 点検者についての取り決め（当面）
- 4. 公開物の取り扱い
- 5. 題材

## 1. 根拠の種類と書式

根拠は次の 6 種類のどれかに分けて書きます。どれにも当てはまらないものは、根拠として書きません。

| 種類 | 意味 | ID の書き方 | 例 |
| --- | --- | --- | --- |
| `spec` | 仕様。RFC、IETF の草案、OpenID Foundation の仕様、IANA の登録簿、IdP・製品の公式文書 | 版と節を書く。RFC は `RFC 番号 §節`、草案は版番号つきの名前と節、製品の文書は文書名と確認日 | `RFC 8693 §4.1`、`draft-ietf-oauth-transaction-tokens-11 §12.2`、`OpenID Connect Core 1.0 §5.1`、`IANA JWT Claims registry（確認 2026-11-17）`、`Keycloak Server Administration Guide（26.8）「Lightweight access token」（確認 YYYY-MM-DD）` |
| `guidance` | 公的な指針。NIST、OWASP、デジタル庁など | 版と項目の番号を書く。ASVS は `v版-章.節.項` | `v5.0.0-8.3.2`（OWASP ASVS 5.0.0 の 8.3.2）、`NIST IR 8587 §5.3.1.7` |
| `book` | 書籍 | 書名・出版社・年と、章（節）と印刷ページだけを書く。本文は引用しない | `『実践 Keycloak』（オライリー・ジャパン 2022）13.5 節 p.276` |
| `incident` | 事故の事例 | CVE の番号、または公的な報告書の名前と項目 | `CVE-2025-55241`、`CSRB 報告書（Storm-0558）勧告 6` |
| `guide-slide` | 本ガイドのスライド | スライドの固定 ID（#15）。スライド番号では書かない | `p06-narrow-downstream` |
| `author-proposal` | 筆者の提案 | 提案の要旨と、裏付けを探す追跡 issue | `関門 1 の基準「Lite の記入が 4 時間以内」（追跡 #NN）` |

### 書き方の決まり

- **版を必ず書く**。草案は版で中身が変わります。`draft-ietf-oauth-transaction-tokens §12.2` のように版のない書き方はしません。ASVS も `8.3.2` だけでは版が分かりません。
- **IdP・製品の公式文書は `spec` に入れる**。文書は予告なく変わるため、確認日を ID に含めます。
- **スライドは固定 ID で指す**。番号はスライドを足すとずれ、黙って別のスライドを指すようになるためです（2026-11-18 に 149 枚から 152 枚になったときにずれました）。#15 で ID が付くまでは、番号と調査日を併記し（`スライド 81（2026-11-18 時点）`）、#15 の後に ID に置き換えます。
- **書籍は場所を指すだけ**。章・節・ページで指し、本文は写しません。要約も、根拠の行には書きません。
- **`author-proposal` は正式な根拠として認める**。一次資料に裏付けのない判断を、こじつけた根拠で飾るより、提案だと明示するほうを優先します（ガイドの「筆者の推奨」「筆者の提案」の書き方に合わせます）。
  - テンプレートや表の上では「筆者の提案」と表示します。
  - 裏付けを探す追跡 issue へのリンクを必ず付けます。リンクのない `author-proposal` は不可です。
- **ケーススタディの実測は根拠の種類に入れない**。実測は「何が起きたか」の記録で、台帳では `evidence`（検証の記録）の列に書きます（#3）。書き方は `jwt-claims-casestudy@<コミット>:<ケース ID>`（例：`jwt-claims-casestudy@080b8da:B9`）です。

### 機械で読む形の例

台帳やカタログでは、根拠を次の形で書きます（列の名前と型は #3 のスキーマで確定します）。

```yaml
refs:
  - kind: spec
    id: "RFC 8693 §4.1"
    url: https://www.rfc-editor.org/rfc/rfc8693#section-4.1
  - kind: guidance
    id: "v5.0.0-8.3.2"
  - kind: guide-slide
    id: "p06-narrow-downstream"
  - kind: author-proposal
    id: "関門 1 の基準「Lite の記入が 4 時間以内」"
    tracking: "#NN"   # 裏付けを探す追跡 issue
evidence:
  - "jwt-claims-casestudy@080b8da:C5"
```

## 2. 完了の定義（全 issue に適用）

各 issue の完了基準に加えて、次のすべてを満たしたときに issue を閉じます。issue を閉じるコメントに、この一覧を写して埋めてください。

```markdown
### 完了の定義（#13）
- [ ] 完了基準ごとに、証拠（コミット・PR・実行ログ・`research/reviews/` の記録）へのリンクを issue のコメントに残している
- [ ] 成果物は PR でマージしている
- [ ] 成果物に含まれる事実（仕様の節・IdP の値・上限・版）を点検し、`research/reviews/<対象>-<日付>.md` に既存と同じ区分（誤り・過大・不一致・曖昧）で記録し、指摘をすべて反映している
- [ ] lint の抑止設定と、重大度の引き下げが 0 件である（入れる場合は、行ごとの理由が出力に出る）
- [ ] 「対象外」「扱わない」で閉じた行には、「起きない前提」と「その前提が崩れる条件」の両方が書かれている。対象外の件数と割合を成果物の冒頭に載せている
- [ ] 「漏れゼロ」を約束する表現がない
- 点検の方法：（例）別の LLM のセッションで点検。人による点検は未実施（#20）
```

### 各項目の補足

**証拠のリンク**。完了基準 1 つにつき、証拠を 1 つ以上書きます。例：

```markdown
- [x] 152 枚すべてに一意の ID があり、重複が 0 件である
  - 証拠：PR #NN、`tools/slide-ids --check` の実行ログ（Actions の run へのリンク）
```

**点検の記録**。ファイル名は `research/reviews/<対象>-<日付>.md` です（例：`research/reviews/registry-v1-2026-12-05.md`）。区分は既存の記録（`research/reviews/factcheck-2026-11-17.md`）と同じです。

| 区分 | 意味 |
| --- | --- |
| 誤り | 必ず直す |
| 過大 | 原典より強い言い方 |
| 不一致 | 成果物の間、または成果物とスライドの間の食い違い |
| 曖昧 | 読み違えやすい |

記録の表は「対象・区分・指摘・直し方」の 4 列にします。指摘を反映しないものがあれば、その理由を「直し方」に書きます。理由のない未反映は、完了の定義を満たしません。

**lint の抑止**。抑止や重大度の引き下げを入れる場合は、行ごとに理由を書き、その理由が lint の出力に出るようにします。件数は完了のコメントに書きます。

**「対象外」の書き方**。次の 3 つをそろえます。

```yaml
- id: I07   # ID は例
  name: ROPC（Resource Owner Password Credentials）での発行
  status: 対象外
  assumption: 組織のクライアントは ROPC を使わない（RFC 9700 §2.4 が使用を禁じている）
  breaks_when: ROPC でしか動かない旧システムを接続する場合。その場合は対象に戻し、発行イベントとして扱う
```

成果物の冒頭には、`対象外 12 件／全 85 件（14%）` のように件数と割合を書きます。

**「漏れゼロ」を約束しない**。想定漏れが一切ないことは原理的に証明できません（#11 の「約束の範囲」）。「漏れなく」「すべての想定を網羅」「漏れゼロ」とは書かず、何の内側で何を検出するかを書きます。

- 書かない：「このカタログで発行の場面を漏れなく洗い出せる」
- 書く：「種になる一覧（IANA OAuth Parameters など）の全項目が、カタログの行か『対象外』にひもづく。一覧の外の場面は、カタログ外を問う質問で探す」

## 3. 点検者についての取り決め（当面）

人の協力者は当面確保できません。そこで、作成者以外による点検を次の手順で代えます。

1. **別の LLM のセッションで点検する**。作成に使ったものとは別のセッション（会話の履歴を引き継がないもの）で点検します。点検の記録に、次を残します。
   - 日付と、使ったモデルの名前
   - 渡した資料（ファイルのパスとコミット）
   - 渡した指示の全文
   - 出力（指摘の一覧）
2. **作成者が 1 日以上空けてから見直す**。点検の指摘と成果物を、作成から 1 日以上空けて読み直し、指摘ごとに直すか、直さない理由を書きます。記録には、作成の日付と見直しの日付の両方を書きます。
3. **「人による点検は未実施」と明記する**。この方法で閉じた issue のコメントと、成果物の README の「点検状況」に、次の文をそのまま書きます。

   > 人による点検は未実施。作成とは別の LLM のセッションで点検し、作成者が 1 日以上空けて見直した（記録：`research/reviews/<対象>-<日付>.md`）。

   「人で検証済み」「レビュー済み」とだけ書くことはしません。人による点検は、協力者が見つかったときに #20 で行い、終えたものから表示を外します。

## 4. 公開物の取り扱い

### ライセンス

| 対象 | ライセンス |
| --- | --- |
| `templates/` の全ファイル | CC0 1.0（`templates/LICENSE`） |
| ガイド本体（スライド・文章・調査メモ） | CC BY 4.0 |
| コード（`deck/`・`tools/`） | MIT |

`templates/` を CC0 にするのは、利用者が表示の義務なしに、社内の設計書へそのままコピーできるようにするためです。そのため、`templates/` に次のものを入れません。

- 他者が権利を持つ文章（各社の文書、書籍、記事）の写し
- ケーススタディ（CC BY 4.0）の文章の写し。参照は ID で行います（`templates/casestudy-mapping.md`）
- 実行するコード。コードは `tools/` に置き、MIT とします

### IANA の登録値や IdP の値

事実の列挙と出典の URL だけを載せ、各社の文書の文章は写しません。

| 書いてよい | 書かない |
| --- | --- |
| `Cognito の Pre token generation の契機の値：TokenGeneration_RefreshTokens など（出典 URL、確認日）` | 文書の説明文を訳したもの、言い換えただけのもの |
| 値の名前、上限の数値、版、既定値 | 文書の手順や注意書きの文章 |

### 版の管理

テンプレート一式は semver で版を管理します。

- タグ：`templates-vX.Y.Z`（例：`templates-v1.0.0`）。最初の公開版は `templates-v1.0.0` です（#11）。それまでは `0.y.z` です。
- 変更の記録：`templates/CHANGELOG.md`。タグを付ける PR で、「未リリース」の節を版の節に移します。
- 各ファイルの先頭に `template_version` を書きます。未リリースの間は、次に付ける版を書きます。

| 形式 | 書き方 |
| --- | --- |
| Markdown | 1 行目に `<!-- template_version: 0.1.0 -->` |
| YAML | 1 行目に `template_version: 0.1.0` |
| JSON Schema | `$id` に版を入れ（例：`https://.../claims.schema.json/v0.1.0`）、最上位に `"template_version": "0.1.0"` |

`LICENSE` と `CHANGELOG.md` には書きません。

| 上げる桁 | 変更の例 |
| --- | --- |
| メジャー（X） | 列の削除・改名、列の意味や列挙値の変更、任意の列を必須にする。既存の設計書が検査を通らなくなる変更 |
| マイナー（Y） | 任意の列・モジュール・lint の規則（warning）の追加。既存の設計書がそのまま通る変更 |
| パッチ（Z） | 文言の修正、例の修正、根拠の版の更新（中身の判断が変わらないもの） |

lint の規則を error で足すと既存の設計書が通らなくなるので、メジャーとして扱います。

### 作成方法の開示

各成果物の README に、ガイドと同じ書き方で作成方法を書きます。

> 本資料は生成AI（Claude）を使って作成し、筆者が確認して公開しています。

あわせて「点検状況」の節を設け、3. の文を書きます。

### 秘密情報の検出

本リポジトリの CI に secret scan を入れます（CI の土台は #16 で作ります）。

- PR と main への push で動かし、検出したら失敗させます。
- 見本のトークンは、試験用の鍵で署名したものだけを置きます。鍵そのもの（秘密鍵・クライアントシークレット）はリポジトリに入れません。ケーススタディも、鍵を `keys/` に置いてリポジトリから外しています。
- 見本のトークンが検出に掛かる場合の除外は、ファイルごとに理由を書きます（完了の定義の「抑止は行ごとの理由」と同じ扱い）。

### 意図的に誤りを含む教材

誤りを埋め込んだ設計書（#12）やレビュー教材の演習（#5）では、各ファイルの先頭に次の文を書きます。コピーされて設計に使われるのを防ぐためです。

| 形式 | 書き方 |
| --- | --- |
| Markdown | 1 行目の見出しの直後に `> **意図的に誤りを含む教材。設計に使わない**` |
| YAML | `template_version` の次の行に `# 意図的に誤りを含む教材。設計に使わない` |

## 5. 題材

題材は、ケーススタディ（https://github.com/Takenori-Kusaka/jwt-claims-casestudy）のシナリオ A・B・C とします。新しい題材は作りません。実測の結果があり、記入例の判断を実験で裏付けられるためです。

| シナリオ | 名前 | IdP（実験環境） | 本計画での使い道 |
| --- | --- | --- | --- |
| A | マルチテナント SaaS | Keycloak 26.8.0（実物）。レルム t1・t2 をテナントとし、Postgres 16 の行単位の制御（RLS）と組み合わせる | 縦の一本（#16）、台帳の記入例（#3） |
| B | 社内業務システム | Keycloak 26.8.0 のレルム corp（実物）と、Entra ID・Okta・Cognito・Auth0 の形を再現した模擬。入口（ゲートウェイ）で内部トークンに交換する | 台帳の記入例（#3）、パイロット（#9） |
| C | AI エージェントの委任 | 組織のトークン発行サービスの模擬（時刻を進めるため）。MCP 風のツールサーバーを経て請求書の API を呼ぶ。別に、Keycloak 26.8 の標準トークン交換を実測している | パイロット（#9） |

「シナリオ A（Keycloak）」と書くときは、Keycloak だけで閉じているシナリオ A を指します。B も Keycloak を使いますが、ほかの 4 つの IdP の模擬を含みます。

ケーススタディの `catalog/catalog.json`・`SCHEMA.md`・`DECISION_POLICY.md`・`decisions/` と、本計画の台帳（#3）・カタログ（#2）との対応と、どちらを正とするかは、[`casestudy-mapping.md`](casestudy-mapping.md) にあります。要点は次のとおりです。

- 805 行のクレームの一覧と、A・B・C ごとの判定の一覧は、ケーススタディを正とします。`templates/` には写さず、ID で参照します。
- 台帳の行（組織のクレームの設計判断）と、発行・利用イベントのカタログは、`templates/` を正とします。
