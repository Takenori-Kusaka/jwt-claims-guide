# 追加前の 25 問の記入例：`https://claims.example.com/` の `tenant_id`（シナリオ A）

> **記入例です。推奨ではありません。** ケーススタディのシナリオ A の前提での一例です。問いはガイドのスライド 142・143（slide:p11-pre-add-questions-1、slide:p11-pre-add-questions-2）によります。様式（`templates/claim_request.md`）は #4 で作るので、ここでは問いと回答だけを並べました。

- 対象：台帳の `C-tenant-id`（`claims.yaml`）。組織の名前空間の共有クレーム
- 判定（slide:p11-pre-add-questions-1 の「答えられない問いが残るなら共有クレームにしない」）：**25 問すべてに答えた。共有クレームにする**
- Lite の縮小案（`research/template-design/gate1.md` の「Lite の縮小案」）では、この 25 問は Lite でも必須です。共有クレームを足すかどうかの関所だからです。台帳の列で答えられる問い（「台帳」と書いた 11 問）は、台帳から写して生成し、手で書くのは残りの 14 問です

| # | 問い（スライド 142・143） | 回答 | 出どころ |
| --- | --- | --- | --- |
| 1 | 受け手はこのクレームで何を決めるか | saas-api が、iss から引いたテナントと一致するかを照合する（テナントを決めるのは iss）。不一致なら拒否する | 台帳：`usage: authz`、`rationale` |
| 2 | 寿命中に値が変わっても困らないか | 困らない。利用者のテナントは変わらない（テナントの切り替えは無い前提）。テナントの停止は、トークンではなく DB の tenants.status で要求ごとに確かめる | 台帳：`volatility: never`、`on_revoke` |
| 3 | 既存の標準クレームで表せないか | 登録されたテナントのクレームは無い（Entra の `tid` は製品の独自のもの）。iss のレルム名で表せるが、ケーススタディの共通の基準に合わせて明示の写しを載せる | 台帳：`registered_ref` なし、`rationale` |
| 4 | 自組織の名前空間か。予約名と衝突しないか | 名前空間 `https://claims.example.com/` の中。Keycloak の予約名との衝突は無い（名前空間のオブジェクトの中なので最上位の名前と重ならない）。予約名の一覧（#6 の L2・L34）とはまだ照合していない | 手書き |
| 5 | 「.」「/」入りの名前を全ての受け手のツールで参照できるか | 受け手は saas-api（Node.js）だけで、JSON のキーとして `payload["https://claims.example.com/"].tenant_id` で読む。Keycloak のマッパーでは `.` をエスケープして書く（`https://claims\.example\.com/.tenant_id`）。ログの基盤など、ほかのツールで参照する予定は無い | 手書き |
| 6 | トップレベルか、組織のオブジェクトの下か | 組織のオブジェクトの下 | 台帳：`namespace`、`shape: single` |
| 7 | 型は 1 つか。区切り文字列を避けたか | 文字列 1 つ。配列は拒否する（ケーススタディ A12） | 台帳：`type: string`、`shape: single`、`enforced_at` |
| 8 | ID・金額は文字列で運ぶか | 文字列（レルム名。数値にしない） | 手書き |
| 9 | 無い・null・false・空配列の意味は | 無い・null・空文字はどれも拒否する。配列も拒否する。DB の側でも、tenant_id は NOT NULL で空文字を CHECK で禁じる | 台帳：`on_missing: 拒否`、`enforced_at`（saas-api の「null・空文字は拒否」と Postgres の行） |
| 10 | 大文字小文字・空白・比較方法は | 完全一致で比べる（大文字小文字を区別し、前後の空白を取らない）。レルム名は小文字の英数字とハイフンで作る運用にする | 手書き |
| 11 | 誰が値を書けるか。自己申告と分けたか | Keycloak のクライアントの Hardcoded claim マッパー（段階 ②）。テナントの管理者が変えられるので、値をそのまま信じず iss と照合する。利用者本人は書けない | 台帳：`authoritative_writer`、`assumption` |
| 12 | 名前と不変の ID を出し、ID で照合させるか | テナント ID（レルム名）だけを出し、表示名は出さない。**レルム名は Keycloak の管理の操作で変更できるので、不変の ID ではない**（変えると iss も変わる）。この例は「作った後に変えない」運用に頼る（前提）。不変にするなら、レルムの内部 ID（UUID）を値にし、iss との対応表もその ID で持つ案がある（#6 の L3 の対象の候補） | 手書き |
| 13 | 上限は。超えたら失敗か、欠落か | 32 バイト。値域はレルム名で固定なので、発行の側では超えない（超えたときの発行の失敗の仕組みは置かない）。受け手の側では、32 バイトを超える値を拒否する（欠落や切り詰めとして扱わない） | 台帳：`max_bytes: 32`、`overflow_strategy`、`enforced_at` |
| 14 | 全リクエストに載せる価値があるか。宛先ごとに絞れるか | 宛先は saas-api だけで、すべての要求でテナントを照合するので載せる。ID トークンには載せない | 手書き |
| 15 | 付与するのは単一の発行者だけか | テナントのレルム（そのテナントの発行者）だけ。ほかのレルムが出した同じ値は、iss との照合で拒否する | 台帳：`enforced_at`（iss との照合）と `issuers`。縮小 Lite では `issuers` は token_types から生成する列になるので、回答の中身は `enforced_at` から写す |
| 16 | 検証を共通ライブラリで提供するか | この例では受け手が saas-api の 1 つなので、saas-api の中の 1 つの関数にまとめる。受け手が増えたら共通の部品にする | 手書き |
| 17 | ヘッダーに移すとき、同名ヘッダーの偽装（大文字小文字・アンダースコアの変種・重複）を除去するか | ヘッダーには移さない。パスや `X-Tenant` のヘッダーではテナントを決めない（ケーススタディ A5） | 手書き |
| 18 | 未検証の値を流すモードは無いか | 無い。検証を飛ばす設定・デバッグのモードを saas-api に作らない | 手書き |
| 19 | 知らない受け手が無視しても安全か | 安全ではない（テナントの照合をしない受け手は、他テナントのデータを返しうる）。そのため受け手は saas-api に限り、DB の RLS でも絞る | 手書き |
| 20 | ログに残すか。値かハッシュか。個人情報か | 値のまま記録する。個人情報ではない | 台帳：`log_policy: 記録する`、`pii_category: 該当なし` |
| 21 | 委任なら act・承認 ID との関係は | 委任は無い。運用者の横断作業はこの例の範囲外 | 手書き |
| 22 | 台帳に登録し、受け手を把握したか | 登録した（`C-tenant-id`）。受け手は saas-api | 台帳：`consumers` |
| 23 | 形式を変えるときの移行計画はあるか | 名前空間のオブジェクトの版 `v` を上げ、受け手を先に直してから発行者（マッパー）を変える（slide:p11-change-procedure） | 手書き |
| 24 | 改名・廃止の互換期間と並行発行は | 改名の手順：(1) 受け手が新旧の両方の名前を読めるようにする。(2) 発行者（マッパー）が両方を出す。(3) 発行者が新しい名前だけを出す。(4) 古い名前で出した最後の AT の受け入れの上限（330 秒＝寿命 300 秒＋時計のずれ 30 秒）が過ぎてから、受け手は古い名前を読むのをやめる | 手書き |
| 25 | 発行前の確認手段と、受け手の条件のテストは | Keycloak のクライアントスコープの評価（Evaluate）で、発行される AT を確かめる。受け手の条件はケーススタディの A5・A8・A11・A12 と同じ形の拒否のテストで確かめる（#8） | 手書き |

手で書いた問い：14 問（4・5・8・10・12・14・16〜19・21・23〜25）。台帳から写せる問い：11 問。
