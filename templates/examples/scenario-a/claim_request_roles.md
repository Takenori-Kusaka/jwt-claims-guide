# 追加前の 25 問の記入例：`https://claims.example.com/` の `roles`（シナリオ A）

> **記入例です。推奨ではありません。** ケーススタディのシナリオ A の前提での一例です。様式は `templates/claim_request.md`、問いはスライド 142・143（slide:p11-pre-add-questions-1、slide:p11-pre-add-questions-2）によります。

- 対象：台帳の `C-roles`（`claims.yaml`）。組織の名前空間の共有クレーム
- 判定：**25 問すべてに答えた。共有クレームにする**

| # | 問い（スライド 142・143） | 回答 | 出どころ |
| --- | --- | --- | --- |
| 1 | 受け手はこのクレームで何を決めるか | saas-api が、承認（approver）とテナントの管理（tenant-admin）の操作を粗く許すかを決める。請求書ごとの許可（BOLA）は DB の側で確かめる | 台帳：`usage: authz`、`rationale` |
| 2 | 寿命中に値が変わっても困らないか | 困るが許容する。ロールを外しても、受け入れの上限（330 秒）の間は残る。330 秒の遅れを許容として `volatility` に書いた | 台帳：`volatility: 330`、`on_revoke` |
| 3 | 既存の標準クレームで表せないか | 名前は RFC 9068 §2.2.3.1 の `roles` と同じ意味にそろえた。最上位の `roles` は Keycloak の `realm_access` と別の形で出すと受け手が迷うので、組織の名前空間に置く（`C-realm-access` は却下） | 台帳：`registered_ref` なし、`rationale` |
| 4 | 自組織の名前空間か。予約名と衝突しないか | 名前空間のオブジェクトの中。最上位の `roles`（RFC 9068）とは別の場所なので衝突しない | 手書き |
| 5 | 「.」「/」入りの名前を全ての受け手のツールで参照できるか | 受け手は saas-api だけで、`payload["https://claims.example.com/"].roles` で読む。DB の RLS には写さない（ロールは API で判定する） | 手書き |
| 6 | トップレベルか、組織のオブジェクトの下か | 組織のオブジェクトの下 | 台帳：`namespace`、`shape: array` |
| 7 | 型は 1 つか。区切り文字列を避けたか | 文字列の配列。空白・カンマ区切りの文字列にしない（ケーススタディの「共有クレームを変えたとき」で、カンマ区切りは 7 つの受け手が黙って誤った） | 台帳：`type: string`、`shape: array` |
| 8 | ID・金額は文字列で運ぶか | 値はロールの名前（approver・tenant-admin）で、ID・金額ではない | 手書き |
| 9 | 無い・null・false・空配列の意味は | 無い・空配列は「ロールなし」（何も許さない）。null は型の誤りとして拒否する | 台帳：`absent_semantics`、`on_missing: 既定値` |
| 10 | 大文字小文字・空白・比較方法は | 語彙（小文字の 2 語）と完全一致で比べる。語彙の外の値は無視する | 手書き |
| 11 | 誰が値を書けるか。自己申告と分けたか | Keycloak の User Realm Role マッパー（段階 ②）。テナントの管理者がロールの割り当てを変えられる。利用者本人は書けない | 台帳：`authoritative_writer` |
| 12 | 名前と不変の ID を出し、ID で照合させるか | ロールは語彙の値で、利用者の識別子ではない。語彙の値は API の側で固定し、改名しない運用にする | 手書き |
| 13 | 上限は。超えたら失敗か、欠落か | 2 件・1 件 12 バイト。スコープの設定で 2 つのロールだけが出る（Full Scope Allowed をオフ）。受け手は 2 件を超えたら拒否する | 台帳：`max_items: 2`、`max_bytes: 12`、`overflow_strategy` |
| 14 | 全リクエストに載せる価値があるか。宛先ごとに絞れるか | 宛先は saas-api だけで、承認・管理の操作の入口で毎回見る。ID トークンには載せない | 手書き |
| 15 | 付与するのは単一の発行者だけか | テナントのレルムだけ。ほかのレルムが出した `roles` は iss の照合で拒否される | 台帳：`issuers`、`enforced_at` |
| 16 | 検証を共通ライブラリで提供するか | saas-api の 1 つの関数で、配列であること・件数・語彙を確かめる | 手書き |
| 17 | ヘッダーに移すとき、同名ヘッダーの偽装を除去するか | ヘッダーに移さない。`X-User-Role` のようなヘッダーではロールを決めない（ケーススタディ B4 の型） | 手書き |
| 18 | 未検証の値を流すモードは無いか | 無い | 手書き |
| 19 | 知らない受け手が無視しても安全か | 安全ではない。許可を与えるクレームなので、読まない受け手は管理の操作を許してはいけない。受け手は saas-api に限る | 手書き |
| 20 | ログに残すか。値かハッシュか。個人情報か | 値のまま記録する。個人情報ではない（ロールの名前だけ） | 台帳：`log_policy: 記録する`、`pii_category: 該当なし` |
| 21 | 委任なら act・承認 ID との関係は | 委任は無い。足すなら、代理される利用者のロールと代理者の権限を分ける（`act` の側で判断する） | 手書き |
| 22 | 台帳に登録し、受け手を把握したか | 登録した（`C-roles`）。受け手は saas-api | 台帳：`consumers` |
| 23 | 形式を変えるときの移行計画はあるか | 語彙を足すときは、saas-api を先に新しい値に対応させ、その後で Keycloak にロールを足す。形（配列）は変えない | 手書き |
| 24 | 改名・廃止の互換期間と並行発行は | ロールを改名するときは、新旧の両方の名前を一時的に割り当て（並行発行）、saas-api が新しい名前だけを読むようになってから古いロールを外す | 手書き |
| 25 | 発行前の確認手段と、受け手の条件のテストは | Keycloak の Evaluate で、Full Scope Allowed をオフにしたクライアントの AT に 2 つのロールだけが出ることを確かめる（ケーススタディの keycloak.full_scope）。受け手の条件は、3 件のロール・語彙の外の値・null のトークンのテスト（#8） | 手書き |

手で書いた問い：14 問。台帳から写せる問い：11 問。
