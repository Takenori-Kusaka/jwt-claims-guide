# 追加前の 25 問の記入例：`https://claims.example.com/` の `user_id`（シナリオ A）

> **記入例です。推奨ではありません。** ケーススタディのシナリオ A の前提での一例です。様式は `templates/claim_request.md`、問いはスライド 142・143（slide:p11-pre-add-questions-1、slide:p11-pre-add-questions-2）によります。

- 対象：台帳の `C-user-id`（`claims.yaml`）。組織の名前空間の共有クレーム
- 判定：**25 問すべてに答えた。共有クレームにする**（ただし認可の鍵にはしない。問 1）

| # | 問い（スライド 142・143） | 回答 | 出どころ |
| --- | --- | --- | --- |
| 1 | 受け手はこのクレームで何を決めるか | saas-api が `sub` と一致することだけを確かめる。認可（BOLA）の鍵は `sub` で、`user_id` ではない。IdP を替えるときに受け手が移れるように載せておく | 台帳：`usage: identifier`、`rationale` |
| 2 | 寿命中に値が変わっても困らないか | 困らない。値は Keycloak のユーザー ID で、利用者の寿命の間変わらない | 台帳：`volatility: never`、`on_revoke` |
| 3 | 既存の標準クレームで表せないか | 今は `sub` と同じ値で、`sub` で表せる。IdP をまたいで同じ人を指す組織の ID が要る将来のために名前空間に置く（ケーススタディ ORG-02） | 台帳：`registered_ref` なし、`rationale` |
| 4 | 自組織の名前空間か。予約名と衝突しないか | 名前空間 `https://claims.example.com/` のオブジェクトの中。最上位の名前ではないので、Keycloak・IANA の名前とは衝突しない | 手書き |
| 5 | 「.」「/」入りの名前を全ての受け手のツールで参照できるか | 受け手は saas-api（Node.js）だけで、`payload["https://claims.example.com/"].user_id` で読む。ログの基盤では、ハッシュにした値を別の列に写すので、この名前を直接は参照しない | 手書き |
| 6 | トップレベルか、組織のオブジェクトの下か | 組織のオブジェクトの下 | 台帳：`namespace`、`shape: single` |
| 7 | 型は 1 つか。区切り文字列を避けたか | 文字列 1 つ（UUID） | 台帳：`type: string`、`shape: single` |
| 8 | ID・金額は文字列で運ぶか | 文字列（UUID の 36 文字）。数値にしない | 手書き |
| 9 | 無い・null・false・空配列の意味は | 無い・null は拒否する（必須クレーム） | 台帳：`on_missing: 拒否` |
| 10 | 大文字小文字・空白・比較方法は | Keycloak が出す小文字の UUID のまま、`sub` と完全一致で比べる。大小を変換しない | 手書き |
| 11 | 誰が値を書けるか。自己申告と分けたか | Keycloak の User Property マッパー（段階 ②）。テナントの管理者がマッパーを変えられるので、`sub` との一致で確かめる。利用者本人は書けない | 台帳：`authoritative_writer`、`enforced_at` |
| 12 | 名前と不変の ID を出し、ID で照合させるか | このクレームが不変の ID そのもの（`identifier_properties`：stable・再割り当てなし）。名前（`preferred_username`）は載せない | 手書き |
| 13 | 上限は。超えたら失敗か、欠落か | 36 バイト（UUID）。値域が固定なので超えない。受け手は 36 バイトを超える値を拒否する | 台帳：`max_bytes: 36`、`overflow_strategy` |
| 14 | 全リクエストに載せる価値があるか。宛先ごとに絞れるか | 宛先は saas-api だけ（AT）。ID トークンには載せない。今は `sub` と重複するので、IdP を替える計画が無くなれば外す候補（見直しの条件） | 手書き |
| 15 | 付与するのは単一の発行者だけか | テナントのレルムだけ（`issuers` は `https://idp.example.com/realms/{tenant}`）。ほかのレルムの値は iss の照合で拒否される | 台帳：`issuers`、`enforced_at` |
| 16 | 検証を共通ライブラリで提供するか | 受け手が saas-api の 1 つなので、AT の検証の関数の中で `sub` との一致を確かめる。受け手が増えたら共通の部品に移す | 手書き |
| 17 | ヘッダーに移すとき、同名ヘッダーの偽装を除去するか | ヘッダーに移さない。`X-User-Id` などのヘッダーでは利用者を決めない | 手書き |
| 18 | 未検証の値を流すモードは無いか | 無い。署名と `sub` の一致を確かめる前に読まない | 手書き |
| 19 | 知らない受け手が無視しても安全か | 安全（受け手は `sub` で判断し、`user_id` は一致の確認だけに使う） | 手書き |
| 20 | ログに残すか。値かハッシュか。個人情報か | ハッシュにして記録する。個人情報（ほかの情報と照合できる ID） | 台帳：`log_policy: ハッシュ化して記録`、`pii_category: 個人情報` |
| 21 | 委任なら act・承認 ID との関係は | 委任は無い。運用者の代理操作はこの例の範囲外で、足すなら `user_id` は代理される利用者のまま、実行者は `act` に置く | 手書き |
| 22 | 台帳に登録し、受け手を把握したか | 登録した（`C-user-id`）。受け手は saas-api | 台帳：`consumers` |
| 23 | 形式を変えるときの移行計画はあるか | IdP を替えて値の作り方が変わるときは、名前空間の版 `v` を上げ、saas-api を新旧の両方に対応させてからマッパーを替える | 手書き |
| 24 | 改名・廃止の互換期間と並行発行は | 廃止するときは、saas-api が読むのをやめてからマッパーを消す。最後に出した AT の受け入れの上限（330 秒）を待つ | 手書き |
| 25 | 発行前の確認手段と、受け手の条件のテストは | Keycloak の Client Scopes の Evaluate で、AT に `user_id` が `sub` と同じ値で出ることを確かめる。受け手の条件は、`user_id` が `sub` と違うトークンを拒否するテスト（#8） | 手書き |

手で書いた問い：14 問。台帳から写せる問い：11 問。
