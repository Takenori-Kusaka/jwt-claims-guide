# 追加前の 25 問の記入例：`https://claims.example.com/` の `user_id`（シナリオ B）

> **記入例です。推奨ではありません。** ケーススタディのシナリオ B＋C の前提での一例です。様式は `templates/claim_request.md`、問いはガイドのスライド 142・143（slide:p11-pre-add-questions-1、slide:p11-pre-add-questions-2）によります。

- 対象：台帳の `C-user-id`（`claims.yaml`）。組織の名前空間の共有クレーム（組織の利用者 ID）
- 判定（slide:p11-pre-add-questions-1 の「答えられない問いが残るなら共有クレームにしない」）：**25 問すべてに答えた。共有クレームにする**
- 縮小 Lite でもこの 25 問は必須。台帳の列で答えられる 11 問は台帳から写せる（出どころが「台帳」の行）。手で書くのは 14 問

| # | 問い（スライド 142・143） | 回答 | 出どころ |
| --- | --- | --- | --- |
| 1 | 受け手はこのクレームで何を決めるか | 受け手が利用者を識別し、注文・請求書・給与明細の持ち主と照合する | 台帳：`usage`、`rationale` |
| 2 | 寿命中に値が変わっても困らないか | 困らない。不変の ID（退職者の ID は再利用しない） | 台帳：`volatility`、`on_revoke` |
| 3 | 既存の標準クレームで表せないか | sub で表せるのは発行者ごとの ID だけで、IdP をまたいで同じ社員を指せない。STS のトークンでは sub にも同じ値を書くが、IdP をまたぐ照合の契約として名前空間の値を別に持つ | 台帳：`registered_ref` なし、`rationale` |
| 4 | 自組織の名前空間か。予約名と衝突しないか | 名前空間 `https://claims.example.com/` のオブジェクトの中。最上位の名前と重ならないので、Keycloak・外部の IdP の予約名とは衝突しない。予約名の一覧との機械の照合は #6 の L2・L34 | 手書き |
| 5 | 「.」「/」入りの名前を全ての受け手のツールで参照できるか | 受け手は組織共通の検証の部品（Node.js と Java の 2 つの実装）で `payload["https://claims.example.com/"].<名前>` として読む。Keycloak のマッパーでは `.` を退避して `https://claims\.example\.com/.<名前>` と書く。ログの基盤は JSON のパスで読める（確かめた） | 手書き |
| 6 | トップレベルか、組織のオブジェクトの下か | 組織のオブジェクトの下 | 台帳：`namespace`、`shape` |
| 7 | 型は 1 つか。区切り文字列を避けたか | 文字列 1 つ（UUID） | 台帳：`type`、`shape`、`enforced_at` |
| 8 | ID・金額は文字列で運ぶか | 文字列（UUID）。数値にしない | 手書き |
| 9 | 無い・null・false・空配列の意味は | 無い・null・空文字は拒否する | 台帳：`on_missing`、`absent_semantics` |
| 10 | 大文字小文字・空白・比較方法は | 小文字の UUID と完全一致で比べる。入口が小文字に正規化する | 手書き |
| 11 | 誰が値を書けるか。自己申告と分けたか | Keycloak の User Attribute マッパーと入口の STS（対応表）だけ。利用者本人は書けない | 台帳：`authoritative_writer`、`provenance` |
| 12 | 名前と不変の ID を出し、ID で照合させるか | ID だけを出す。表示名（name）は ID トークンだけに載せ、照合には使わない | 手書き |
| 13 | 上限は。超えたら失敗か、欠落か | 36 バイト（UUID）。値域で固定。受け手は UUID の形でない値を拒否する | 台帳：`max_bytes`、`overflow_strategy`、`enforced_at` |
| 14 | 全リクエストに載せる価値があるか。宛先ごとに絞れるか | 組織のトークンのすべての宛先で持ち主の照合に使うので載せる | 手書き |
| 15 | 付与するのは単一の発行者だけか | Keycloak のレルム corp と入口の STS。外部の IdP の利用者は、入口が対応表から書く | 台帳：`authoritative_writer`、`issuers` |
| 16 | 検証を共通ライブラリで提供するか | 組織共通の検証の部品（`template:modules/M_token_validation#shared-validator`）が、型・必須・語彙を確かめて値を返す。各サービスはトークンを自分で解析しない | 手書き |
| 17 | ヘッダーに移すとき、同名ヘッダーの偽装（大文字小文字・アンダースコアの変種・重複）を除去するか | ヘッダーには移さない。入口はクライアントが送った `X-User-*` のヘッダーを、大文字小文字・アンダースコア・重複を含めて捨てる（ケーススタディ B4・B5・B6） | 手書き |
| 18 | 未検証の値を流すモードは無いか | 無い。検証を飛ばす設定・デバッグのモードを部品にも各サービスにも作らない | 手書き |
| 19 | 知らない受け手が無視しても安全か | 安全ではない（照合しない受け手は他人のデータを返しうる）。受け手は共通の部品を使い、持ち主の照合を各サービスの拒否のテストで確かめる | 手書き |
| 20 | ログに残すか。値かハッシュか。個人情報か | ハッシュ化して記録する。個人情報 | 台帳：`log_policy`、`pii_category` |
| 21 | 委任なら act・承認 ID との関係は | 委任のトークンでは「誰の権限で」の利用者を示す（sub と同じ値）。エージェントは act に書き、この値には書かない | 手書き |
| 22 | 台帳に登録し、受け手を把握したか | 登録した（`C-user-id`）。受け手は gateway・orders・ledger・docs・payroll・invoice-mcp・invoices | 台帳：`consumers` |
| 23 | 形式を変えるときの移行計画はあるか | 名前空間オブジェクトの版 `v`（C-v）を上げ、受け手（共通の部品）を先に新旧の両方を読めるように直し、その後で発行者（Keycloak のマッパーと入口の STS）を変える（slide:p11-change-procedure） | 手書き |
| 24 | 改名・廃止の互換期間と並行発行は | 改名の予定は無い。payroll の社員番号（C-employee-id）の廃止の移行先 | 手書き |
| 25 | 発行前の確認手段と、受け手の条件のテストは | Keycloak のクライアントスコープの評価（Evaluate）で KC_AT を確かめる。入口の STS の発行は、発行側の検査用の JSON Schema（`schemas/INT_AT.issuer.schema.json`）で CI で確かめる。受け手の条件は拒否のテスト（#8）で確かめる | 手書き |
