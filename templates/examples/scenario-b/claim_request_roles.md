# 追加前の 25 問の記入例：`https://claims.example.com/` の `roles`（シナリオ B）

> **記入例です。推奨ではありません。** ケーススタディのシナリオ B＋C の前提での一例です。様式は `templates/claim_request.md`、問いはガイドのスライド 142・143（slide:p11-pre-add-questions-1、slide:p11-pre-add-questions-2）によります。

- 対象：台帳の `C-roles`（`claims.yaml`）。組織の名前空間の共有クレーム（粗いロール）
- 判定（slide:p11-pre-add-questions-1 の「答えられない問いが残るなら共有クレームにしない」）：**25 問すべてに答えた。共有クレームにする**
- 縮小 Lite でもこの 25 問は必須。台帳の列で答えられる 11 問は台帳から写せる（出どころが「台帳」の行）。手で書くのは 14 問

| # | 問い（スライド 142・143） | 回答 | 出どころ |
| --- | --- | --- | --- |
| 1 | 受け手はこのクレームで何を決めるか | orders が管理・編集の操作を許すかを決める | 台帳：`usage`、`rationale` |
| 2 | 寿命中に値が変わっても困らないか | 困る場合がある。ロールを外しても INT_AT の受け入れの上限（330 秒）まで残る。管理の操作では orders が Keycloak の利用者のロールを引き直す | 台帳：`volatility`、`on_revoke` |
| 3 | 既存の標準クレームで表せないか | 最上位の roles（RFC 9068 §2.2.3.1）は IdP ごとに意味と語彙が違い、Auth0 では予約名で黙って外れる（B20）。組織の語彙に正規化した値として名前空間に置く | 台帳：`registered_ref` なし、`rationale` |
| 4 | 自組織の名前空間か。予約名と衝突しないか | 名前空間の中。最上位の `roles`（RFC 9068）は `C-rfc-roles` として却下し、Auth0 が予約名の `roles` を黙って外す問題（ケーススタディ B20）も避ける | 手書き |
| 5 | 「.」「/」入りの名前を全ての受け手のツールで参照できるか | 受け手は gateway と orders だけ。orders の Node.js の実装で読めることは、ケーススタディの実験の orders で確かめた形と同じ。ほかの受け手は読まない | 手書き |
| 6 | トップレベルか、組織のオブジェクトの下か | 組織のオブジェクトの下 | 台帳：`namespace`、`shape` |
| 7 | 型は 1 つか。区切り文字列を避けたか | 文字列の配列。区切りの文字列にしない | 台帳：`type`、`shape`、`enforced_at` |
| 8 | ID・金額は文字列で運ぶか | 該当しない（ID・金額でない） | 手書き |
| 9 | 無い・null・false・空配列の意味は | 無いときは拒否する（超過で消えたのを「ロールなし」と読まない。B8）。空の配列は「ロールなし」 | 台帳：`on_missing`、`absent_semantics` |
| 10 | 大文字小文字・空白・比較方法は | 語彙は小文字の英字に固定し、完全一致で比べる。語彙の外の値は無視する | 手書き |
| 11 | 誰が値を書けるか。自己申告と分けたか | Keycloak のレルムロール（管理者が付ける）と入口の対応表。Cognito の custom:role のような本人が書ける値は使わない（B18） | 台帳：`authoritative_writer`、`provenance` |
| 12 | 名前と不変の ID を出し、ID で照合させるか | ロールの名前を出す。ロールは識別子ではないので、ID と対にしない | 手書き |
| 13 | 上限は。超えたら失敗か、欠落か | 4 件・1 件 6 バイト。値域が語彙で閉じているので超えない。4 件を超えたら受け手が拒否する | 台帳：`max_bytes`、`overflow_strategy`、`enforced_at` |
| 14 | 全リクエストに載せる価値があるか。宛先ごとに絞れるか | orders 宛ての INT_AT にだけ載せる（ledger・docs・payroll 宛てには載せない） | 手書き |
| 15 | 付与するのは単一の発行者だけか | Keycloak のレルム corp と入口の STS | 台帳：`authoritative_writer`、`issuers` |
| 16 | 検証を共通ライブラリで提供するか | orders の 1 か所で、配列であること・4 件以下・語彙の中であることを確かめる。gateway は写すときに語彙に絞る | 手書き |
| 17 | ヘッダーに移すとき、同名ヘッダーの偽装（大文字小文字・アンダースコアの変種・重複）を除去するか | ヘッダーに移さない。`X-User-Role` は入口で大文字小文字・アンダースコア・重複を含めて捨てる（ケーススタディ B4〜B6 はこのクレームの値を偽装する型） | 手書き |
| 18 | 未検証の値を流すモードは無いか | 無い。ロールが無いトークンを「全部許す（`*`）」で処理する既定値を作らない（ケーススタディ B8 の型） | 手書き |
| 19 | 知らない受け手が無視しても安全か | 安全ではない（無視すると管理の操作を誰にでも許しうる）。読むのは orders だけで、拒否のテストで確かめる | 手書き |
| 20 | ログに残すか。値かハッシュか。個人情報か | 値のまま記録する。個人情報ではない | 台帳：`log_policy`、`pii_category` |
| 21 | 委任なら act・承認 ID との関係は | 委任のトークン（AGENT_AT・TASK_AT）には載せない。エージェントの権限は scope と act の方針表で決める | 手書き |
| 22 | 台帳に登録し、受け手を把握したか | 登録した（`C-roles`）。受け手は gateway・orders | 台帳：`consumers` |
| 23 | 形式を変えるときの移行計画はあるか | ロールを足すときは、orders を先に新しい値に対応させてから対応表に足す。形（配列）は変えない | 手書き |
| 24 | 改名・廃止の互換期間と並行発行は | ロールの名前を変えるときは、受け手が新旧の両方の名前を語彙に持ち、入口が新しい名前を出し、受け入れの上限（330 秒）の後で古い名前を語彙から消す | 手書き |
| 25 | 発行前の確認手段と、受け手の条件のテストは | Evaluate で、Full Scope Allowed をオフにした portal の KC_AT に 4 つの語彙の外のロールが出ないことを確かめる。INT_AT は `schemas/INT_AT.issuer.schema.json`（語彙が閉じているので enum）で確かめる。受け手の条件は、5 件・語彙の外・null のロールのテスト（#8） | 手書き |
