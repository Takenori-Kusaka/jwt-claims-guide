# 追加前の 25 問の記入例：`https://claims.example.com/` の `tenant_id`（シナリオ B）

> **記入例です。推奨ではありません。** ケーススタディのシナリオ B＋C の前提での一例です。様式は `templates/claim_request.md`、問いはガイドのスライド 142・143（slide:p11-pre-add-questions-1、slide:p11-pre-add-questions-2）によります。

- 対象：台帳の `C-tenant-id`（`claims.yaml`）。組織の名前空間の共有クレーム（テナント（固定値 corp））
- 判定（slide:p11-pre-add-questions-1 の「答えられない問いが残るなら共有クレームにしない」）：**25 問すべてに答えた。共有クレームにする**
- 縮小 Lite でもこの 25 問は必須。台帳の列で答えられる 11 問は台帳から写せる（出どころが「台帳」の行）。手で書くのは 14 問

| # | 問い（スライド 142・143） | 回答 | 出どころ |
| --- | --- | --- | --- |
| 1 | 受け手はこのクレームで何を決めるか | すべての受け手が、corp 以外のテナントのトークンを拒否する（社内システムなのでテナントは 1 つ） | 台帳：`usage`、`rationale` |
| 2 | 寿命中に値が変わっても困らないか | 困らない。値は corp に固定 | 台帳：`volatility`、`on_revoke` |
| 3 | 既存の標準クレームで表せないか | 登録されたテナントのクレームは無い（Entra の tid は製品の独自のもの）。ケーススタディの共通の基準（ORG-01）に合わせて明示の値を載せる | 台帳：`registered_ref` なし、`rationale` |
| 4 | 自組織の名前空間か。予約名と衝突しないか | 名前空間 `https://claims.example.com/` のオブジェクトの中。最上位の名前と重ならないので、Keycloak・外部の IdP の予約名とは衝突しない。予約名の一覧との機械の照合は #6 の L2・L34 | 手書き |
| 5 | 「.」「/」入りの名前を全ての受け手のツールで参照できるか | 受け手は組織共通の検証の部品（Node.js と Java の 2 つの実装）で `payload["https://claims.example.com/"].<名前>` として読む。Keycloak のマッパーでは `.` を退避して `https://claims\.example\.com/.<名前>` と書く。ログの基盤は JSON のパスで読める（確かめた） | 手書き |
| 6 | トップレベルか、組織のオブジェクトの下か | 組織のオブジェクトの下 | 台帳：`namespace`、`shape` |
| 7 | 型は 1 つか。区切り文字列を避けたか | 文字列 1 つ。配列は拒否する（ケーススタディ G13） | 台帳：`type`、`shape`、`enforced_at` |
| 8 | ID・金額は文字列で運ぶか | 文字列 | 手書き |
| 9 | 無い・null・false・空配列の意味は | 無い・null・空文字はどれも拒否する（既定のテナントで処理しない。G12） | 台帳：`on_missing`、`absent_semantics` |
| 10 | 大文字小文字・空白・比較方法は | 小文字の corp と完全一致で比べる | 手書き |
| 11 | 誰が値を書けるか。自己申告と分けたか | Keycloak の Hardcoded claim マッパーと入口の STS だけ。利用者もクライアントも書けない | 台帳：`authoritative_writer`、`provenance` |
| 12 | 名前と不変の ID を出し、ID で照合させるか | テナントの ID だけを出し、表示名は出さない。corp は変えない値として扱う | 手書き |
| 13 | 上限は。超えたら失敗か、欠落か | 4 バイト。値は固定なので超えない。受け手は corp 以外を拒否する | 台帳：`max_bytes`、`overflow_strategy`、`enforced_at` |
| 14 | 全リクエストに載せる価値があるか。宛先ごとに絞れるか | すべての組織のトークンに載せる（4 バイトで費用が小さく、将来テナントを分けるときに型を変えずに済む）。ID トークンには載せない | 手書き |
| 15 | 付与するのは単一の発行者だけか | Keycloak のレルム corp（KC_AT）と入口の STS（INT_AT・AGENT_AT・TASK_AT）。外部の IdP の値は読まない | 台帳：`authoritative_writer`、`issuers` |
| 16 | 検証を共通ライブラリで提供するか | 組織共通の検証の部品（`template:modules/M_token_validation#shared-validator`）が、型・必須・語彙を確かめて値を返す。各サービスはトークンを自分で解析しない | 手書き |
| 17 | ヘッダーに移すとき、同名ヘッダーの偽装（大文字小文字・アンダースコアの変種・重複）を除去するか | ヘッダーには移さない。入口はクライアントが送った `X-User-*` のヘッダーを、大文字小文字・アンダースコア・重複を含めて捨てる（ケーススタディ B4・B5・B6） | 手書き |
| 18 | 未検証の値を流すモードは無いか | 無い。検証を飛ばす設定・デバッグのモードを部品にも各サービスにも作らない | 手書き |
| 19 | 知らない受け手が無視しても安全か | 今は安全（値は 1 つ）。テナントを分けたら、照合しない受け手が他テナントのデータを返しうるので、そのときに受け手の照合を必須にする（revisit_trigger） | 手書き |
| 20 | ログに残すか。値かハッシュか。個人情報か | 値のまま記録する。個人情報ではない | 台帳：`log_policy`、`pii_category` |
| 21 | 委任なら act・承認 ID との関係は | 委任のトークンでも同じ値。act・承認 ID とは関係しない | 手書き |
| 22 | 台帳に登録し、受け手を把握したか | 登録した（`C-tenant-id`）。受け手は gateway・orders・ledger・docs・payroll・invoice-mcp・invoices | 台帳：`consumers` |
| 23 | 形式を変えるときの移行計画はあるか | 名前空間オブジェクトの版 `v`（C-v）を上げ、受け手（共通の部品）を先に新旧の両方を読めるように直し、その後で発行者（Keycloak のマッパーと入口の STS）を変える（slide:p11-change-procedure） | 手書き |
| 24 | 改名・廃止の互換期間と並行発行は | 改名の予定は無い。改名するなら、受け手が新旧の両方を読めるようにし、発行者が両方を出し、最後の INT_AT の受け入れの上限（330 秒）の後で古い名前を消す | 手書き |
| 25 | 発行前の確認手段と、受け手の条件のテストは | Keycloak のクライアントスコープの評価（Evaluate）で KC_AT を確かめる。入口の STS の発行は、発行側の検査用の JSON Schema（`schemas/INT_AT.issuer.schema.json`）で CI で確かめる。受け手の条件は拒否のテスト（#8）で確かめる | 手書き |
