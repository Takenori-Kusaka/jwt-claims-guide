# レビューの手順（読み方）

設計書の PR をレビューする順序です。段には番号があり、レビューレポートの「実施した手順の段」に、どこまで行ったかを番号で書きます（[report_template.md](report_template.md)）。

- 作成方法：本資料は生成AI（Claude）を使って作成し、筆者が確認して公開しています。人による点検は未実施
- 段の順序と時間の目安は筆者の提案です（追跡 #5。#9 のパイロットで測って直す）

<a id="steps"></a>

## 段の一覧

| 段 | すること | 使うもの | 終わりの条件 |
| --- | --- | --- | --- |
| 0 | 受け付け | 設計書の 1.（CI の結果）、README の Lite／Full の判定 | CI の error が 0。Lite／Full の判定が README の 5 問と合う |
| 1 | 範囲と自信のない点を読む | 設計書の 12.・2.・6. | 書き手が自信のない点と、範囲の外にしたものを書き出した |
| 2 | 問い × 仕組みを判断の木で確かめる | [decision_tree.md](decision_tree.md)、対比表 | 6. の要る問いのすべてで、木の節と設計の仕組みを比べた |
| 3 | 6 段の問いに答える | [perspectives.md](perspectives.md) の 1.〜6. | 全問に Yes／No／該当なし（理由つき）を付けた |
| 4 | 追加前の 25 問と理由を採点する | perspectives.md の 1.2、[rationale_rubric.md](rationale_rubric.md) | 共有クレームの全件の 25 問を見た。理由を抜き取って採点した |
| 5 | 一覧の外を探す | perspectives.md の `q-outside-catalog`、図と経路 | カタログ外の場面と、問いの一覧に無い気づきを書いた |
| 6 | 専門家に回す | [escalation.md](escalation.md) | 基準に当たる行を全部回した（または当たらないことを確かめた） |
| 7 | 記録して戻す | report_template.md | 指摘・対応・回した項目・カタログと観点書に戻す事項を書いた |
| 8 | 対応を確かめて閉じる | report_template.md の対応の一覧 | 全指摘が「直した」「直さない（理由を確かめた）」「保留（追跡 issue）」のどれか |

<a id="step-0"></a>

## 0. 受け付け

1. 設計書の 1.（`template:00_core#ci-results`）に、claim_lint の結果が貼られ、error が 0 か。0 でなければレビューに入らず返す
   - lint の版の扱い：判定は、設計書のコミットの時点の lint の結果（設計書の 1. に貼られたもの）と、今の main の lint の結果の両方を見る。今の lint で新たに出た error は、規則が後で厳しくなったものなので、受け付けは止めずに、種別「実装とのずれ」の指摘として記録する（シナリオ B の較正の F01）
2. 設計書の冒頭の「Lite／Full」が、README の 5 問（`template:README#lite-criteria`）の答えと合うか。1 つでも Yes なのに Lite なら、Full に書き直すよう返す（シナリオ A の A17）
3. 設計書に「CI の結果」として書かれた lint の挙動の記述（「R8 の info が出る」など）が、貼られた結果と合うか（シナリオ A の A06）

<a id="step-1"></a>

## 1. 範囲と自信のない点を読む

1. **12.（書き手が自信のない点）から読む**。ここに書かれた点は、指摘の候補の第一です
2. 2.（範囲と信頼の境界）の図で、境界・入口・データ層・範囲の外を確かめ、矢印ごとに「攻撃者が触れるもの」（ヘッダー・本人の属性・テナントの管理画面・トークンのヘッダー）を書き出す
3. 6.（問い × 仕組み）で、ユースケースごとに「要る」とした問いを書き出す

<a id="step-2"></a>

## 2. 問い × 仕組みを判断の木で確かめる

問いごとに判断の木の節を選び、設計書の仕組みと比べます。違えば「目的と仕組みの不一致」として、**取り違えた問い**（判断の木の節の ID か `questions.yaml` の ID）を書きます。迷ったら対比表（[contrasts/](contrasts/)）の「解く問い」の表を見ます。

<a id="step-3"></a>

## 3. 6 段の問いに答える

段ごとに、担当の役割（perspectives.md の各段の「誰が確かめるか」）のレビュアーが答えます。

| 段 | 担当の役割 | 主に開く欄 |
| --- | --- | --- |
| 1. 定義 | 台帳の持ち主＋受け手の代表 | `claims.yaml`、`claim_request_*.md` |
| 2. 発行 | 発行者 | `claims.yaml` の書き手の列、IdP のモジュール、`catalog_answers.yaml` |
| 3. 伝搬 | 入口 | `hops.yaml`、シーケンス図、範囲の図 |
| 4. 検証 | 受け手 | `token_types.yaml`、M_token_validation |
| 5. 認可 | 受け手（PEP・PDP・データ層） | `claims.yaml` の `enforced_at`、M_authz_pdp、M_data_layer |
| 6. 運用 | 運用 | 9. ライフサイクル表、`token_types.yaml` の寿命・失効・鍵の列 |

- 問いごとに Yes／No／該当なし を付けます。「該当なし」には理由を書きます（例：「JWE を使わない」）
- 見る欄が空で判定できないときは No と同じに扱い、指摘にします
- lint が通っている欄でも、問いを省きません。lint は宣言の有無を見て、理由の妥当さは見ません
- 問いの見る欄がモジュール・プロファイルの欄（`template:modules/…`・`template:profiles/…`）で、設計書にその欄が無いときは、台帳の列で答えられるなら答えて「代替」と書き、答えられなければ No にします。Full の設計書で、使うと決めたモジュールの欄が無いこと自体も指摘にします（シナリオ B の較正の F13）

<a id="step-4"></a>

## 4. 追加前の 25 問と理由を採点する

1. 共有クレームのすべてについて、`claim_request_<名前>.md` を perspectives.md の 1.2 の問い（`pa-01`〜`pa-25`・`pa-gate`・`pa-trace`）で確かめる
2. 台帳の `rationale`（採用・却下の理由）を抜き取り、[rationale_rubric.md](rationale_rubric.md) で採点する。抜き取りの数は、採用の行と却下の行からそれぞれ 5 件（5 件未満なら全件）。乱数の種か選んだ行の ID をレポートに書く
3. 不合格の理由は、種別「理由の不備」の指摘にする

<a id="step-5"></a>

## 5. 一覧の外を探す

1. `q-outside-catalog` に答える（カタログの外の発行・利用の場面）
2. 問いの一覧に無い気づきを、出どころ「テンプレート外」として書く。**0 件が続くことは良い兆しではありません**（問いの一覧に慣れて、外を見なくなった印のことがある。[metrics.md](metrics.md)）

<a id="step-6"></a>

## 6. 専門家に回す

[escalation.md](escalation.md) の基準の表を上から順に見て、当てはまる行を回します。当てはまらない基準も、「当てはまらない」と確かめたことをレポートに書きます。

<a id="step-7"></a>

## 7. 記録して戻す

- 指摘を [report_template.md](report_template.md) に書く。場所は、設計書の節（項目 ID）・台帳の行の ID と列・25 問の番号・観点書の問い ID で書く
- **戻す**：見つけた漏れを、次のどれかに戻す。戻す PR か issue をレポートに書く
  - カタログ（`templates/catalog/`）：カタログ外の発行・利用の場面
  - 観点書（この文書群）：問いが無かった、問いはあったが見る欄が分からなかった
  - 対応表（`templates/trace/`）：スライドの規則が要件になっていなかった
  - lint・実行テスト：機械で拾えるのに拾えなかった

<a id="step-8"></a>

## 8. 対応を確かめて閉じる

全指摘の判定と対応の状態がそろったら閉じます。閉じた後に見つかった欠陥は [escaped_defects.md](escaped_defects.md) に記録します。

<a id="single-reviewer"></a>

## 1 名で行う場合

レビュアーが 1 名しかいないときは、役割を切り替えて読みます。1 人で 6 つの役割を同時に持つと、書き手と同じ前提で読んでしまうためです。

1. **書いた人と別の人が行う**。書き手が自分の設計書をレビューするのは、この手順の外です（書き手のセルフチェックとして段 0〜3 を使うのはよい）
2. **役割を 1 つずつ切り替える**。perspectives.md の 7.（役割ごとの索引）の順に、1 つの役割で読み終えてから次へ進む。順序は、攻撃者 → 受け手 → 発行者 → 運用 → 個人情報 → クライアント（攻撃者の視点を先にするのは、前提を疑う読み方を最初に作るため）
3. **時間を分ける**。段 0〜3 と段 4〜6 を別の日に行う。1 日空けて、段 3 の No の指摘を読み直し、取り下げるものと重大度を変えるものを決める。LLM のセッションがレビュアーのときは、日を分ける代わりに、段 3 の No の指摘を別の新しいセッションに読み直させる（そのセッションには指摘と設計書だけを渡す）
4. **LLM を 2 人目の目として使ってよい**（下の「LLM で一次スクリーニングする」）。ただし LLM の指摘は、出どころ「LLM」として区別し、レビュアーが 1 件ずつ採否を決める
5. **専門家に回す基準を緩めない**。1 名のときほど、escalation.md に当たる行は回す
6. レポートの「レビュアーと役割」に「1 名（役割を切り替えた）」と書き、切り替えの順と日付を書く

根拠：templates/CONTRIBUTING.md の 3.、筆者の提案：1 名で行う場合の役割の切り替えの順（追跡 #5）

<a id="llm-screening"></a>

## LLM で一次スクリーニングする

LLM によるレビューの自動化は、この計画の範囲の外です（#11）。ここでは、人のレビューの前の一次スクリーニングとして使う手順だけを書きます。

1. 渡すもの：設計書のディレクトリ、この観点書と対比表、判断の木。渡さないもの：書き手の結論・レビュアーの見立て・「正しいことを確かめて」のような答えを前提にした指示（追認になるのを防ぐ。`templates/CONTRIBUTING.md` の 3.）
2. 指示：「perspectives.md の各問いに、見る欄を開いて Yes／No を付け、No の問いを指摘として、場所（項目 ID・台帳の ID と列）とともに出す」
3. 記録：日付・モデルの名前・渡した資料（パスとコミット）・指示の全文・出力
4. 人の確認：LLM の指摘のすべてを、レビュアーが採用・却下・保留に分ける。却下にも理由を書く。採用した指摘の出どころは「LLM」のままにする（[metrics.md](metrics.md) で、LLM の指摘の採用率を測る）
5. LLM が「指摘なし」と出した問いも、人のレビューで省かない
