# レビューの手順（読み方）

設計書の PR をレビューする順序です。段には番号があり、レビューレポートの「実施した手順の段」に、どこまで行ったかを番号で書きます（[report_template.md](report_template.md)）。

- 作成方法：本資料は生成AI（Claude）を使って作成し、筆者が確認して公開しています。人による点検は未実施
- **レビュアーが答えるのは、人の判断が要る問いだけです**（[short_list.md](short_list.md)）。観点書（[perspectives.md](perspectives.md)）の全問には答えません。機械で確かめられる問いは lint が、書き手が確かめられる問いは書き手の提出前のチェックリストが受け持ちます（#56。振り分けは [triage.yaml](triage.yaml)）
- 段の順序・時間の目安・問いの数は筆者の提案です（追跡 #56。パイロット #9 は LLM によるレビューで、人の時間は測れていません。人による確かめは #20）
- **時間の目安は、段 0〜6 の全部で 60〜100 分です**（LLM の見積もり。人では測っていません）。そのうち、問いに答える時間（段 3 と段 5）が 30〜60 分です

<a id="steps"></a>

## 段の一覧

| 段 | すること | 使うもの | 終わりの条件 | 時間の目安 |
| --- | --- | --- | --- | --- |
| 0 | 受け付け | 設計書の 1.（CI の結果）、PR の自己点検、README の Lite／Full の判定 | lint の error が 0。書き手の自己点検が済み、No なら Blocker の行から 3 件を抜き取って確かめた。Lite／Full の判定が README の 5 問と合う | 10 分 |
| 1 | 範囲・自信のない点・設計の性質を読む | 設計書の 12.・2.・6.、`python tools/review_triage.py --design` | 書き手が自信のない点と、範囲の外にしたものを書き出した。性質の表を図と要求に照らし、出す問いが決まった | 10 分 |
| 2 | 問い × 仕組みを判断の木で確かめる | [decision_tree.md](decision_tree.md)、対比表 | 6. の要る問いのすべてで、木の節と設計の仕組みを比べた | 5〜10 分 |
| 3 | 短い一覧の問いに答える | `--design` の 1 枚（全部の問いは [short_list.md](short_list.md) の 2.・3.） | 出た問い（15〜25 問が目安）に、自分の言葉の答えか、指摘を付けた | 20〜40 分 |
| 4 | 理由と根拠を抜き取って確かめる | [rationale_rubric.md](rationale_rubric.md) | 却下の行から抜き取った理由を採点し、根拠つきの行から 3 件の引用先を読んだ | 10〜15 分 |
| 5 | 開いた問いで、一覧の外を辿る | short_list.md の 4. | 開いた問いごとに、辿った範囲と気づきを書いた | 10〜20 分 |
| 6 | 専門家に回す | [escalation.md](escalation.md)、short_list.md の 5. | 基準に当たる行を全部回した（または当たらないことを確かめた） | 5 分 |
| 7 | 記録して戻す | report_template.md | 指摘・対応・回した項目・カタログと観点書に戻す事項を書いた | — |
| 8 | 対応を確かめて閉じる | report_template.md の対応の一覧 | 全指摘が「直した」「直さない（理由を確かめた）」「保留（追跡 issue）」のどれか | — |

段 0〜6 の目安を足すと 60〜100 分です。#56 が目標にした「1 回のレビューで 30〜60 分」には、**問いに答える時間（段 3 と段 5）しか収まっていません**。受け付け・読み・抜き取り・専門家に回す分は、その外です。どの数字も LLM の見積もりで、人では測っていません（設計書の長さで大きく変わります。パイロットの設計書は 1,000 行を超えます）。超えそうなら、優先 1 の問いと開いた問いを先に済ませ、答えなかった問いをレポートに書きます。**全部に答えることより、優先 1 の問いと開いた問いに時間を使うことを優先します**（パイロットでは、人の判断が要る Major の指摘の半分が、問いの一覧の外から出ました。`research/template-design/pilot.md` の 9.）。

<a id="step-0"></a>

## 0. 受け付け

機械と書き手が受け持つ分が済んでいることを確かめます。ここで済んでいないものを、レビュアーが代わりに確かめることはしません。

1. 設計書の 1.（`template:00_core#ci-results`）に、claim_lint の結果が貼られ、error が 0 か。0 でなければレビューに入らず返す
   - lint の版の扱い：判定は、設計書のコミットの時点の lint の結果（設計書の 1. に貼られたもの）と、今の main の lint の結果の両方を見る。今の lint で新たに出た error は、規則が後で厳しくなったものなので、受け付けは止めずに、種別「実装とのずれ」の指摘として記録する（シナリオ B の較正の F01）
   - warn には、行ごとの理由が書いてあるか（[../CONTRIBUTING.md](../CONTRIBUTING.md) の 2.）。warn の出た行は、段 3 で関係する問いを出す（short_list.md の 3.）
2. PR に、書き手の提出前の自己点検（`.github/PULL_REQUEST_TEMPLATE/design_doc.md`。観点書の区分 B の問いと、規則がまだ無い区分 A の問い）があるか。無ければ、書き手に求めて返す
   - **印の無い行**（書き手が「満たさない」「当てはまらない」とした行）を読み、理由が通らなければ指摘にする
   - **印のある行から、【No なら Blocker】の行を 3 件抜き取り、見る欄を開いて確かめる**（5 分。3 件未満なら全件）。印を付け間違えた行は、ほかに誰も見ないためです。データ層の行（DB の文脈の設定・RLS をすり抜ける主体・文脈が欠けたときの扱い）があれば、そこから選びます（シナリオ A の較正で、レビュアーが Blocker を見つけた場所。A04・A12・A13）。食い違いがあれば指摘にし、残りの印つきの行も疑って、書き手に見直しを求めます
3. 設計書の冒頭の「Lite／Full」が、README の 5 問（`template:README#lite-criteria`）の答えと合うか。1 つでも Yes なのに Lite なら、Full に書き直すよう返す（シナリオ A の A17。lint の `lint:L73` も warn を出す）
4. 設計書に「CI の結果」として書かれた lint の挙動の記述（「R8 の info が出る」など）が、貼られた結果と合うか（シナリオ A の A06）

<a id="step-1"></a>

## 1. 範囲・自信のない点・設計の性質を読む

1. **12.（書き手が自信のない点）から読む**。ここに書かれた点は、指摘の候補の第一です
2. 2.（範囲と信頼の境界）の図で、境界・入口・データ層・範囲の外を確かめ、矢印ごとに「攻撃者が触れるもの」（ヘッダー・本人の属性・テナントの管理画面・トークンのヘッダー）を書き出す
3. 6.（問い × 仕組み）で、ユースケースごとに「要る」とした問いを書き出す
4. **設計の性質を読み、出す問いを決める**（short_list.md の 1.）。`python tools/review_triage.py --design <設計書のディレクトリ>` が、12 の性質（委任がある・発行者が複数ある・個人情報を載せる など）を「当たる／当たらない／読めない」と読んだ欄つきで出し、当たる問いだけを 1 枚にします（エディターのレビューモードの「観点のチェックリスト」も同じ）
   - 性質は、台帳が示すか、書き手がカタログへの回答で宣言していれば当たります。読むためのファイルが無い性質は「読めない」になり、その問いは出ます
   - **表の 12 行を、図と要求に照らして確かめます**（1〜2 分）。「当たらない」とされた性質が実際にはある（例：要求には代理の主体がいるのに、委任が「当たらない」）なら、それ自体を指摘にし、その行に書かれた「出さない問い」も足して答えます。ここを飛ばすと、書き手が書き落とした分だけ、一覧が黙って短くなります

<a id="step-2"></a>

## 2. 問い × 仕組みを判断の木で確かめる

問いごとに判断の木の節を選び、設計書の仕組みと比べます。違えば「目的と仕組みの不一致」として、**取り違えた問い**（判断の木の節の ID か `questions.yaml` の ID）を書きます。迷ったら対比表（[contrasts/](contrasts/)）の「解く問い」の表を見ます。

<a id="step-3"></a>

## 3. 短い一覧の問いに答える

`--design` の 1 枚の問いを、読む単位ごとに答えます。台帳の行を読みながら答える問い、ホップと範囲の図を読みながら答える問い、全体を読んでから答える問いの順です。問いは 1 文で、その下の「手がかり」は、見る場所と、あわせて確かめることです。

| 読む単位 | 主に開く欄 |
| --- | --- |
| クレームの行 | `claims.yaml`（書き手・出どころ・鮮度の列）、`claim_request_*.md` |
| 経路 | `hops.yaml`、範囲の図、シーケンス図、`claims.yaml` の `enforced_at` |
| 設計の全体 | 9. ライフサイクル表、`token_types.yaml` の寿命・失効・鍵の列、`catalog_answers.yaml` |

- **Yes／No だけで済ませません**。問いごとに、自分の言葉で答えを 1 行書きます（例：`q-revocation-delivery` なら「ロールを外してから最悪 5 分で止まる。支払いはその場で問い合わせる」）。書けない・設計書から読み取れないなら No にして、指摘にします
- 行ごとの問い（「値ごとに」「行ごとに」）は、全部の行に答えを書く必要はありません。認可・識別子に使う行を順に見て、答えが変わる行だけを書きます
- 記録の回答は Yes／No／該当なし で、答えの 1 行は「理由」に書きます。「該当なし」には理由を書きます
- 優先 1 を先に、優先 2 を次に答えます。優先 3 と、区分 A・B・D の問いには答えません。気になったときは、観点書の該当の問いを開いて答えてもかまいません（その分は、レポートの 8. に足します）
- 問いの見る欄・No のときの重大度の目安・根拠は、観点書の同じ ID の問いにあります。見る欄がモジュール・プロファイルの欄で、設計書にその欄が無いときは、台帳の列で答えられるなら答えて「代替」と書き、答えられなければ No にします
- lint の warn が出ている行は、short_list.md の 3. の問いも答えます

<a id="step-4"></a>

## 4. 理由と根拠を抜き取って確かめる

1. 台帳の `rationale`（却下の理由）を抜き取り、[rationale_rubric.md](rationale_rubric.md) で採点する。抜き取りは `python tools/review_record.py sample --seed <種> <設計書のディレクトリ>` が引く**却下の行 3 件**（3 件未満なら全件）で、種をレポートに書く
   - これまでの手順は「採用・却下からそれぞれ 5 件」でしたが、道具が引くのは却下の行 3 件で、パイロットの 4 回とも食い違いました。この版から、手順を道具に合わせます。採用の行の理由の採点を記録する場所は、まだありません（#62 で決めます）。採用の行の理由は、段 3 の問い（`q-revocation-delivery`・`q-variant-comparison` など）と、下の 3. で読みます
2. 不合格の理由は、種別「理由の不備」の指摘にする
3. **根拠の引用先を 3 件読む**（`q-evidence-attribution`）。数値・製品の挙動に根拠を付けた行から 3 件を選び、引いた節・文書が、その数値・挙動を本当に述べているかを確かめる。別の種類のクライアント・別の製品の根拠を引いていないかも見る。1 件に数分かかるので、短い一覧の問いからここに移しました

追加前の 25 問（`claim_request_*.md`）は、回答があることを lint（`lint:L72`）が、回答の中身が書けていることを書き手の自己点検が受け持ちます。レビュアーが読むのは、段 3 の `pa-01`（そのクレームで受け手が何を決めるか）です。

<a id="step-5"></a>

## 5. 開いた問いで、一覧の外を辿る

1. 開いた問い（short_list.md の 4.）を、1 つずつ辿る。設計書の決まった欄を開くだけでは答えられないので、要求の文と運用の場面から自分で辿り、辿った範囲（見た欄・考えた場面）と、気づいたことを書く
2. 気づきを指摘にする。出どころは「テンプレート外」。図に無い入口や場面（旧経路・テストの経路など）は、段 3 の `q-outside-catalog` で挙げます（出どころは「カタログ外の質問」）
3. **0 件が続くことは良い兆しではありません**（問いの一覧に慣れて、外を見なくなった印のことがある。[metrics.md](metrics.md)）。0 件のときも、辿った範囲は書きます

<a id="step-6"></a>

## 6. 専門家に回す

[escalation.md](escalation.md) の基準の表を上から順に見て、当てはまる行を回します。当てはまらない基準も、「当てはまらない」と確かめたことをレポートに書きます。観点書の区分 D の問い（short_list.md の 5.）は、レビュアーが答えずに、この段で回します。

<a id="step-7"></a>

## 7. 記録して戻す

- 指摘を [report_template.md](report_template.md) に書く。場所は、設計書の節（項目 ID）・台帳の行の ID と列・25 問の番号・観点書の問い ID で書く
- 問いごとの回答（レポートの 8.）は、答えた問いだけを書く。答えなかった問いがあれば、基本情報の「問いの回答」に、出た問いの数・答えた数・答えなかった理由を書く
- **戻す**：見つけた漏れを、次のどれかに戻す。戻す PR か issue をレポートに書く
  - カタログ（`templates/catalog/`）：カタログ外の発行・利用の場面
  - 観点書・短い一覧（この文書群）：問いが無かった、問いはあったが出る条件に当たらなかった、問いの文が分からなかった
  - 対応表（`templates/trace/`）：スライドの規則が要件になっていなかった
  - lint・実行テスト：機械で拾えるのに拾えなかった。書き手の自己点検に置いた問いで、機械で決まるもの

<a id="step-8"></a>

## 8. 対応を確かめて閉じる

全指摘の判定と対応の状態がそろったら閉じます。閉じた後に見つかった欠陥は [escaped_defects.md](escaped_defects.md) に記録します。

<a id="single-reviewer"></a>

## 1 名で行う場合

レビュアーが 1 名しかいないときは、役割を切り替えて読みます。1 人で 6 つの役割を同時に持つと、書き手と同じ前提で読んでしまうためです。

1. **書いた人と別の人が行う**。書き手が自分の設計書をレビューするのは、この手順の外です（書き手は、提出前の自己点検を行います。段 0 の 2.）
2. **役割を 1 つずつ切り替える**。short_list.md の 2. の読む単位（行 → 経路 → 全体）ごとに、役割を決めて読む。行は受け手と発行者、経路は攻撃者と入口、全体は運用の立場で読む。段 5 の開いた問いは、攻撃者の立場から始める（前提を疑う読み方を作るため）。役割ごとの全問の索引は perspectives.md の 7. にある
3. **時間を分ける**。段 0〜3 と段 4〜6 を別の日に行う。1 日空けて、段 3 の No の指摘を読み直し、取り下げるものと重大度を変えるものを決める。LLM のセッションがレビュアーのときは、日を分ける代わりに、段 3 の No の指摘を別の新しいセッションに読み直させる（そのセッションには指摘と設計書だけを渡す）
4. **LLM を 2 人目の目として使ってよい**（下の「LLM で一次スクリーニングする」）。ただし LLM の指摘は、出どころ「LLM」として区別し、レビュアーが 1 件ずつ採否を決める
5. **専門家に回す基準を緩めない**。1 名のときほど、escalation.md に当たる行は回す
6. レポートの「レビュアーと役割」に「1 名（役割を切り替えた）」と書き、切り替えの順と日付を書く

根拠：templates/CONTRIBUTING.md の 3.、筆者の提案：1 名で行う場合の役割の切り替えの順（追跡 #5）

<a id="llm-screening"></a>

## LLM で一次スクリーニングする

LLM によるレビューの自動化は、この計画の範囲の外です（#11）。ここでは、人のレビューの前の一次スクリーニングとして使う手順だけを書きます。

1. 渡すもの：設計書のディレクトリ、観点書（全問）と対比表、判断の木。LLM には、区分にかかわらず全問を渡してかまいません（人と違い、量は負担になりません。区分 A・B の問いを LLM が見ることは、lint と自己点検の二重の確かめになります）。渡さないもの：書き手の結論・レビュアーの見立て・「正しいことを確かめて」のような答えを前提にした指示（追認になるのを防ぐ。`templates/CONTRIBUTING.md` の 3.）
2. 指示：「perspectives.md の各問いに、見る欄を開いて Yes／No を付け、No の問いを指摘として、場所（項目 ID・台帳の ID と列）とともに出す」
3. 記録：日付・モデルの名前・渡した資料（パスとコミット）・指示の全文・出力
4. 人の確認：LLM の指摘のすべてを、レビュアーが採用・却下・保留に分ける。却下にも理由を書く。採用した指摘の出どころは「LLM」のままにする（[metrics.md](metrics.md) で、LLM の指摘の採用率を測る）
5. LLM が「指摘なし」と出した問いも、短い一覧にある問いは、人のレビューで省かない
