# 理由の採点基準（rationale rubric）

台帳の採用・却下の理由（`claims.yaml` の `rationale`・`assumption`・`revisit_trigger`、目録の `rationale`、カタログの回答の `assumption`・`breaks_when`）を採点する基準です。レビューの段 4（[procedure.md](procedure.md)）で、抜き取った理由に使います。

- 理由が「書いてあるか」は lint が見ます（R1・R2 など）。ここでは、**理由が判断を支えているか**を見ます
- 各観点は「満たす／満たさない」（と、決めた場合だけ「該当なし」）で付けます。1 つでも「満たさない」があれば、その理由は不合格で、種別「理由の不備」の指摘にします。採点の単位と迷いやすい点の決まりは、下の「採点の範囲と決まり」にあります
- 下の例は、採点の練習のための架空の行です。**採点の例です。設計書に写さないでください**（`templates/00_core.md` の「理由の見本は載せない」と同じ理由）
- 観点の選び方は筆者の提案です（追跡 #5。採点の一致率を `research/reviews/rubric-agreement-2026-11-23.md` で測る）
- 作成方法：本資料は生成AI（Claude）を使って作成し、筆者が確認して公開しています。人による点検は未実施

| 観点 | 問い（満たすなら Yes） | よくある不合格 |
| --- | --- | --- |
| RR1 主張と判断の対応 | 理由が、その行の判断（採用・却下・寿命の値など）を直接に支えているか | 一般論だけ（「セキュリティのため」）。別の判断の理由 |
| RR2 前提と崩れる条件 | 判断が依存する前提と、前提が崩れたら見直す条件が書いてあるか | 前提が暗黙。「必要になったら見直す」だけ |
| RR3 代わりと代償 | 却下なら、却下した仕組みの代わりにどう問いに答えるか。採用なら、その代償（剥奪の遅れ・サイズ・依存）が書いてあるか | 却下したのに、問いに答える手段が残っていない |
| RR4 根拠の当てはまり | 引いた根拠（スライド・仕様の節・実測）が、その主張を述べているか | 別の節・別の製品・別の版を引いている |
| RR5 状況への当てはまり | この設計の状況（クライアントの種類・IdP・規制・経路）に当てはまる理由か | 公開クライアントの根拠を機密クライアントに使う。別の IdP の挙動を前提にする |
| RR6 固有性 | この行に固有の内容（受け手の名前・値・経路）があるか。ほかの行の理由の写しでないか | 複数の行で同じ文。クレーム名を差し替えただけ |
| RR7 内部の一貫性 | 理由の中・同じ行の列の間で、数値・名前・トークンが一致するか | 「300 秒の遅れを許す」と「最大 330 秒」が並ぶ |

<a id="rr1"></a>

## RR1 主張と判断の対応

- 合格の例：「却下。`department` は注文 API の認可に使わない（受け手 orders の `enforced_at` に無い）ので、注文 API 宛ての AT に載せない」
- 不合格の例：「却下。最小化の原則のため」（どの受け手がなぜ要らないかが無く、判断を支えていない）

<a id="rr2"></a>

## RR2 前提と崩れる条件

- 合格の例：「AT の寿命を 5 分にする。前提：剥奪は 5 分遅れてよい（人事の通知が 5 分ごと）。崩れる条件：即時の停止が要る操作を足すとき」
- 不合格の例：「AT の寿命を 5 分にする。必要があれば見直す」（何が起きたら見直すかが無い）

<a id="rr3"></a>

## RR3 代わりと代償

- 合格の例：「Back-Channel Logout を却下。代わりに BFF がセッションごとに 60 秒ごとにイントロスペクションで確かめ、IdP のログアウトから最悪 60 秒で止める」
- 不合格の例：「Back-Channel Logout を却下。実装が複雑なため」（ログアウトを届ける手段が無くなったことに答えていない）

<a id="rr4"></a>

## RR4 根拠の当てはまり

- 合格の例：「RT のローテーションを使わない。根拠：FAPI 2.0 Security Profile（Final）§5.3.2.1（機密クライアントと送信者制約の AT では、例外的な場合を除き、AS はローテーションを使わない）」
- 不合格の例：「`aud` の確認を外せない。根拠：Keycloak の軽量アクセストークンの節」（その節は宛先の確認を述べていない）

<a id="rr5"></a>

## RR5 状況への当てはまり

- 合格の例：「公開クライアント（SPA）なので、RT はローテーション＋再利用検知にする（RFC 9700 §4.14.2 は公開クライアントに求める）」
- 不合格の例：「機密クライアントの BFF でも、RFC 9700 が求めるので RT をローテーションする」（RFC 9700 のその要求は公開クライアントが対象）

<a id="rr6"></a>

## RR6 固有性

- 合格の例：「`tenant_id` は全受け手（orders・billing・reports）が行の絞り込みに使い、テナントの付け替えは無い（解約で ID を廃番にする）ので載せる」
- 不合格の例：3 つのクレームに同じ文「受け手が必要とするため載せる。変化は少ない」を使う

<a id="rr7"></a>

## RR7 内部の一貫性

- 合格の例：「AT の寿命は 300 秒、時刻のずれの許容は 30 秒。剥奪の反映は最大 330 秒まで遅れてよい（人事の通知が 5 分ごとのため）」
- 不合格の例：「300 秒の遅れを許す。…AT の寿命が 300 秒なので最大 330 秒で反映する」（許す遅れと最悪の遅れが食い違う）

<a id="scoring-rules"></a>

## 採点の範囲と決まり

PR #45 の採点の一致の測定で、2 人の採点者が同じところで迷った点を、次のとおり決めました（`research/reviews/rubric-agreement-2026-11-23.md` の 5.）。

- **採点の単位**：台帳の 1 行の `rationale`・`assumption`・`revisit_trigger`・`refs`・`evidence`（と、却下の行の `rejection_kind`・`alt`）をまとめて、1 つの理由として採点します。`rationale` だけを見て、ほかの列にあることを「無い」としません
- **3 つの値**：各観点は「満」「否」「該当なし」のどれか。「該当なし」は合否で「満」と同じに数えます。使えるのは下に書いた場合だけです
- **RR2**：前提（`assumption`）と、崩れる条件（`revisit_trigger`）の**両方**が要ります。どちらか一方だけなら「否」。例外：
  - 却下の種類が「禁止」（規則でいつも禁じる）の行は、禁じる規則の出どころ（スライド・仕様・組織の規則）があれば、崩れる条件は要りません（規則が変わるまで見直さないため）
  - 「既定どおり」の行も、前提（例：受け手が読まない）と崩れる条件（例：読む受け手が増えたら）の両方が要ります
- **RR3**：採用の行は、代償（依存・サイズ・遅延・剥奪の遅れ・実装の手間のどれか）を 1 つ以上書きます。代償を別の行や設計書の節に書いたなら、その参照で足ります。却下の行で「前提が成り立つので要らない」という理由は、その前提が `assumption` にあり、却下した仕組みが答えていた問いに、別の手段で答えるか、問いが要らないことが書いてあれば「満」です
- **RR4**：
  - 根拠（スライド・仕様・実測）を 1 つも引いていない行は「該当なし」。根拠が要る主張（数値・製品の挙動）なのに引いていなければ「否」です
  - 採点者は、引用元を開いて確かめます。開かずに採点したときは、記録の表にその旨を書きます（その場合は、引用の名前と主張が対応するかだけを見ています）
  - ほかの製品・事例との類推（「Okta の例と同じ誤り」）は説明で、根拠ではありません。主張を支える根拠が別にあれば「満」、類推しか無ければ「否」です
- **RR6**：ほかの行・回答への参照（「I29 の回答と同じ前提」）は写しではありません。参照先が実在し、この行で何が同じかが分かれば「満」です。同じ文をそのまま繰り返している、またはクレーム名を差し替えただけなら「否」です
- **RR7（足した観点）**：理由の中、または同じ行の列の間で、数値・名前・トークンが食い違わないか。例：「300 秒の遅れを許す」と「最大 330 秒で反映する」が同じ理由に並ぶなら「否」です（どちらが正しいかを書き手に確かめる）
