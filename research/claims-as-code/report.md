JWT クレームの設計書を YAML で正本として管理し、スライド 114 の「載せない情報」の 6 分類（認証の秘密、機微な属性、平文の個人情報を含む ID、変わりうる識別子、細かい権限の一覧、接続元の詳細）に当たる定義を CI で検出する仕組みは、今回の調査の範囲では見つからなかった。近いものは三つの方向に分かれている。第一は、クレーム単位のメタデータの標準である。SD-JWT VC の Type Metadata と OpenID4VCI が `path`・`mandatory`・`sd`・`display` までを定めている。第二は、アプリのソースコードにある `jwt.sign` の引数を見る SAST ルールで、Semgrep、Bearer、Datadog にある。第三は、宣言とポリシーを突き合わせる privacy-as-code（Fides）とデータ契約（ODCS）である。どれも「宣言されたクレーム台帳 × トークンが通る場所 × 識別子の安定性」を判定しない。だから、このリポジトリの claim-lint が取り組んでいるのは空白地帯にあたる。ただし、ゼロから作る必要はない。フィールド名は SD-JWT VC に、形の検証は JSON Schema 2020-12 に、名前の衝突は IANA の CSV に合わせられる。「何のデータか」の語彙は fideslang から、「宣言 × ポリシー → 違反を名指し」の構成は `fides evaluate` から、版の比較は oasdiff と buf から借りられる。新しく作るべきなのは、6 分類を判定するための台帳の列と規則である。中でも計画への影響が大きい点が二つある。一つ目に、いまの `pii_category`（個人情報保護法の区分）だけでは「認証の秘密」と「接続元の詳細」を表せない。二つ目に、要件 `p09-do-not-carry.R6`（接続元の詳細）には機械検査が一つも割り当てられていない。

## 標準が定めるのは path・mandatory・sd・display の 4 つまで

「クレーム版の OpenAPI」に最も近い標準は、SD-JWT VC の Type Metadata である。**【確認済】** 最新版は draft-ietf-oauth-sd-jwt-vc-27（2026-11-16）で、IESG の評価段階にある。クレーム単位のメタデータ（§5.6）は、`path`（必須）、`display`（`locale`・`label`・`description`、任意の `dir`）、`mandatory`（既定 false）、`sd`（`always`／`allowed`／`never`。既定 `allowed`）、`svg_id` の 5 つである。このうち `svg_id` は SVG のテンプレートで描画するための参照なので、台帳の列として数えるのは残りの 4 つである。仕様は Type Metadata の形式（§5.2）で「Consumers MUST ignore properties that are not understood」と定めるので、独自のプロパティを足しても互換性は壊れない。また、-04 で入れた JSON Schema を -12 で削除しており、現行の Type Metadata は型と形を持たない（[IETF Datatracker](https://datatracker.ietf.org/doc/draft-ietf-oauth-sd-jwt-vc/)）。OpenID4VCI 1.0（Final、2025-09-16）の claims description も、`path`・`mandatory`・`display` の 3 つにとどまる（[OpenID4VCI 1.0](https://openid.net/specs/openid-4-verifiable-credential-issuance-1_0.html)）。EUDI ARF は namespace を「属性の識別子・構文・意味」をエコシステム全体で一意に定める単位としている。ただし、rulebook は人が読む文書（Markdown・PDF）で、機械可読な版は見つからなかった（[ARF Annex 1（v3.0.0）](https://eudi.dev/3.0.0/annexes/annex-1/annex-1-definitions/)。調査ノートは 1.3.0 を引いていたが、その URL はいま 404。namespace の定義は現行の v3.0.0 でも同じ）。**【未検証】** rulebook に機械可読版がない、という点は否定の主張で、点検でも確かめていない。現行の ARF には rulebook の一覧を置いた別のリポジトリがあり、再調査が要る。

OAuth・OIDC 側のメタデータは、クレームをさらに薄くしか扱わない。**【確認済】** IANA の JSON Web Token Claims レジストリの列は、Claim Name、Claim Description、Change Controller、Reference の 4 つだけである。登録は約 160 件で、claims の表は CSV（`/assignments/jwt/claims.csv`）で取得できる（[IANA JWT registry](https://www.iana.org/assignments/jwt/jwt.xhtml)）。**【未検証】** OIDC Discovery の `claims_supported`、RFC 9068、RFC 9728 はクレームを名前でしか扱わない、という記述は記憶に基づき、原文を取得していない（点検でも取得していない）。**【未検証】** OpenAPI にも JWT クレームを記述する標準の仕組みはなく、`x-jwt-claims` のような共通の拡張も検索では見つからなかった（否定の主張なので、点検では確かめられない）。必須クレームの宣言は製品ごとの設定に分かれている。Azure APIM の `<required-claims>`（[Microsoft Learn](https://learn.microsoft.com/en-us/azure/api-management/validate-jwt-policy)）、Tetrate の `x-tsb-authorization`（[Tetrate](https://docs.tetrate.io/service-bridge/refs/tsb/application/v2/openapi_extensions)。2026-11-22 に確認。版つきの 1.5.x の URL は 404）、Envoy の `jwt_authn` がその例で、Envoy は任意のクレーム値の条件を持たない（[Envoy](https://www.envoyproxy.io/docs/envoy/latest/api-v3/extensions/filters/http/jwt_authn/v3/config.proto)）。型付きでクレームを受け止める仕組みとして最も強いのは、Amazon Verified Permissions と Cedar schema である。ID トークンのクレームは principal の属性に、アクセストークンのクレームは `context.token.<属性>` に入る（[AWS: Mapping OIDC tokens to schema](https://docs.aws.amazon.com/verifiedpermissions/latest/userguide/oidc-map-token-to-schema.html)）。

**【提案】** 以上から、台帳の列のうち標準に対応するものがあるのは、名前・必須性・選択的開示・表示ラベルの 4 種類だけである。意味しないこと（`not_meaning`）、データ源、寿命、サイズ、秘匿先、採否の理由に対応する標準のフィールドはない。そして、スライド 114 の判定に必要な「識別子が変わりうるか」「どこから見えるか」も標準にはない。台帳の 1 行を SD-JWT VC の claim metadata の上位集合として設計し、`path`・`mandatory`・`sd`・`display` を同じ名前と意味で持たせるのが、最も安い互換性の確保になる。標準が未知のプロパティの無視を MUST にしているので、上位集合にしても標準側は壊れない。

## 既存の検査は「コードの中」か「署名の欠陥」を見ている

JWT 専用のツールの大半は、署名と検証の実装の欠陥を狙う。**【確認済】** jwt_tool、ZAP の JWT add-on、Burp の JWT Scanner が見るのは、alg=none、アルゴリズムの混同、JWK の注入、期限の欠落である（[jwt_tool](https://raw.githubusercontent.com/ticarpi/jwt_tool/master/README.md)、[ZAP](https://www.zaproxy.org/blog/2020-09-03-zap-jwt-scanner/)、[PortSwigger](https://github.com/PortSwigger/jwt-scanner)）。Spectral の OWASP ルールセットの `owasp:api2:2023-jwt-best-practices` は、securityScheme の説明文が RFC 8725 に言及しているかを見るだけで、クレームの中身は見ない（[ruleset.ts](https://app.unpkg.com/@stoplight/spectral-owasp-ruleset@2.0.1/files/src/ruleset.ts)）。ペイロードの中身を見るのは、ソースコード上の発行箇所を対象にした SAST ルールである。Semgrep の `jwt-python-exposed-data` は、関数の引数をそのまま `jwt.encode` に渡す箇所を拾う監査ルールである（WARNING・confidence LOW。[Semgrep](https://semgrep.dev/r/python.jwt.security.audit.jwt-exposed-data.jwt-python-exposed-data)、[規則の YAML](https://github.com/semgrep/semgrep-rules/blob/develop/python/jwt/security/audit/jwt-exposed-data.yaml)）。Bearer の `javascript_lang_jwt`（CWE-312）は `jwt.sign({ user: { email } })` を危険、`jwt.sign({ user: user.uuid })` を安全とする（[Bearer](https://docs.bearer.com/reference/rules/javascript_lang_jwt)）。Datadog にも同じ趣旨の規則がある（[Datadog](https://docs.datadoghq.com/security/code_security/static_analysis/static_analysis_rules/javascript-node-security/jwt-sensitive-data/)）。IdP の設定の監査では、kcwarden が `ClientWithFullScopeAllowed`（全ロールがトークンに載る）を検出する。ただし、protocol mapper ごとに機微な属性を見る監査は、clients の監査のページには記載されていない（[kcwarden](https://iteratec.github.io/kcwarden/auditors/clients)。**【未検証】** ほかの監査のページは見ておらず、「ない」とは言い切れない）。

スライド 114 の分類に当てはめると、既存ツールの守備範囲が偏っていることがわかる。

| スライド 114 の分類 | 既存の検出手段（入力） | 台帳にそのまま使えるか |
|---|---|---|
| 1. 認証の秘密 | Semgrep `jwt-python-exposed-credentials`（コード。ERROR、audit。`"password"` というキーのリテラルだけを検出する。**【確認済】** semgrep-rules に残っている。[Semgrep](https://semgrep.dev/r/python.jwt.security.jwt-exposed-credentials.jwt-python-exposed-credentials)、[規則の YAML](https://github.com/semgrep/semgrep-rules/blob/develop/python/jwt/security/jwt-exposed-credentials.yaml)） | 使えない |
| 2. 機微な属性 | Bearer・Datadog（コード）、Presidio・Google DLP（値） | 語彙と値の検査だけ使える |
| 3. 平文の個人情報を含む ID | Bearer の email 検出（コード）が部分的に | 使えない |
| 4. 変わりうる識別子 | 検出するルールは見つからなかった（**【未検証】** 否定の主張）。Entra の文書が「`upn` は認可に使わない」「`email` と `upn` は変わりうる」と明言している（[Entra](https://learn.microsoft.com/en-us/entra/identity-platform/optional-claims-reference)） | 根拠と既知の一覧として使える |
| 5. 細かい権限の一覧 | kcwarden `ClientWithFullScopeAllowed`（Keycloak の設定。間接的） | 発想を借りられる |
| 6. 接続元の詳細 | 検出するルールは見つからなかった（**【未検証】** 否定の主張） | なし |

**【提案】** これらの SAST ルールの入力はアプリのソースコードなので、台帳には向けられない。それでも、IdP の外で自前に JWT を発行するコードがある組織では、claim-lint と並べて CI に入れる価値がある。台帳の宣言とコード上の発行の食い違い（ドリフト）を見つけるためである。シークレットスキャンも、別の層で役に立つ。**【確認済】** gitleaks の既定ルールには `jwt`（ヘッダーとペイロードがそれぞれ `ey` で始まる 17 文字以上、entropy 3 以上）と `jwt-base64` があるが、ペイロードを復号して中身を判定する仕組みはない（[gitleaks.toml](https://raw.githubusercontent.com/gitleaks/gitleaks/master/config/gitleaks.toml)）。そのため、このガイドのスライドや docs にある例示用の JWT のうち、完全な形のものは検出される。`eyJhbGciOi...` のように省略した例は当たらない。**【提案】** 完全な形の例を置くなら、許可リスト（allowlist）か、署名部を明らかなダミーにする規約が先に要る。

## 借りるべき型は「宣言 × 場所」の判定と「lint／diff の分離」

検出の仕組みとして最も近い先例は、JWT ではなく privacy-as-code にある。**【確認済】** Fides は、システムの YAML に書いたプライバシー宣言（data category × data use × data subject）を、ポリシー（ANY／ALL／NONE の規則）と照らし合わせて `fides evaluate` で評価する。違反した宣言と規則を名指しで出し、Git hook や CI に組み込める（[Fides CLI: evaluate](https://ethyca.com/docs/dev-docs/cli/check/cmd-evaluate)）。ただし、ethyca/fides の GitHub リポジトリは 2026 年に archived になっている（最後の push は 2026-08-06、最新のリリースは 2.86.2〔2026-06-01〕）。借りるのはツールではなく、構成の考え方だけである。fideslang の data category は階層ラベルで、スライド 114 にそのまま対応するキーがある。認証の秘密は `user.authorization.credentials`・`user.authorization.password`、機微な属性は `user.name.*`・`user.contact.address.*`・`user.demographic.date_of_birth`、メールは `user.contact.email`、接続元は `user.device.ip_address`・`user.device.device_id`・`user.location.*` である。API キー、社員番号、アカウント ID の専用キーはなく、既存の親の下に子カテゴリを足して拡張することが推奨されている（[fideslang data categories](https://ethyca.github.io/fideslang/taxonomy/data_categories/)）。**【確認済】** fideslang のライセンスは、ethyca/fideslang と IABTechLab/fideslang のどちらも CC BY 4.0 である（GitHub のライセンスの判定と README のバッジ。Python のパッケージを別のライセンスにする LICENSE ファイルはない）。CC0 の `templates/` に語彙を写すと表示の義務が生じるので、写さずに版を固定して参照する（「調査ノート間の食い違い」の表と「計画への反映」）。もう一つ、小さいが型が同じ先例がある。obs-types は、分類の enum と出力先の組み合わせで lint する。L002 は「PII を LABEL に置かない」、L003 は「SECRET を LOG・AUDIT 層に置かない」である（[obs-types](https://docs.rs/obs-types/0.1.0/src/obs_types/classification.rs.html)）。これは、計画中の L65（`confidential_from` × `visible_to`）と同じ「分類 × 出る場所」の型である。

**【確認済】** 一方で、Fides の evaluate が一部の列（data categories・use・subjects・qualifier）しか見ておらず、`dataset_references` は検査に入らない、という issue が 2021 年に報告された。この issue は同じ月に完了として閉じており、いまの制約ではない（[ethyca/fides#151](https://github.com/ethyca/fides/issues/151)。2021-10-08 に作成、2021-10-29 に completed で閉じた）。**【提案】** それでも、この経緯は台帳にとっての警告になる。「列はあるのに、どの規則にも使われない列」は形骸化する。`trace_check.py` と同じ発想で、スキーマの各列が少なくとも一つの規則か生成物に使われていることを検査する「列のカバレッジ」を入れるとよい。

構成の面では、OpenAPI とデータ契約の両方が、形の検査（lint）と版の比較（breaking／changelog）を別のコマンドに分けている。**【確認済】** oasdiff は 2 版を比べて破壊的変更を ERR と WARN に分け（`changelog` ではさらに INFO も出す）、`--fail-on ERR` で CI を止める（[oasdiff](https://github.com/tufin/oasdiff/blob/v1.10.16/BREAKING-CHANGES.md)）。buf breaking は、互換の基準を FILE ⊃ PACKAGE ⊃ WIRE_JSON ⊃ WIRE という入れ子のカテゴリから選ばせる（[buf](https://buf.build/docs/breaking/rules/)）。datacontract-cli は `lint`、`breaking`、`changelog` を分けている（[datacontract-cli](https://pypi.org/project/datacontract-cli/)）。逆の教訓もある。Azure は、手書きの OpenAPI から上位の DSL（TypeSpec）へ移った。自前の linter である azure-openapi-validator は、README で新しい lint 規則を受け付けないとしている。依存する AutoRest は 2026-07-01 に退役した（README の予告による。[Azure/azure-openapi-validator](https://github.com/Azure/azure-openapi-validator)）。**【提案】** claim-lint を自前で作るなら、規則をエンジンから切り離して宣言の表（`issuance_effects.yaml` 型）として持つのが、退役に備える保険になる。

## 調査ノート間の食い違いと、確かめるべきこと

三つの調査ノートは、いくつかの点で食い違っている。取り込んだ版ではどれも決着させずに確かめ先を書いていたが、fideslang の 2 行は点検で一次資料に当たって決着したので、結果を書いた。

調査ノートが未検証としていた事項のうち、次は点検で一次資料に当たって決着した。**【確認済】** スライド 114 の「FAL2 以上では、平文の個人情報を含む ID を禁止」は、NIST SP 800-63C-4 の原文どおりである。FAL2 の節に "At FAL2, federated identifiers SHALL NOT contain plaintext personal information, such as usernames, email addresses, employee numbers, etc." とあり、「Federated Identifiers」の節に "This restriction is a requirement at FAL2 and above" とある。FAL1 では SHOULD NOT である（[NIST SP 800-63C-4](https://pages.nist.gov/800-63-4/sp800-63c.html)）。**【確認済】** Entra の groups の超過の閾値は、JWT で 200、SAML で 150 である（ID トークンとアクセストークンの両方の文書。[Entra: access token claims](https://learn.microsoft.com/en-us/entra/identity-platform/access-token-claims-reference)）。**【確認済】** ツールのライセンスは、Bearer CLI が Elastic License 2.0（LICENSE ファイルの冒頭。GitHub の判定は NOASSERTION。[Bearer](https://github.com/Bearer/bearer)）、gitleaks が MIT、trufflehog が AGPL-3.0、Presidio が MIT（`microsoft/presidio` は [data-privacy-stack/presidio](https://github.com/data-privacy-stack/presidio) に移った）、kcwarden が Apache-2.0（[kcwarden](https://github.com/iteratec/kcwarden)）である。

点検でも確かめられなかった事項は次のとおりである。**【未検証】** conftest の `--combine` の現行の挙動、datacontract-cli が PII を検査するか、ISO 18013-5 の本文（有償の規格）は確かめていない。否定の主張（ARF の rulebook に機械可読版がない、OpenAPI に共通の `x-jwt-claims` がない、kcwarden に protocol mapper ごとの監査がない、スライド 114 の分類 4 と 6 を検出する既存の規則がない）は、探した範囲で見つからなかったという意味にとどまる。OIDC Discovery・RFC 9068・RFC 9728 の扱いも原文を取得していない。誤検知の見込みはすべて推論で、実データで測った値はない。なお、W3C VC JSON Schema の成熟度は、取り込みの際に仕様のページで Candidate Recommendation Draft（2025-02-04）と確かめた（点検者は確かめていない）。

## 計画への反映：二つの列を足し、R6 に検査を割り当てる

いまの計画では、スライド 114 の要件が次のように割り当てられている（`templates/trace/requirements.yaml`）。R1（秘密）は `lint:L51` と `pii_category`、R2（機微な属性）は `lint:L50`、R3（平文の ID）は `lint:L52`、R4（変わる識別子）は `lint:L3`。R5（権限の一覧）は `M_authz_pdp` とサイズの `lint:R8`、R6（接続元）は `review:perspectives#q-access-context-from-pep` だけである。**【提案】** 構造上の穴は三つある。第一に、`pii_category` は個人情報保護法の区分なので、パスワードや API キーのような「個人情報ではないが秘密」なものを表せない。そのため、L51 は何を入力に判定するかが決まっていない。第二に、L3 が見る「変わりうる値」を宣言する列がない。`volatility` は値の反映までに許す秒数で、識別子が付け替わるか（reassignable）とは別の軸である。第三に、R6 を機械で検査する手段が一つもない。以下はすべて本報告の提案で、リポジトリの規約（#13）に従い `origin: proposed`、根拠の種類は `author-proposal` として追跡する。規則の番号は仮で、既存の L1〜L67 と重ならないように L68 から付けた。

**#3（台帳）に足す列。** 一つ目は `data_category` で、「何のデータか」を表す。fideslang の data category を版を固定して使い（fideslang は CC BY 4.0 なので、カテゴリの一覧は `templates/` に写さず、固定した版を参照する）、足りないものは子カテゴリとして拡張する（`user.authorization.credentials.api_key`、`user.unique_id.employee_number`、`authorization.permissions` など。名前は仮）。`pii_category`（法の区分）はそのまま残し、二つの軸を並べる。両者の組み合わせの矛盾、たとえば `user.contact.email` なのに「該当なし」となっている行は、warn で知らせる。二つ目は `identifier_properties: {stable, reassignable, pairwise, id_scheme}` で、`id_scheme` は `opaque`・`pairwise`・`email`・`employee_number` などを取る。`usage` が identifier か authz のクレームでは必須にする。三つ目として、提案中の `allowed_values`（正規表現）と、SD-JWT VC と同名・同義の `path`・`mandatory`・`sd`・`display` を加える。後者の 4 つは、将来 VC に射影するときのための列である。最後に、エディタでの即時検証のため、各 YAML の先頭のコメントに `# yaml-language-server: $schema=./claims.schema.json` を置く。**【確認済】** yaml-language-server は、2026-06-26 のコミット 416ede2（"fix: ignore modeline schema comment after yaml content"）から、modeline を文書の先頭のコメント（最初の YAML の内容より前）からしか読まない（[yamlParser07.ts の `getDocumentHeaderComments`](https://github.com/redhat-developer/yaml-language-server/blob/main/src/languageservice/parser/yamlParser07.ts)、[コミット 416ede2](https://github.com/redhat-developer/yaml-language-server/commit/416ede2)）。取り込んだ版は「1 行目は `template_version` と決まっているので、2 行目に置く」としていたが、1 行目が YAML のキー `template_version: 0.1.0` なら、2 行目の modeline は無視される。そこで本 PR で `templates/CONTRIBUTING.md` を直し、YAML の `template_version` は 1 行目のコメント（`# template_version: 0.1.0`）とし、modeline はその後の先頭のコメントの中に置く、と決めた。既存の `templates/trace/*.yaml` と `tools/trace_check.py` の出力は、もとからこの形である。

**#6（lint）の規則の入力を決める。** L51 は、`data_category` が `user.authorization.credentials*` か `user.authorization.password` のクレームが、どのトークン種別に載っても error とする。L52 は、`sub` の `id_scheme` が `email` か `employee_number` なら error とする。SP 800-63C-4 は、FAL2 以上で平文の個人情報を含む federated identifier を SHALL NOT、FAL1 で SHOULD NOT としている（前節）。台帳に FAL の列を持つなら、FAL1 では warn に下げる、という条件を加えられる。L3 は、`identifier_properties.stable` が false か、`reassignable` が true のクレームを、identifier や authz に使ったら error とする。さらに、Entra の文書を根拠にした既知の一覧（`email`・`upn`・`preferred_username`・`unique_name`）は、宣言が stable でも warn にする。`phone_number` は Entra の文書には出てこないので、この一覧には入れない。入れるなら、OIDC Core の標準クレームで利用者が変えうる値、という別の根拠で書く。そのうえで、次の新しい規則を warn として入れる。semver の規約では error の規則の追加はメジャー版になるので、warn で誤検知の割合を測ってから昇格させる。

名前のヒューリスティックを単独で error にしないのは、Semgrep の監査ルールのように、すべての行が人による確認の対象になるのを避けるためである。誤検知の例として、`name` がテナント名を指す場合や、Entra の `ipaddr` のような IdP 標準のクレームがある。規則が出す違反の形式は、Fides にならって、規則 ID、対象のクレームとホップ、根拠の版、抑止の理由を名指しで出すものにする。

**#19（生成）で、生成するスキーマを二つに分ける。** いまの完了基準は、トークン種別ごとのペイロードの JSON Schema を `additionalProperties: true` で生成し、発行側の設定と照合することである。受け手にとって、これは「未知のクレームは無視」と一致するので正しい。しかし、実際に発行したトークンに台帳にないクレーム（`password` や `email` など）が紛れ込んでも、このスキーマは通してしまう。そこで、受け手用（`additionalProperties: true`）に加えて、発行側の適合性を見るスキーマ（`additionalProperties: false`、`sub` には `not: {format: email}`、`allowed_values` から作る `pattern`）を生成する。そのうえで、シナリオ A・B の Keycloak から CI でトークンを発行し、デコードしたペイロードを後者で検証する。この検証は、`lint:L61`（設定に台帳にないクレーム名がある）の静的な照合では見えない、フックやスクリプトによる追加を捉える最後の照合になる。OPA の `io.jwt.decode` は署名を検証しないので（[OPA Token builtins](https://openpolicyagent.org/docs/policy-reference/builtins/tokens)）、検証済みのトークンを入力にするか、テストの目的を内容の検査に限ると明記する。生成物には、IdP の Discovery 用の `claims_supported` の一覧も加えられる。この向きは台帳からメタデータを作るもので、逆向き（メタデータから台帳を作る）は情報が足りず成り立たない。

**claim-lint の外の CI** としては、三つを提案する。IANA の `claims.csv` を取り込む処理を L1a の入力にする。gitleaks を、例示用 JWT の許可リストと合わせて入れる。L10（版の比較）を #21 から MVP に繰り上げるかを検討する。最後の一つは、スライド 133 の「トークンの中身の変更は破壊的変更」を機械で守る唯一の手段である。buf 型のカテゴリ（受け手の検証が壊れる／意味が変わる／説明だけ）で出力させるのがよい。

## 結論

既存のツールは、クレームが「どう署名されたか」と「どのコードが詰めたか」は見ているが、「その情報がトークンに載るべきだったか」は見ていない。スライド 114 の判断は、データの種類・識別子の安定性・トークンが通る場所という三つの宣言の組み合わせでしか下せない。その三つを同じ行に持てるのは、設計の台帳だけである。そのため、claim-lint が再発明を疑われるのは規則のエンジンの部分であって、判定の対象そのものではない。語彙は fideslang から（写さずに版を固定して参照し）、形は JSON Schema から、比較は oasdiff と buf から借り、新しく作るのは列と規則に絞るのが、最も根拠に沿った分担である。

計画の上で最も効くのは、規則を足すことより、規則の入力になる列を先に決めることである。`pii_category` を一つの列で全部まかなおうとすると、秘密と端末 ID が抜け落ち、L51 と R6 は空回りする。#3 のスキーマを確定させる前に、`data_category` と `identifier_properties` を入れるかどうかを決め、fideslang（CC BY 4.0）のどの版を参照するかを固定するべきである。この二つは、後から足すと台帳の全行の書き直しになる。
