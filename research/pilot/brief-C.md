# 要求の概要：シナリオ C AI エージェントの委任（Lite で記入）

この文書は、パイロット（jwt-claims-guide #9）で設計書を書く人に渡す要求だけをまとめたものです。ケーススタディのどのクレームを採用したか・しなかったか、どう防いだか、実験の結果は載せていません（末尾の「除外したもの」）。

- 出典の表記：`CS` は https://github.com/Takenori-Kusaka/jwt-claims-casestudy のコミット `080b8da`。`Lx-y` はそのファイルの行

## 1. システムの概要

利用者が AI エージェントに仕事を任せ、エージェントが MCP 風のツールサーバーを通じて、上流の請求書の API を呼びます。組織は 1 つ（社内）です。

- 出典：CS `cs/scen_c.py` L2-5、CS `README.md` L43、guide `templates/casestudy-mapping.md` L44-50（§2 の表）

## 2. 登場するもの

### 利用者・行為者

| 名前 | 何か | してよい操作（組織の方針） |
| --- | --- | --- |
| u1・u2 | 利用者（請求書の持ち主） | 自分の請求書について |
| agent:expense | 経費のエージェント。利用者から仕事を任される | 読む・支払う・返金する |
| agent:viewer | 読み取り専用のエージェント | 読むだけ |
| console:admin | 管理コンソール | 読む・支払う・返金する |
| portal | 利用者が自分で使うクライアント | 読む・支払う・返金する |
| tool:invoice-mcp | 請求書の MCP ツールサーバー | 読む・支払う・返金する |

- 呼び出し元は、ワークロードの ID（mTLS など）で識別できる前提
- 出典：CS `cs/scen_c.py` L4-5、L18-19、L139-141

### サービス

- **請求書の API**（宛先 invoices）：請求書を読む・支払う・返金する。請求書には持ち主・金額・振込先がある（例：inv-1 は u1 の 120,000 円・振込先 B-019、inv-2 は u2 の 50,000 円・振込先 B-020）
- **MCP のツールサーバー**：エージェントから呼ばれ、上流の請求書の API を呼ぶ。MCP サーバーは複数ありうる（例：A と B）。そのうち 1 つが悪意を持つことを想定する
- **承認の記録**：人が支払いを承認した記録。承認の ID・持ち主・対象の請求書・金額・相手先を持つ（例：ap-311 は u1 が inv-1 を 120,000 円で B-019 に払う承認）
- 出典：CS `cs/scen_c.py` L16-17、L86-87、L139-141、L203-206

### トークンの発行

- 組織の内部のトークン発行サービスが発行する（時刻を進めて試すための模擬）。利用者からエージェントへの委任（同意）と、トークンの交換（RFC 8693 の型）ができる
- 実物の IdP の代わりとして Keycloak 26.8 の標準トークン交換も使える（ケーススタディでは別に測っている）
- 出典：CS `cs/scen_c.py` L4-5、L47-64、L233-234、guide `templates/casestudy-mapping.md` L45

## 3. 業務の要求

- エージェントは、利用者の代わりに、その利用者の請求書だけを扱う
- 支払いは、人の承認の記録どおり（対象の請求書・金額・相手先）にだけ行う
- エージェントへの仕事（タスク）には範囲がある。例のタスクは「読む・支払う」で、返金は含まない
- 利用者は委任を取り消せる。取り消した後は、エージェントが続けて使えてはいけない
- 委任は多段になりうる（エージェント → ツール → …）。2 段は正規の利用、5 段は拒否したい
- 行為者ごとにしてよい操作が違う（上の表）。今その操作をしている行為者の権限で判断する
- 出典：CS `cs/scen_c.py` L54-56、L117-136、L162-230

## 4. 正規の利用（受け付けなければならない）

| ID | 内容 |
| --- | --- |
| C1 | 利用者 u1 の代わりにエージェントが、ツール経由で u1 の請求書を読む |
| C8 | 承認どおり 120,000 円を B-019 に支払う |
| C11 | 2 段の委任の連鎖で読む |

- 出典：CS `cs/scen_c.py` L213、L222、L225

## 5. 脅威（防がなければならない）

| ID | 内容 |
| --- | --- |
| C2 | ツールが受け取ったトークンを、そのまま上流に渡して読む |
| C3 | u1 に委任されたエージェントが、ツールに u2 の請求書を読ませる |
| C4 | 過去に連鎖にいた行為者（管理コンソール）の権限で、読み取り専用のエージェントが支払う |
| C5 | 120,000 円の承認で、990,000 円を支払う |
| C6 | 承認の金額のまま、振込先を別の口座に変える |
| C7 | 存在しない承認 ID をリクエストの本文に書いて支払う |
| C9 | 利用者が委任を取り消した後（発行から 9 分後）に、エージェントが読む |
| C10 | 5 段の委任の連鎖で読む |
| C12 | エージェントが利用者自身のトークン（ポータルで得たもの）を借りて支払う |
| C13 | 複数の MCP サーバー向けに得た広い宛先のトークンを、悪意ある MCP サーバー B が A に再送する |
| C14 | 「読む・支払う」のタスクで、ツールが返金の範囲を求めて返金する |
| C15 | ツールが交換のときに利用者を u2 に差し替えて、u2 の請求書を読む |

- 出典：CS `cs/scen_c.py` L214-229
- 補足：現状の実装では、交換をしないときツールは自分の広い ID（すべての請求書を読める）で上流を読む（CS `cs/scen_c.py` L151-155）。また承認の ID は本文に書かれたものをそのまま信じている（同 L129-132）

## 6. 制約・前提

- 攻撃に使うトークンは、どれも正しい発行者が署名し、期限内で、多くは宛先も合っている（CS `cs/scen_c.py` の各ケースが正規の発行サービス `STS.mint` で作られている：L162-230）
- 汎用の攻撃（署名アルゴリズムの差し替え、鍵の注入、期限切れ、宛先違い、別の発行者など）はシナリオによらず防ぐ前提（CS `README.md` L40）
- 時刻は仮想の時計で進む（CS `cs/scen_c.py` L4、L15）

## 7. 書き手が決める必要がある、あいまいな点

1. **委任の深さの上限**：2 段は通し、5 段は止める、までが要求。3・4 段をどうするか、その根拠（標準があるか）は書き手が決める
2. **取り消しの反映の速さ**：C9 は「9 分後」の例だけ。何秒（何分）以内に止まればよいかは要求に無い
3. **トークンの寿命**：要求としての数値は無い（除外したものを参照）
4. **ツールが上流を呼ぶときのトークン**：受け取ったものを使うか、別のものを得るか。要求は C2・C13・C15 を防ぐことだけ
5. **承認の内容をどこで照合するか**：トークンか、承認の記録の都度の参照か。要求は C5〜C8 を満たすことだけ
6. **タスクの範囲の表し方**：「読む・支払う」をどの単位で表すかは要求に無い
7. **「今の行為者」の判定**：委任の連鎖のどれを、呼び出し元のワークロードの ID と照らすかは書き手が決める
8. **Keycloak の標準トークン交換を使うか**：発行サービスを実物の IdP に置き換えるかは要求に無い
9. **利用者の識別子とテナント**：組織は 1 つだが、テナントを表す値を持つかは要求に無い
