この文書は、パイロット（jwt-claims-guide #9）で設計書を書く人に渡す要求だけをまとめたものです。ケーススタディのどのクレームを採用したか・しなかったか、どう防いだか、実験の結果は載せていません（末尾の「除外したもの」）。

## 1. システムの概要

社内の業務システムです。社員は複数の IdP のどれかでログインし、入口（ゲートウェイ）を通って社内のサービスを呼びます。組織は 1 つ（社内）で、顧客ごとのテナントはありません。

- 出典：CS `cs/scen_b.py` L2-6、CS `README.md` L42（題材 B の説明）、guide `templates/casestudy-mapping.md` L44-50（§2 の表）

## 2. 登場するもの

### 利用者（主体）

- 社員。一般社員・管理者・経理部門・営業部門の社員・契約社員がいる。異動（部署の変更）とログアウトが起きる
- 例として、Keycloak の利用者 carol（営業、approver ロール）、dave（経理）がいる
- 出典：CS `cs/scen_b.py` L4-5、L205-221、L234-235、CS `kc/import/corp.json`（users の節）

### IdP（5 つ）

| IdP | 前提 | 利用者を表す値・ロールの来かた（IdP 側の事実） |
| --- | --- | --- |
| Keycloak 26.8（実物、レルム corp） | 社内の主な IdP | 利用者は `sub`。レルムロールは `realm_access.roles`。部署は利用者の属性として持つ |
| Entra ID（模擬） | マルチテナント型のアプリ登録で、`{tenantid}` を含む発行者の形 | 利用者は `oid`＋`tid`（`sub` はアプリごとの仮名）。グループは `groups`。グループが上限（模擬では 200）を超えると `groups` が消え、代わりに参照先（`_claim_names`・`_claim_sources`）が入る。`upn` もある |
| Okta（模擬、カスタム認可サーバー default） | 自社 API 向けのアクセストークン | `sub` はログイン名（メール形式）で、退職後に別の人へ再利用されうる。`uid` は不変。グループは `groups`。部署はインラインフックで足すが、フックは 3 秒で打ち切られることがある |
| Cognito（模擬） | 既定の構成 | アクセストークンに `aud` が無く、`client_id` がある。種類は `token_use`（access／id）。グループは `cognito:groups`。`custom:` の属性は利用者本人が書き換えられる。発行前のフックがグループを外すことがある |
| Auth0（模擬、RFC 9068 プロファイル） | Action で独自の値を足す | 利用者は `sub`。名前空間の無い予約名（例 `roles`）として足した値を黙って外す。社員番号を数値として出すことがある |

- 出典：CS `cs/jwtlib.py` L88-126（模擬の発行者とトークンの形）、CS `cs/scen_b.py` L223-249、L264-283（各 IdP の癖を前提にしたケース）、CS `README.md` L42

### クライアントと API

- クライアント：社員用のポータル（Keycloak のクライアント `portal`）。ほかの IdP では `client-app`
- API（サービス）：注文のサービス `orders`、請求書のサービス `invoices`。どちらも入口の後ろにある
- IdP ごとに、注文のサービスを表す宛先の値が違う（Keycloak は `orders`、Entra は `api://orders`、Okta は `api://default`、Auth0 は `https://api.example.com`、Cognito は宛先なし）
- 出典：CS `cs/scen_b.py` L65-66、L202-203、CS `kc/import/corp.json`（clients の節）、CS `cs/infra.py` L109-121

### 入口（ゲートウェイ）と現状

- サービスの前に入口がある。**現状の入口は Keycloak 向けに作られていて**、Keycloak のレルムロールを `X-User-Role` ヘッダーに写してサービスへ渡し、サービスはそのヘッダーを信じている
- サービスのフレームワークは、ヘッダー名を小文字にし、`_` を `-` に変え、同じ名前のヘッダーの値を `,` でつなぐ（CVE-2026-26308 の型）
- 入口を通らずにサービスへ直接届く経路がありうる
- 出典：CS `cs/scen_b.py` L6、L28-33、L123-126、L262-263

## 3. 業務の要求（操作ごとの許可）

| 操作 | 許可する人 | 備考 |
| --- | --- | --- |
| 注文を読む（read） | すべての社員 | 自分のデータを、正しい本人として読めること |
| 管理操作（admin） | 管理者のロール（admins） | |
| 経理台帳（ledger） | 経理部門（finance）の社員 | **重要な操作**。異動・ログアウトの後に古い情報で通ってはいけない |
| 社内文書（docs） | 営業部門（sales）または経理部門の社員 | 部署で絞り込む |
| 編集（edit） | 編集者のロール（editor） | |
| 給与明細（payslip） | 本人 | 社員番号で本人の明細を引く |

- 出典：CS `cs/scen_b.py` L4-5、L164-188

## 5. 脅威（防がなければならない）

| ID | 内容 |
| --- | --- |
| B2 | ログインで得た ID トークンを API に送る |
| B3 | 請求書のサービス宛てのトークンを注文のサービスに送る |
| B4 | クライアントが `X-User-Role: admins` を付けて送る |
| B5 | アンダースコア版の `X_User_Role: admins` を付けて送る（CVE-2025-64484 の型） |
| B6 | 小文字の `x-user-role` を足して重複させ、値を連結させる |
| B7 | 入口を通らずサービスに直接、正しいトークンと偽のヘッダーを送る |
| B8 | グループが 250 個あって `groups` が消えた一般社員が、管理操作を呼ぶ |
| B10 | 別の顧客テナントで発行された Entra のトークンで管理操作を呼ぶ |
| B11 | 経理から営業に異動した直後に、異動前に得たトークンで経理台帳を読む |
| B12 | ログアウト（セッションの失効）の後に、残ったトークンで経理台帳を読む |
| B13 | Okta でログイン名を再利用した新しい社員が、前任者のデータを読む |
| B15 | Okta のフックが打ち切られ、部署の情報なしで出たトークンで、契約社員が社内文書を読む |
| B17 | Cognito の ID トークン（`token_use=id`）を API に送る |
| B18 | 利用者本人が書き換えた Cognito の `custom:` の属性（例：ロール admins）で管理操作を呼ぶ |
| B19 | 発行前のフックがグループを外した Cognito のトークンで管理操作を呼ぶ |
| B20 | Auth0 が黙って外した値の代わりに、既定のロール（editor）が使われて編集できてしまう |
| B22 | 2^53 を超える数値の社員番号を JavaScript 流に読み、別の社員の給与明細を得る |
| B23 | 漏れたトークンを別の端末からそのまま再送する |

- 出典：CS `cs/scen_b.py` L253-285
- 補足：B20 の「既定のロール」と B15 の「部署の既定値」は、現状の実装が値の欠落時に既定値（ロール editor・部署 sales など）を使うことによる（CS `cs/scen_b.py` L89-94）

## 6. 制約・前提

- 汎用の攻撃（署名アルゴリズムの差し替え、鍵の注入、期限切れ、宛先違い、別の発行者など）はシナリオによらず防ぐ前提（CS `README.md` L40）
- 時刻は Keycloak 以外では仮想の時計で進む（試験の都合。CS `cs/scen_b.py` L62、CS `README.md` L3）
- 鍵・パスワード・クライアントシークレットは試験用（CS `README.md` L67）

## 7. 書き手が決める必要がある、あいまいな点

1. **内側のサービスがどのトークンを受けるか**：IdP のトークンをそのまま受けるか、入口で何かに置き換えるか。要求は「5 つの IdP が混在し、現状の入口は Keycloak 向け」までで、構成は決まっていない
2. **「重要な操作」の範囲**：出典で重要と明示されているのは経理台帳だけ。管理操作を含めるかは書き手が決める
3. **異動・ログアウトの反映の速さ**：B11・B12 は「直後」としか書いていない。何秒（何分）までの遅れを許すかは要求に無い
4. **トークンの寿命**：要求としての数値は無い（除外したものを参照）
5. **B23（盗まれたトークンの再送）**：防ぐ対象として挙がっているが、どこまでの費用をかけて防ぐかは要求に無い。防がない場合は見直し条件を書くこと
6. **値が欠けたときの扱い**：現状の実装は既定値を使う（B15・B20 の原因）。新しい設計でどう扱うかは書き手が決める
7. **社員番号の型**：IdP によっては数値で来る。どの型で受け渡すかは書き手が決める
8. **Entra のグループ超過時の扱い**：B8 は拒否、B9 は受け付ける必要がある。両立させる方法は要求に無い
9. **個人情報（氏名・メールなど）の扱い**：ポータルがログイン画面で表示に使うかどうかは出典に無い
