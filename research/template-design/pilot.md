**どちらに決めたか：31 件とも付け直しを採りました。** 理由は次の 3 つです。

- 付け直しは、4 回の 92 件に同じ決まり（区分の定義と優先順。`reattribution.yaml` の `rules`）を当て、当たる問い・行・規則の ID を 1 件ずつ書いています。レビュアーの申告には ID が無いものがあります

付け直しが引いた観点書の問いの ID は、61 個すべてが観点書にあります（この分析では 10 個を確かめ、独立点検が全件を確かめました）。問いの中身が指摘に当たるかは、1 件ずつは確かめていません。

レビューは、この 3 つの warn が言う論点を指摘にしていません。「残した warn に理由が書いていない」という形（B-R1 F08、C-R2 F23）と、同じ欄の別の論点（R2-13）で触れただけです。**出来上がった設計書では、lint だけが見つけた欠陥は 0 件でした。**

lint の働きは、記入の途中にあります。

- B：最初の lint は error 115。YAML の誤り・必須の列・名前の規則などを直して 0 にした
- C：空の骨組みで error 120、台帳とホップを書いた時点で error 10、カタログへの回答を書いて 0。途中で L7（必須クレームが台帳に無い）を直している

これらはレビュアーに届く前に直っています。ただし、**どの規則が何件出たかの内訳は記録していません**（`author-log.md` には件数だけがあります）。「lint が、レビューでは見つからない何を拾ったか」を数えるには、次に測るときに lint の出力を段ごとに保存する必要があります。

## 8. 時間

**ここにある時間は、すべて LLM の壁時計です。人の時間ではありません。**

| | シナリオ B（Full） | シナリオ C（Lite の欄） |
| --- | --- | --- |

これが何を意味するか：

- LLM は読みと判断を並行して進め、1000〜2000 の欄を 16〜27 分で埋めます。人が同じ欄を埋める時間は、ここからは分かりません。欄の数に 1 欄あたりの時間を掛ける見積もりも、根拠がありません
- **Lite と Full の差（同じ区間で 16 分と 27 分、1.7 倍）を、人の負担の差として読むことはできません。** 欄の数は 1.9 倍で、時間の比と近く見えますが、1 回ずつの記録で、題材も違います。LLM の時間が欄の数に比例するとも、しないとも言えません
- 関門 2 の「Full の記入が 2 日を超えた」は、この記録では**判定できません**
- 関門 1 の「Lite の記入が 4 時間以内」も、作成者の見積もり（4 時間を超える）のままで、実測はありません（[`gate1.md`](gate1.md) の 2. と 9.）

**時間を理由には変えません。** 人の時間が無いので、Lite の項目が多すぎるかどうかを結論できないためです。人の時間は #20 で測り、そのときに見直します。

## 11. 関門 2 の判定案

**これは案です。判定は作成者が行います。**

### 3 つの基準と、当てはめ

| 基準（#9） | 当てはめ | 根拠 | 確かさ |
| --- | --- | --- | --- |
| **続ける**：2 ケースとも記入でき、claim-lint とレビューが、どちらか一方だけでは見つからなかった指摘を出した | **レビューの側だけ当たる。lint の側は測れていない** | 記入：2 件とも error 0（0.）。ただし C は Lite の欄で、Full の profile では error 53。レビューだけ：56 の話題、うち Major を含むもの 26（1.・3.）。lint だけ：記入の途中の error（内訳の記録なし）と、残った warn 3 件（欠陥は 0） | レビューの側は件数は多いが、**指摘が正しいかも、重大度も、人は確かめていない**（10.）。lint の側は、出来上がった設計書で lint だけが見つけた欠陥が 0 件で、記入の途中の働きは中身を数えていない。基準は両方に「一方だけの指摘」を求めるので、**基準を満たしたとは言えない** |
| **絞る**：Full の記入が 2 日を超えた、または迷いが多い | **決められない** | 時間：LLM で 27 分。人の時間は無い（8.）。迷い：Full で 28 件、Lite の欄で 26 件。3 回以上出た欄が 6 つ（6.）。欠陥の報告が 17（7.）。関門 1 のシナリオ A は迷い 16 件だった | 「多い」の線が #9 に無い。迷いの 3 分の 1 ほどは、複数の IdP を書けないこと（#58）と、Lite／Full の線引き（#61）に集まっている。項目の多さよりも、**書けない・食い違う**ことから出ている |
| **方針を変える**：レビューへの上乗せが見られない | **当たらない（ただし直接には測れていない）** | 92 件のうち 60 件（65%）、Major 37 件のうち 21 件が観点書の問いに当たる。カタログ・テンプレートの欄・カタログ外の質問からも 11 件（2.）。2 回のレビューがどちらも、一覧の外の Major を見つけた（4.） | 対照（観点書なしのレビュー）が無い（10.）。「問いに当たる」は「問いがあったから見つかった」と同じではない。観点書は同じ題材で較正済みで、60 件のうち 11 件は較正で足した問いに当たる（10.）。#12（誤りを埋め込んだ設計書）で測る |

### 案

**「続ける」。ただし、#12 へ進む前に直すものがある。**

- 理由は「縮める根拠が無い」ことです。「続ける」の基準を満たしたから、ではありません（上の表）。2 つの題材で、ブラインドでも設計書を書き切れ、レビューは Blocker 0 件・Major 37 件の指摘を出しました（正しさは未確認）。構想を「台帳＋カタログ＋claim-lint」に縮める理由は、この記録からは出てきません。Major 37 件のうち、今の lint が出すのは 3 件（どれも Lite／Full の食い違いに関わるもの）で、指摘の一部でも正しければ、lint だけでは届かない欠けがあることになります
- 「絞る」に当たる材料（Full の項目が多すぎる）は、人の時間が無いので出せません。迷いの多くは項目の多さではなく、書けない・食い違うことから出ているので、項目を減らすより先に #58・#61・#60 を直すほうが効くと見ています（推測）
- レビューの側を絞ること（168 問を人が使える量にする）は、#56 がすでに扱っています。9. の材料は、#56 に「問いだけの短い一覧では足りない」ことを示しています

進め方の案：

1. **#12 の前に**：#58（複数の IdP と作り直し）、#61（P4 の Lite／Full）、#60（道具の出力の誤り）。この 3 つは、書き手が回避策を取った結果、機械の検査が走らなくなるか、レビューの Major になったものです
2. **#12 と並行して**：#59（誤検知の候補）、#62（手順と道具）、#63（テンプレート外の指摘を戻す）、#64（案内）、#56（振り分け）
3. **#21・#7（後回しの部分）**：#9 の「続ける」は「#21 の項目は需要に応じて着手する」としています。パイロットから、#21 を前倒しする理由は出ていません
4. **次に測るとき**：lint の出力を段ごとに保存する。本当に Lite に当たる題材を 1 つ入れる。観点書を使わないレビューを対照に置く
