## 3. 難しさの区分（規則）

誤りごとに、次の 2 つを `seeded_errors.yaml` に書き、表で区分を決めます。どちらも、設計書と教材を見れば誰が決めても同じになるように書いています。

- **手がかり**（`signpost`）。数えるのは、その誤りの正解の問い（`confused_questions`・`also_accepted`）だけです。別のことを問う問いが、たまたま同じ欄を見る欄に挙げていても数えません
  - `P1`：その設計書の 1 枚（`sheet.md`）に出る**優先 1 の問い**のうち、`見る欄` か手がかりの文が、誤りのある欄・節を名指すものがある
  - `P2`：P1 は無いが、1 枚に出る**優先 2 の問い**か**開いた問い**が名指す。または、その行に **lint の warn** が出ている
  - `なし`：1 枚に出る問いは名指さない。観点書の優先 3・区分 A／B／D の問い、対比表、判断の木にだけある（または、どこにも無い）
- **読む場所の数**（`span`）
  - `1`：誤りが 1 か所（1 つの行の 1 つの列、または 1 つの段落）を読めば分かる
  - `2+`：2 か所以上を突き合わせて初めて分かる（要求の数値と寿命の列、ホップと種別、本文と YAML）。または、あるべきものが無いこと（欠けていること）で初めて分かる

| 手がかり ＼ 読む場所 | 1 | 2+ |
| --- | --- | --- |
| P1 | easy | medium |
| P2 | medium | hard |
| なし | hard | hard |

## 7. 採点の規則

### 一致（指摘と、埋め込んだ誤り）

指摘 F が、埋め込んだ誤り E に一致するのは、次の 2 つを両方満たすときです。

- **(a) 場所**：F の場所が、E の `locations` のどれかを指す。ファイルと、行の ID（YAML）か節（design.md の見出し・アンカー）が合うこと。列の名前だけ・ファイルの名前だけでは足りない。シーケンス図・本文の場合は、その節を指していれば足りる
  - **生成の区間の読み替え（測定前の改訂 R3）**：design.md の生成の区間（`<!-- render:…:begin -->` から `end` まで。1.・4.・5.・8.・9.1 の表・9.2・10.・11.・M_privacy_minimization の 2.）の行を指す指摘は、その行の出どころの台帳の行（8. の矢印の表なら、その行のクレームの `C-…` の行とホップの `H…` の行。10. なら判断の行の ID、11. ならカタログのイベントの回答）を指したものとみなす
  - **locations は、同じ誤りの文が出るすべての場所**（測定前の改訂 R3）：seeded と対照の差分の行のうち、その誤りの言い回しを含む行の節・行を、機械で集めて足した（見出しは `heading` に書き、`calibration_check.py` の C4 が実在を確かめる）。誤りが 1 つの説明の節（3.・3.1・6.・9.2 など）に繰り返し出ていても、どこを指しても (a) を満たす
- **(b) 中身**：F の内容が、E の **`core`（核）の 1 文**を述べている（測定前の改訂 R3）。`wrong` の残りの部分（理由が弱いこと・付随する影響）は、述べていなくてよい。「確かめが要る」「不明」だけで、何が誤りかを言わないものは満たさない

#### 採点の例（PR #81 の独立点検が仮に作った 3 つの指摘）

| 指摘 | 当てる誤り | (a) | (b) | 得点 |
| --- | --- | --- | --- | --- |
| 「3.1 の重点『元の依頼元のエージェントで判断』は入れ子の act で認可している（q-actor）」 | A01 | 満たす（3.1 は A01 の `heading` にある） | 満たす（核：行為者の許可に入れ子の act を使っている） | 1（`q-actor` は `also_accepted`） |
| 「8. の矢印の表 H8 の approval_id：2 秒で省くのは失敗時に開く（q-dependency-outage）」 | A16 | 満たす（生成の区間の 8. の行は、出どころの `C-approval-id` と `H8` を指すとみなす。8. も `heading` にある） | 満たす（核：応答しないと確認を省いて通す） | 1（`q-dependency-outage` は `confused_questions`） |
| 「TOOL_AT の max_lifetime 1800 秒が STAFF_AT の 600 秒を超える（q-hop-lifetime）」 | A03 | 満たす（`TOOL_AT` の行） | 満たす（核は寿命が上流を超えること。例外の理由の弱さには触れなくてよい） | 1（`q-hop-lifetime` は `confused_questions`） |

### 得点

| 得点 | 条件 |
| --- | --- |
| 1 | (a)・(b) を満たし、F の「取り違えた問い」に、E の `confused_questions` か `also_accepted` の ID がある |
| 0.5（部分点） | (a)・(b) を満たすが、取り違えた問いが無いか、どれにも当たらない |
| 0 | (a) か (b) を満たさない |

- 厳密な再現率は得点 1 の数、緩い再現率は 0.5 以上の数を、埋め込んだ誤りの数で割る。得点の合計を割ったもの（部分点込み）も書く
- 1 つの誤りに複数の指摘が当たれば、いちばん高い得点を 1 回だけ数える。1 つの指摘は 1 つの誤りにだけ当てる。ただし、1 つの指摘が 2 つの場所と 2 つの誤りを別々に述べていれば、分けて当てる
- 指摘の一覧（1）のほか、問いごとの回答（2）の No の理由と、開いた問いの気づきも、(a)・(b) を満たせば指摘として数える
- 種別と重大度は得点に入れない。正解との一致の割合を別に書く

### どの誤りにも一致しない指摘の判定

| 判定 | 意味 |
| --- | --- |
| 真（基の設計の欠陥） | 双子の両方にある、本当の欠陥。対照では誤検出に数えない。基の設計の欠陥として記録し、再測定の組では直す |
| 真（埋め込みの副作用） | 埋め込みのせいで生じた、正解の一覧に無い矛盾（seeded のみ）。誤検出に数えない |
| 誤検出 | 設計書の記述が正しいのに、誤りとした |
| 判定できない | 仕様・製品の事実が確かめられない。誤検出にも真にも数えず、件数を別に書く |

- **書き手が理由を付けて見送った点への指摘**（測定前の改訂 R4。例：control-b の 3.1 の送信者制約の見送り、Entra での無効化が次の取り直しまで届かないこと）：
  - 指摘が、書かれた理由を確かめるよう求めるもの（「見送りの理由が要求と合うか確かめてほしい」「この遅れを要求が許すか確認」）なら、誤検出に数えない。「確認の依頼」として件数を別に書く
  - 指摘が欠陥だと言い切り（「〜なので誤り」「〜は不可」）、書かれた理由が要求と矛盾しないなら、誤検出
  - 書かれた理由が要求と矛盾するなら、真（基の設計の欠陥）
- 判定は、レビューにも採点にも関わらない別のセッションが行う。渡すものは、その指摘、その設計書、指摘が触れる仕様の節。seeded の指摘の判定では、正解の一覧も渡す（副作用かを決めるため）
- 採点は、互いに独立した 2 つのセッションが全件を行う。食い違った指摘は、3 つ目のセッションが決める。食い違いの割合を書く
- **正解の一覧は採点のために直さない**。採点の途中で正解の一覧の誤り（場所の書き間違いなど）が見つかったら、「正解の訂正」として記録し、訂正の前と後の両方の得点を書く

## 8. 記録と固定の順序

1. 資料一式を作る（`packet`）。資料一式のファイルの sha256 を記録する
2. 12 回のセッションを行う。各回の出力（レポート全文）を `research/template-design/calibration/results/<ラベル>-<回>.md` に保存し、すべての出力の sha256 と終了の時刻を `results/commitments.txt` に書く
3. **12 件の出力と `results/commitments.txt` だけを入れたコミット**を作る。採点・判定はこのコミットの後に始める（コミットの時刻が順序の証拠）
4. ラベルの割り当てを記録し、採点・判定を行う。結果を `results/scores.yaml` と `results.md` に書く
5. 各セッションの記録には、日付・モデルの名前・渡した資料一式の sha256・指示の全文（上の文から変えていないこと）を書く

## 10. この測定を信じてよい範囲

| 脅威 | 中身 | 影響 |
| --- | --- | --- |
| 同じ系統のモデル | 設計書・正解・目標を Claude で作り、レビュアーの多くも Claude | 同じ盲点を共有する。作り手が見落とす種類の誤りは、埋め込まれてもいない |
| 作り手が教材を知っている | 埋め込んだ誤りは、観点書・対比表の「典型的な誤用」を見ながら作った | 教材がよく問う型の誤りに偏る。教材の外の誤りの見つけやすさは測れない。そのため、経路 `none` の誤りを意図して入れた |
| 誤りの密度 | 1 つの設計書に 16〜19 件で、実際の設計書より多い | 見つけやすくなる（どこを見ても何かある）か、注意が分散する。どちらに出るかは分からない |
| 双子の対照 | 対照は seeded と同じ設計 | 誤検出は「この 2 つの設計での」誤検出。別の題材での誤検出は分からない。対照の本当の欠陥は 7. で真として除く |
| 対照が本当に正しいか | 対照は LLM が書き、人は確かめていない | 本当の欠陥があれば、真の指摘として数える（誤検出を低く見積もらないよう、判定は別のセッション） |
| 書き手の自己点検が無い | 資料一式に PR の自己点検（区分 B）が無い | 手順の段 0 の抜き取りを測っていない。区分 B の問いが受け持つ誤りは、経路 `none` に入る |
| 件数が少ない | 誤り 35 件、セッション 12 回 | 区分ごとの割合は 1 件で大きく動く。参考値 |
| 難しさは目立ちやすさを数えない（測定前の改訂 R6） | 難しさの区分（3.）は、1 枚の問いがその場所を指すか（手がかり）と、読む場所の数で決める。誤りの文が目立つか、生成の区間で何度も写されるかは数えていない。PR #81 の独立点検では、正解を読む前の 20 分で 19 件のうち 15 件に当たり、hard の A01・A13 も見つかった | hard・medium の再現率は、区分の名前から思うより高く出やすい。目標（5.）はそのまま置き、結果を読むときは「hard ＝ 手がかりが弱い」であって「見つけにくい」ではないと読む。目立ちやすさの区分は、2 組目で足すかを決める |
| 書き手が理由を付けた見送り | 対照（特に control-b）には、要求の近くに、理由を付けた見送りがある（7. の R4） | 誤検出の数は、見送りへの指摘をどう判定するかで動く。判定の決まりを 7. に書き、確認の依頼は別に数える |
| 測定の後に教材や lint が変わる | templates・claim_lint が変わると、C2（lint の件数）・C3（render --check）が落ちる | 測定の後は設計書を描き直さない。C2・C3 が落ちたら、測定に使った版（コミット）を記録に書き、`expected_lint.yaml` は測定の時の値のまま、検査の対象を測定の時のコミットに固定する PR を出す |
| 人がいない | 人は測っていない | 人の見つけやすさ・時間は分からない（#20） |
