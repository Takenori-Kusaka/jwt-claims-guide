# 追加前の 25 問：`https://minato-denki.example/claims/` の `case_id`

> **意図的に誤りを含む教材。設計に使わない**

- 対象：台帳の `C-case-id`（claims.yaml）
- 判定：共有クレームにする（25 問すべてに答えた）

| # | 問い（スライド 142・143） | 回答 | 出どころ |
| --- | --- | --- | --- |
| 1 | 受け手はこのクレームで何を決めるか | 決めない（usage は identifier、answers は q-txn）。どの案件の操作かを agent-sts の交換の監査ログで結ぶ。agent-sts は案件の担当者が sub と一致するかを確かめてから載せる | 台帳：`usage`・`answers`・`rationale` |
| 2 | 寿命中に値が変わっても困らないか | 困らない（volatility は never）。案件の ID は変わらない。担当者の割り当ての変更は、次の交換で agent-sts が拒否する | 台帳：`volatility`・`on_revoke` |
| 3 | 既存の標準クレームで表せないか | 表せない。Txn-Token の txn は 1 つの取引で、案件はツールの呼び出しを何回もまたぐ。Txn-Token も使わない（prior_art_search） | 台帳：`registered_ref`・`prior_art_search` |
| 4 | 自組織の名前空間か。予約名と衝突しないか | 自組織の名前空間 https://minato-denki.example/claims/ の下。IANA の登録名と衝突しない | 手書き |
| 5 | 「.」「/」入りの名前を全ての受け手のツールで参照できるか | 受け手（agent-sts）は組織の共通の検証部品で、名前を完全一致の文字列のキーとして読む（JSONPath の式に埋めない） | 手書き |
| 6 | トップレベルか、組織のオブジェクトの下か | トップレベルに、名前空間の接頭辞つきの名前で置く（flat_prefix） | 台帳：`namespace`・`shape` |
| 7 | 型は 1 つか。区切り文字列を避けたか | 文字列 1 つ（shape は single）。区切り文字列にしない | 台帳：`type`・`shape` |
| 8 | ID・金額は文字列で運ぶか | 文字列で運ぶ（CS- と 10 桁の数字） | 手書き |
| 9 | 無い・null・false・空配列の意味は | 無ければ拒否（on_missing は拒否）。null・空文字も拒否 | 台帳：`absent_semantics`・`on_missing` |
| 10 | 大文字小文字・空白・比較方法は | 正規表現 ^CS-[0-9]{10}$ に合わない値を拒否し、完全一致で比べる | 手書き |
| 11 | 誰が値を書けるか。自己申告と分けたか | agent-sts だけが書く。エージェントが要求に書いた案件の ID は、案件の管理で担当者の割り当てを確かめてから載せる（申告のまま載せない） | 台帳：`authoritative_writer`・`provenance` |
| 12 | 名前と不変の ID を出し、ID で照合させるか | 案件の ID そのものが不変の ID。名前（件名）は載せない | 手書き |
| 13 | 上限は。超えたら失敗か、欠落か | 13 バイトで固定（上限で固定） | 台帳：`max_bytes`・`max_items`・`overflow_strategy` |
| 14 | 全リクエストに載せる価値があるか。宛先ごとに絞れるか | agent-sts だけが読む。DELEG_AT だけに載せ、TOOL_AT・STAFF_AT には載せない | 手書き |
| 15 | 付与するのは単一の発行者だけか | agent-sts だけ（issuers）。ツールは agent-sts の iss のトークンだけを受ける | 台帳：`issuers`・`enforced_at` |
| 16 | 検証を共通ライブラリで提供するか | 提供する。組織の共通の検証部品が、形式の検査と必須の検査を行う（design.md の付録 D の M_token_validation の 11.） | 手書き |
| 17 | ヘッダーに移すとき、同名ヘッダーの偽装（大文字小文字・アンダースコアの変種・重複）を除去するか | ヘッダーに移さない。ツールはトークンから直接読む | 手書き |
| 18 | 未検証の値を流すモードは無いか | 無い。本番の agent-sts は案件の管理を引かずに載せる設定を持たない | 手書き |
| 19 | 知らない受け手が無視しても安全か | 安全。判断に使わない識別子で、無視しても権限は広がらない | 手書き |
| 20 | ログに残すか。値かハッシュか。個人情報か | 値のまま記録する。個人情報ではない（案件の番号で、顧客を直接指さない） | 台帳：`log_policy`・`pii_category` |
| 21 | 委任なら act・承認 ID との関係は | act（誰が代理したか）と別の問い（どの案件か）に答える。承認の記録にも case_id を持たせる | 手書き |
| 22 | 台帳に登録し、受け手を把握したか | 登録した。受け手は agent-sts だけ | 台帳：`consumers` |
| 23 | 形式を変えるときの移行計画はあるか | 形式を変えるときは新しい名前の行を足し、受け手が新旧の両方を受けるようになってから agent-sts が新しい名前で出す（design.md の 9.3） | 手書き |
| 24 | 改名・廃止の互換期間と並行発行は | DELEG_AT の受け入れの上限（330 秒）より長く、少なくとも 1 回の配備の周期（2 週間）は新旧を並行して出す | 手書き |
| 25 | 発行前の確認手段と、受け手の条件のテストは | agent-sts の結合試験で、他人の案件の ID を要求したときに拒否されること、case_id の無い DELEG_AT を拒否することを確かめる | 手書き |
