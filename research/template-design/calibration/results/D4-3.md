## 手順 4：開いた問い 3 つ

**op-proof-holder**
- 辿った範囲は、各ツールの cnf 照合、H2〜H11 の mTLS、鍵の更新（M_sender_constraint の 4.）です。
- ツールは「mTLS の相手の証明書の拇印」と cnf を照合します。cnf の元は、agent-sts への交換要求を出した相手の証明書です。
- コンソールの経路も、cnf はコンソールの証明書で、同じ証明書でツールを呼びます。サブエージェントの経路も、subagent の証明書への束縛です。
- トークンを持つ者と鍵を持つ者は、どの箇所でも一致します。
- 気づいたこと
  - 束縛されるのは「実行基盤の証明書」で、案件単位ではありません。assist-agent は複数の担当者の案件を扱えるので、案件間の取り違えは cnf では防げません。
  - SVID の更新（1 時間）で、更新前の証明書に束縛したトークンは最大 300 秒使えなくなります。設計書は再交換で扱うと書いています。
  - X.509-SVID の失効は、登録を外してから最悪 1 時間残ります。AGENT_SVID が 300 秒で切れるので、交換は 330 秒で止まります。
  - DELEG_AT は束縛が無く、may_act と mTLS の突き合わせだけで守っています。H9 の発行側の検査（STAFF_AT の azp・案件の担当者）が hops の validates に書かれていません（F14）。

**op-source-change**
- 選んだ出来事は「退職」です。
- 経路は次のとおりです。
  1. 人事の台帳
  2. hr-sync（事象の同期は 120 秒以内、夜間の全件同期が補う）
  3. Keycloak の管理 API で、利用者の無効化・ロールの削除・セッションの削除
  4. PDP が読む（キャッシュ 30 秒）
  5. 返金は refund-tool が毎回 PDP に問い合わせる（150 秒）
  6. agent-sts の交換は introspection で 0 秒、照会・配送先の変更は TOOL_AT が最悪 330 秒
- 誰も時間を約束していない区間は 3 つあります。
  - 退職の事実が人事の台帳に入るまでの遅れ。REQ-07 の 5 分をどこから数えるかが不明です。
  - 事象の同期が止まったとき。夜間の同期まで遅れ、10 分の警報の後は責任者が止めるか判断するだけです（付録 A）。
  - 120 秒は書き手の目標で、未計測です（12.）。
- 図に無い書き込みの経路は 3 つあります。
  - Keycloak のレルム管理者・グループの管理者によるロール・属性の変更。C-groups の前提「クライアントのロールの割り当ては人事連携だけが行う」は、強制する仕組みが書かれていません。
  - approval-svc の承認者ロールの付与。出どころの記述がありません。
  - 案件の管理での割り当ての変更。範囲の外とされていますが、agent-sts の案件確認と C-case-id の on_revoke が依存しています。
- F8（hr-sync が止まった場合）と F9（書き込みの経路）にしました。

**op-one-time**
- 辿った対象は、承認の消費、approval_id、jti、AUTH_CODE、LOGOUT_TOKEN です。
- 並行する 2 件は、approval-svc の条件つき更新（未使用なら使用済み）で 1 回に絞られます。これは妥当です。
- 通信が切れた後の再送と、決済代行の障害では穴があります（F5）。
  - 「消費してから決済代行を呼ぶ」順序で、呼ぶ前に落ちると、使用済みのまま返金されず、正しい 1 回が失われます。
  - 決済代行の結果が不明（タイムアウト）のとき、失敗として「未使用に戻す」と、実際は成功していた場合に二重返金になります。
  - 決済代行側の冪等キーを approval_id にする、と書かれていません。
  - 3 万円以下の返金には 1 回限りの値がありません。TOOL_AT の jti も重複を確かめていません（replay_check: false）。
- AUTH_CODE は 60 秒＋PKCE＋PAR で、LOGOUT_TOKEN は jti を 120 秒覚えるので問題ありません。
