# designs/target（はこぶね）のレビュー結果

指摘は 19 件です（Blocker 0、Major 13、Minor 6）。重いのは次の 4 つです。
- **ロール剥奪の遅れ**：ロールを外してから効くまで、実際には最悪 960 秒かかります。許容の 900 秒を超えます（F04）。
- **ロールを付けられる人の数え漏れ**：荷主の Entra のグループ所有者なども、管理者のロールを付けられます（F03）。
- **退職の反映の遅れ**：荷主の Entra 側で利用者を止めても、最大 8 時間届きません（F06）。
- **上流の宣言を外して、機械の検査を止めている**：外したホップでは、上流より広い scope が出ています（F08）。

CI は error 0・warn 4 で、warn には全部理由があります。

## 手順 1：性質の表の確かめ
- 11 行は合っていました。
- 「操作ごとの承認がある」が「当たらない」になっているのは**誤り**です。break-glass の承認（2.2、H18・H19、`C-tctx` の approval_id）があります。authorization_details ではなく tctx で表しているので、読み方の条件に掛かりませんでした。その性質の問い `dc-05` を足して答えました（F01・F02）。

## 手順 2：6. の「要る」の問いと判断の木の比較
- q-sub、q-actor、q-req-wl、q-txn、q-user、q-agent、q-resource は、節と仕組みが合っていました（keep-sub-exchange、txn-tctx）。
- UC2 の q-peer は合っていません。運送会社との間は TLS だけで、直接の相手を Bearer の AT の client_id で代えています（peer-mtls、F09）。
- UC3 の q-authorized は、承認を tctx の approval_id と記録で表しています。RAR と比べた記録がありません（rar-vs-custom、F13）。

## 手順 4：開いた問い
**op-source-change**（辿った範囲：2.1、9.2、`C-org-roles`・`C-entra`・`C-scope`、SECURITY_EVENT_TOKEN の行、subject_states）
- (a) 異動で Auth0 のロールが外れる場合：荷主の管理者がはこぶねの画面で外す → どこかのサービスが Auth0 の管理 API で書く → 次の RT の取り直しで Action が org_roles を書き直す（最大 630 秒）→ TTS → TXN_TOKEN（最大 330 秒）。合計で最悪 960 秒です。
  - 画面から Auth0 の管理 API に書くサービスが、図にもホップにもありません。
  - キュー越しの作り直しで使う「今のロール」の元がありません。
- (b) 荷主の Entra で退職させる場合：はこぶねは、次の Entra を通るログインまで知りません。RT の取り直しでは Entra に問い合わせないので、最大 28800 秒続きます。
  - この区間の時間は誰も約束しておらず、要求にも数値がありません。止める手段は、荷主の管理者がはこぶねでメンバーを止める手作業だけです。

**op-one-time**（辿った範囲：AUTH_CODE、CLIENT_ASSERTION、RT、break-glass の承認、MSG_CTX、label-svc の重複の防止）
- AUTH_CODE・client assertion の jti・RT の再利用の検知は、Auth0 の挙動に頼っています。確かめていません（12.）。
- 承認は 1 回きりではなく、60 分の間は何度でも使えます。それが意図かどうか、書いてありません。
- MSG_CTX は 3600 秒の間、TTS に何度でも出して TXN_TOKEN に替えられます。
- 「同じ txn と荷物の ID のラベルを 2 回作らない」は、確かめてから作るまでが不可分になっていません。同じメッセージが 2 件並行して届くと、2 回通ります。記録先が止まったときに通すか止めるかも決まっていません。
- 期限切れの後の再配送では、正しい 1 回が失われます（荷主に再依頼してもらう扱い）。

**op-clock**（辿った範囲：M_token_validation の 6.、`C-auth-time`、承認の期限、付録 C、鍵のローテーション）
- TTS のトークンの exp − iat は、両方とも TTS の時計なので問題ありません。
- 次の比較は、2 つの時刻を別の時計が書いていますが、ずれの扱いが書いてありません。
  - auth_time（Auth0 の時計）と web-bff の現在の時刻
  - 承認の期限（書いた側の時計）と、TTS・billing-svc の時計
  - Webhook の created（はこぶねの時計）と運送会社の時計
- 鍵を外す時刻が台帳と設計書で食い違っています（F18）。
