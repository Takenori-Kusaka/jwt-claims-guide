## 手順 4：開いた問い 3 つの、辿った範囲と気づき

**op-proof-holder（送信者制約を選んだ設計に当たるため出た問い）**
- 辿った範囲は、cnf の行の enforced_at、TOOL_AT の holder・sender_constraint、M_sender_constraint の 4. です。
- 箇所ごとの「トークンを持つ者」と「鍵を持つ者」は次のとおりです。
  - 各ツールの cnf 照合では、トークンを持つ者は assist-agent、subagent、support-console のどれかで、cnf はその証明書です。一致します。
  - 予約の返金では、保存した TOOL_AT を refund-batch が使います。cnf の鍵は元の assist-agent などで、鍵の持ち主を確かめる箇所がありません（F-04）。
  - STAFF_AT と DELEG_AT は束縛なしのベアラートークンです。assist-agent のメモリに置き、STAFF_AT は交換が失敗したときの代わりの経路（H12・H13）では 2 つのツールに直接出ます。
- 気づいたこと：
  - SVID は 1 時間ごとに更新されます。更新の前の証明書に束縛した TOOL_AT が寿命の内に切れる、という記述は、SPIRE が寿命の半分で更新すると成り立ちません。使えなくなる時間帯が出るので Minor です（F-21）。

**op-source-change（権限の元データが変わる出来事）**
- 辿った出来事は、異動で refund-operator のロールが外れる、または退職、です。
- 辿った経路は、人事の台帳、hr-sync、Keycloak、PDP（キャッシュ 30 秒）、refund-tool です。
- 気づいたこと：
  - 返金の権限は、ロールではなくグループ「返金担当」で判断しています。グループはチームのリーダーが出し入れします。人事連携の経路の外です（F-07・F-08）。
  - refund_limit_jpy は担当者本人が編集できます。夜間の同期まで本人の値が残ります（F-09）。
  - 人事連携の 120 秒は未測定です。同期が止まれば、10 分で警報が出た後は責任者が手で決めます。誰も時間を約束していません（付録 A）。
  - support_tier を受け取るクレームも判断も、設計に見当たりません（F-20）。

**op-one-time（1 回だけ使える値）**
- 辿ったのは、approval_id の消費（付録 D の P4 の 5.）です。並行の 2 件、通信が切れた後の再送、記録先の障害の 3 場面で見ました。
  - 並行の 2 件：条件つきの更新（未使用なら使用済みにする）で 1 回です。ここは問題ありません。
  - 再送：approval_id を冪等キーにして、前の結果を返します。ここは問題ありません。
  - 返金の失敗後に「未使用に戻す」処理：決済代行側では成功して応答が失われると、再び使えます。二重返金になりえます。
  - approval-svc の 2 秒無応答：消費を省いて返金します。承認が何回でも通ります（F-02）。
- 気づいたこと：
  - TOOL_AT の jti は replay_check が false です。1 つの TOOL_AT で、承認が要らない 3 万円以下の返金を何件でも出せます。1 件ごとの上限は PDP に任せています。
