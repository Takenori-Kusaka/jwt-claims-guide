# 追加前の 25 問：`https://hakobune.example/claims/` の `org_roles`

> **意図的に誤りを含む教材。設計に使わない**
- 対象：台帳の `C-org-roles`（claims.yaml）
- 判定：共有クレームにする

| # | 問い（スライド 142・143） | 回答 | 出どころ |
| --- | --- | --- | --- |
| 1 | 受け手はこのクレームで何を決めるか | TTS が、Txn-Token の scope をどこまで出してよいかを決める（usage: authz）。内側のサービスは読まない | 台帳：`usage`・`answers`・`rationale` |
| 2 | 寿命中に値が変わっても困らないか | ロールを外してから AT に届くまで最大 630 秒（次の RT での取り直し）。許す時間は 900 秒（volatility）で、その中に収まる。すぐ止めたいときはメンバーを止め、TTS が次の発行から拒む | 台帳：`volatility`・`on_revoke` |
| 3 | 既存の標準クレームで表せないか | roles（RFC 7643 §4.1.2 の語彙）は名前の値を想定し、Auth0 の RBAC の permissions は Auth0 の API の設定の権限で、組織でのロールではない。Auth0 の AT には組織でのロールを出す既定のクレームが無い（Access Token Profiles の 2026-11-25 の確認）。組織の名前空間に置く | 台帳：`registered_ref`・`prior_art_search` |
| 4 | 自組織の名前空間か。予約名と衝突しないか | はこぶねの https://hakobune.example/claims/ の下。Auth0 の Actions の独自クレームは名前空間つきが前提で、Auth0 の予約するドメインを使わない | 手書き |
| 5 | 「.」「/」入りの名前を全ての受け手のツールで参照できるか | 受け手は TTS だけ。TTS の AT の読み込みの部品で URL の名前を読めることを試験で確かめる | 手書き |
| 6 | トップレベルか、組織のオブジェクトの下か | トップレベルの、名前空間を前に付けた名前（flat_prefix）。配列 | 台帳：`namespace`・`shape` |
| 7 | 型は 1 つか。区切り文字列を避けたか | 文字列の配列。空白・カンマで区切った 1 つの文字列にしない | 台帳：`type`・`shape` |
| 8 | ID・金額は文字列で運ぶか | ロールの名前を文字列で運ぶ | 手書き |
| 9 | 無い・null・false・空配列の意味は | 無い・空の配列はロールなし（on_missing: 既定値）。TTS は読み取りの scope も出さない（拒否の側に倒れる） | 台帳：`absent_semantics`・`on_missing` |
| 10 | 大文字小文字・空白・比較方法は | ロールの名前を小文字にして写し、TTS は語彙（admin・shipper・viewer）と完全一致で比べる | 手書き |
| 11 | 誰が値を書けるか。自己申告と分けたか | post-login の Action（はこぶねの基盤チームが持つ）だけが書く。値の元は組織のメンバーのロールで、荷主の管理者がはこぶねの画面で割り当て、はこぶねが Auth0 の管理の API で書く（provenance: 管理者が設定した値）。利用者が自分で変えられない | 台帳：`authoritative_writer`・`provenance` |
| 12 | 名前と不変の ID を出し、ID で照合させるか | ロールの名前を出す。名前は Auth0 と Entra で共通の語彙にする | 手書き |
| 13 | 上限は。超えたら失敗か、欠落か | 10 件・1 件 32 バイト。超えたら発行を失敗させる（ロールを落として発行しない） | 台帳：`max_bytes`・`max_items`・`overflow_strategy` |
| 14 | 全リクエストに載せる価値があるか。宛先ごとに絞れるか | 荷主の口の AT（AUTH0_AT）にだけ載せる。TTS が読み終えたら、Txn-Token には載せない（scope に替える） | 手書き |
| 15 | 付与するのは単一の発行者だけか | Auth0 だけ（issuers は Auth0 の 1 つ）。TTS は Auth0 の AT の中の値だけを読む | 台帳：`issuers`・`enforced_at` |
| 16 | 検証を共通ライブラリで提供するか | 読むのは TTS だけなので、TTS の中の 1 つの関数にまとめる | 手書き |
| 17 | ヘッダーに移すとき、同名ヘッダーの偽装（大文字小文字・アンダースコアの変種・重複）を除去するか | ヘッダーに移さない | 手書き |
| 18 | 未検証の値を流すモードは無いか | 無い。TTS は署名を検証した AT からだけ読む | 手書き |
| 19 | 知らない受け手が無視しても安全か | 受け手は TTS だけ。TTS が無視すれば scope が出ない（許可が増えない）ので安全 | 手書き |
| 20 | ログに残すか。値かハッシュか。個人情報か | ロールの名前を TTS の発行の記録に残す。個人情報ではない（誰のロールかは sub のハッシュと組でだけ分かる） | 台帳：`log_policy`・`pii_category` |
| 21 | 委任なら act・承認 ID との関係は | 委任には使わない。運用者の代理（TXN_OPS）では、ロールではなく break-glass の申請の範囲で scope を決める | 手書き |
| 22 | 台帳に登録し、受け手を把握したか | 登録した。受け手は tts だけ | 台帳：`consumers` |
| 23 | 形式を変えるときの移行計画はあるか | 形式を変えるときは、新しい名前で並べて出し、TTS が両方を読めるようにしてから古い名前をやめる（受け手が TTS だけなので短い期間で済む） | 手書き |
| 24 | 改名・廃止の互換期間と並行発行は | 並行して出す期間は、AT の寿命（600 秒）と RT の最大の寿命（28800 秒）を過ぎるまで | 手書き |
| 25 | 発行前の確認手段と、受け手の条件のテストは | ステージングの Auth0 で、組織のロールを付け外ししたメンバーでログインし、AT の org_roles を確かめる。TTS の試験で、語彙に無い名前・11 件以上・空の配列のそれぞれで scope が出ないことを確かめる | 手書き |
