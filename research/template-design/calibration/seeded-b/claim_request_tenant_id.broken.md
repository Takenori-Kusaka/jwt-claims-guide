# 追加前の 25 問：`https://hakobune.example/claims/` の `tenant_id`

> **意図的に誤りを含む教材。設計に使わない**
- 対象：台帳の `C-tenant-id`（claims.yaml）
- 判定：共有クレームにする

| # | 問い（スライド 142・143） | 回答 | 出どころ |
| --- | --- | --- | --- |
| 1 | 受け手はこのクレームで何を決めるか | 各サービスは、取り出す・書き込む行のテナントがこの値と同じかを決める。各サービスは、この値を DB の文脈（SET app.tenant_id）に写し、RLS が行を絞る（usage: authz、answers: q-resource） | 台帳：`usage`・`answers`・`rationale` |
| 2 | 寿命中に値が変わっても困らないか | 値は変わらない（volatility: never）。テナントの停止は値の変化ではなく状態で、Auth0 の組織からメンバーを外して止める | 台帳：`volatility`・`on_revoke` |
| 3 | 既存の標準クレームで表せないか | IANA の JWT Claims に、テナントを表す登録名は無い。Auth0 の org_id は Auth0 の組織の ID で、運送会社の口・運用の口・夜間の処理では無い。Txn-Token の草案もテナントの名前を定めない。組織の名前空間に置く | 台帳：`registered_ref`・`prior_art_search` |
| 4 | 自組織の名前空間か。予約名と衝突しないか | はこぶねが持つ https://hakobune.example/claims/ の下。Auth0 が予約する名前空間（auth0.com などのドメイン）とは重ならない | 手書き |
| 5 | 「.」「/」入りの名前を全ての受け手のツールで参照できるか | 受け手は共通の検証部品（hakobune-txn-verifier）の関数でだけ読み、名前を手で書かない。部品の試験で、URL の名前をそのまま読めることを確かめる。DB には各サービスが値だけを写すので、名前は DB に出ない | 手書き |
| 6 | トップレベルか、組織のオブジェクトの下か | トップレベルの、名前空間を前に付けた名前（flat_prefix）。単一の値 | 台帳：`namespace`・`shape` |
| 7 | 型は 1 つか。区切り文字列を避けたか | 文字列 1 つ。複数のテナントを 1 つのトークンに入れない | 台帳：`type`・`shape` |
| 8 | ID・金額は文字列で運ぶか | 文字列（t_ で始まる値）。数値にしない | 手書き |
| 9 | 無い・null・false・空配列の意味は | 無ければ拒否（on_missing: 拒否）。共通のライブラリは値の無い取引で DB に問い合わせず、RLS は設定が無いとき 0 行を返す | 台帳：`absent_semantics`・`on_missing` |
| 10 | 大文字小文字・空白・比較方法は | TTS が台帳の値を小文字のまま書く。受け手は完全一致で比べ、前後の空白を許さない | 手書き |
| 11 | 誰が値を書けるか。自己申告と分けたか | TTS だけが書く（台帳から引いた値。provenance: 発行者が確かめた値）。edge-gw が request_details で渡す値は申告として扱い、TTS が org_id・割り当て・申請の記録から引き直す | 台帳：`authoritative_writer`・`provenance` |
| 12 | 名前と不変の ID を出し、ID で照合させるか | 不変の ID を出す。表示名は別の行（tenant_name）で出す | 手書き |
| 13 | 上限は。超えたら失敗か、欠落か | 40 バイトで、値域が上限を超えない | 台帳：`max_bytes`・`max_items`・`overflow_strategy` |
| 14 | 全リクエストに載せる価値があるか。宛先ごとに絞れるか | 内側のすべてのサービスがデータの絞り込みに使うので、すべての Txn-Token に載せる。外の AT には載せない | 手書き |
| 15 | 付与するのは単一の発行者だけか | TTS だけ（issuers は TTS の 1 つ）。受け手は TTS の iss のトークンでだけ読む | 台帳：`issuers`・`enforced_at` |
| 16 | 検証を共通ライブラリで提供するか | する。hakobune-txn-verifier が読み、各サービスのコードが DB の文脈に写す | 手書き |
| 17 | ヘッダーに移すとき、同名ヘッダーの偽装（大文字小文字・アンダースコアの変種・重複）を除去するか | ふだんはヘッダーに移さない。TTS の障害の間だけ、edge-gw が検証した AT の値を X-Tenant-Id に書いて内側に送る（縮退の運転） | 手書き |
| 18 | 未検証の値を流すモードは無いか | TTS の障害の間の縮退の運転では、edge-gw が検証した AT の値をヘッダーで渡し、各サービスはそのヘッダーで処理する。ふだんは無い | 手書き |
| 19 | 知らない受け手が無視しても安全か | 安全ではない（無視すれば絞り込みが効かない）。だから受け手は共通の部品でしか Txn-Token を受けず、部品は値が無ければ拒む。新しいサービスは部品を入れるまでメッシュの許可に載せない | 手書き |
| 20 | ログに残すか。値かハッシュか。個人情報か | 値のまま監査ログに残す。個人情報ではない（法人のテナントの ID） | 台帳：`log_policy`・`pii_category` |
| 21 | 委任なら act・承認 ID との関係は | 運用者の代理（TXN_OPS）では、テナントは break-glass の申請の記録のテナント。billing-svc は approval_id の申請のテナントとこの値が同じかを確かめる | 手書き |
| 22 | 台帳に登録し、受け手を把握したか | 登録した。受け手は tts・shipment-svc・warehouse-svc・billing-svc・label-svc・report-svc・postgres | 台帳：`consumers` |
| 23 | 形式を変えるときの移行計画はあるか | 形式を変える予定は無い。変えるときは、設計書の 9.3 の手順（受け手が先、発行者が後）で、新しい名前を並べて出す | 手書き |
| 24 | 改名・廃止の互換期間と並行発行は | 改名するときは、新旧の名前を TXN_TOKEN の寿命（300 秒）の数倍以上の期間並べて出し、すべての受け手が新しい名前を読むと確かめてから古い名前をやめる | 手書き |
| 25 | 発行前の確認手段と、受け手の条件のテストは | TTS の試験で、台帳から引いた値と発行したトークンの値が同じかを確かめる。受け手ごとに、値が無い・別のテナント・形の違う値で拒むことの契約テストを持つ。RLS は設定が無いとき 0 行になることを DB の試験で確かめる | 手書き |
