# 追加前の 25 問：`https://hakobune.example/claims/` の `entra`

> **意図的に誤りを含む教材。設計に使わない**
- 対象：台帳の `C-entra`（claims.yaml）
- 判定：共有クレームにする

| # | 問い（スライド 142・143） | 回答 | 出どころ |
| --- | --- | --- | --- |
| 1 | 受け手はこのクレームで何を決めるか | TTS が、Entra を連携した利用者について、(1) メールのドメインからどの荷主か、(2) どのメンバーか（メール）、(3) どのロールか、を決める（usage: identifier） | 台帳：`usage`・`answers`・`rationale` |
| 2 | 寿命中に値が変わっても困らないか | tid・oid は変わらない。groups は荷主の Entra で変わっても、次の Entra を通るログインまで届かない（最大 28800 秒）。急ぐ剥奪はメンバーの停止で行い、TTS が次の発行から拒む | 台帳：`volatility`・`on_revoke` |
| 3 | 既存の標準クレームで表せないか | Entra の tid・oid・groups は Entra が決めた名前で、Auth0 の AT には載らない。Auth0 の名前のまま下流に渡せないので、組織の名前空間に写す。登録名の sub は Auth0 の user_id で、Entra の (tid, oid) ではない | 台帳：`registered_ref`・`prior_art_search` |
| 4 | 自組織の名前空間か。予約名と衝突しないか | はこぶねの https://hakobune.example/claims/ の下 | 手書き |
| 5 | 「.」「/」入りの名前を全ての受け手のツールで参照できるか | 受け手は TTS だけ。TTS の読み込みの部品の試験で確かめる | 手書き |
| 6 | トップレベルか、組織のオブジェクトの下か | トップレベルの名前空間つきの名前で、中身は tid・oid・groups のオブジェクト | 台帳：`namespace`・`shape` |
| 7 | 型は 1 つか。区切り文字列を避けたか | オブジェクト 1 つ。tid・oid・mail は文字列、groups は文字列の配列。tid と oid を連結した文字列にしない | 台帳：`type`・`shape` |
| 8 | ID・金額は文字列で運ぶか | GUID を文字列で運ぶ | 手書き |
| 9 | 無い・null・false・空配列の意味は | 無いのは Entra を連携していない利用者。Entra の連携を登録した荷主の組織で無ければ拒否する。groups が無い・空ならグループによるロールなし（組織のロールだけ） | 台帳：`absent_semantics`・`on_missing` |
| 10 | 大文字小文字・空白・比較方法は | Action が小文字の GUID に正規化して書き、TTS は完全一致で比べる | 手書き |
| 11 | 誰が値を書けるか。自己申告と分けたか | 書くのは post-login の Action。値の元は荷主の Entra（provenance: 発行者が確かめた値）。groups は荷主の Entra の管理者が決めるロール・グループの名前で、TTS は org_roles と同じ語彙で読む | 台帳：`authoritative_writer`・`provenance` |
| 12 | 名前と不変の ID を出し、ID で照合させるか | tid・oid と、メンバーを引くメール（mail）、ロールの名前（groups）を出す。UPN は出さない（台帳の却下の行） | 手書き |
| 13 | 上限は。超えたら失敗か、欠落か | 900 バイト（groups は 20 件まで）。超えたら発行を失敗させる。グループを黙って落とさない | 台帳：`max_bytes`・`max_items`・`overflow_strategy` |
| 14 | 全リクエストに載せる価値があるか。宛先ごとに絞れるか | 荷主の口の AT にだけ載り、TTS が読んだ後は Txn-Token に載せない | 手書き |
| 15 | 付与するのは単一の発行者だけか | Auth0 だけ。上流の Entra の iss は upstream_issuer に書いた | 台帳：`issuers`・`enforced_at` |
| 16 | 検証を共通ライブラリで提供するか | 読むのは TTS だけなので、TTS の中の 1 つの関数にまとめる | 手書き |
| 17 | ヘッダーに移すとき、同名ヘッダーの偽装（大文字小文字・アンダースコアの変種・重複）を除去するか | ヘッダーに移さない | 手書き |
| 18 | 未検証の値を流すモードは無いか | 無い | 手書き |
| 19 | 知らない受け手が無視しても安全か | 受け手は TTS だけ。TTS がメールのドメインの照合を飛ばすと別の荷主の利用者が入れるので、TTS の試験で照合の拒否を必ず確かめる | 手書き |
| 20 | ログに残すか。値かハッシュか。個人情報か | oid は個人情報（荷主の社員を表す）。監査ログにはハッシュで残す | 台帳：`log_policy`・`pii_category` |
| 21 | 委任なら act・承認 ID との関係は | 委任には使わない | 手書き |

| 24 | 改名・廃止の互換期間と並行発行は | 改名するときは、RT の最大の寿命（28800 秒）を過ぎるまで新旧を並べて出す | 手書き |
| 25 | 発行前の確認手段と、受け手の条件のテストは | ステージングで試験用の Entra のテナントを 2 つ連携し、別のテナントの利用者が拒まれること、グループの付け外しが次のログインで反映されることを確かめる | 手書き |
