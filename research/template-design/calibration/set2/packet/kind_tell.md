# 指摘の種別の見分け方

指摘の一覧の「種別」（理由の不備／前提の誤り／実装とのずれ／候補の漏れ／目的と仕組みの不一致）を決めるときに使います。

先に「**選んだ仕組みが答える問いは、要る問いと同じか**」を問います。違えば、ほかの種別にも当たるときでも「目的と仕組みの不一致」を第一の種別にします（併記するなら先に書く）。同じなら、下の表の右の列の種別から選びます。

| 迷う種別 | 目的と仕組みの不一致にする | その種別のままにする |
| --- | --- | --- |
| 前提の誤り | 事実（仕様・製品の挙動）は合っているが、仕組みが別の問いに答える（例：受け手が `jti` の重複の記録で、利用者の 1 日の利用回数を数える。`jti` の意味は正しく引けているが、答えているのは「このトークンが再び使われたか」で、「この利用者が何回使ったか」ではない） | 事実が誤っていて、事実を直せば判断も直る（例：「JWKS の `kid` は鍵を回しても変わらない」と書いてある） |
| 理由の不備 | 理由が弱いうえに、選んだ仕組みが要る問いに答えていない（例：画像の配信の URL に AT を付ける理由が「共有されても期限で切れるから」。AT は「誰がこの API を呼べるか」に答える仕組みで、「この 1 つのファイルを誰が見てよいか」に答えない） | 仕組みは問いに答えているが、理由が選択を支えていない（例：JWKS のキャッシュを 900 秒にした理由が書いていない） |
| 実装とのずれ | 2 か所の一方が、別の問いに答える仕組みを書いている（例：台帳は受け手が `scope` で操作を許すと書くが、ホップの確かめでは `client_id` が一覧にあるかだけを見る） | 2 か所が同じ仕組みについて食い違う（例：目録とホップで JWKS のキャッシュの秒数が違う） |
| 候補の漏れ | 仕組みを選んだが、それが別の問いに答える | 要る仕組み・値そのものが無い（例：画面に出す表示名を、どの発行者の値から取るかがどこにも決まっていない） |

**取り違えた問いの列は、種別が目的と仕組みの不一致なら空にしません**。判断の木の節の ID か、観点書・sheet.md の問い ID を書きます。迷ったら 2 つまで書いてかまいません。ほかの種別の指摘も、No と答えた問い・答えを決める問いの ID を「場所」に書きます（lint の warn からの指摘なら、その規則が答えを決める問い。short_list.md の 3.）。
