# 追加前の 25 問：`https://shirogane-sonpo.example/claims/` の `agency_code`

> **測定の対照に使う教材。設計に使わない**
- 対象：台帳の `C-agency-code`（claims.yaml）
- 判定：共有クレームにする

| # | 問い（スライド 142・143） | 回答 | 出どころ |
| --- | --- | --- | --- |
| 1 | 受け手はこのクレームで何を決めるか | claim-svc と document-svc が、代理店の担当者の請求・書類を、その代理店が扱う証券の請求だけに絞る（usage: authz）。TTS は AGENCY_AT の値が代理店の登録と同じかを確かめてから Txn-Token に写す | 台帳：`usage`・`answers`・`rationale` |
| 2 | 寿命中に値が変わっても困らないか | 代理店コードそのものは変えない（合併・分割では新しい代理店コードを割り当てる）。代理店の登録を止めてから効くまで最大 390 秒（TTS の登録のキャッシュ 60 秒と Txn-Token の 330 秒）。許す時間は 900 秒（REQ-02。volatility） | 台帳：`volatility`・`on_revoke` |
| 3 | 既存の標準クレームで表せないか | 代理店そのものの変わらない番号を表す登録名は無い（IANA JWT Claims を 2026-11-27 に確認）。client_id は代理店が証明書を替えてクライアントを登録し直すと変わり、azp は ID トークンの受け手の意味。組織の名前空間に置く | 台帳：`registered_ref`・`prior_art_search` |
| 4 | 自組織の名前空間か。予約名と衝突しないか | しろがねの https://shirogane-sonpo.example/claims/ の下。shirogane-as と TTS はしろがねが作る発行者で、ほかの製品の予約名と重ならない | 手書き |
| 5 | 「.」「/」入りの名前を全ての受け手のツールで参照できるか | 受け手は TTS・claim-svc・document-svc の 3 つで、どれも共通の検証部品（shirogane-txn-verifier）の、URL の名前を 1 つのキーとして読む関数で読む。部品の試験で確かめる | 手書き |
| 6 | トップレベルか、組織のオブジェクトの下か | トップレベルの、名前空間を前に付けた名前（flat_prefix）。単一の値 | 台帳：`namespace`・`shape` |
| 7 | 型は 1 つか。区切り文字列を避けたか | 文字列 1 つ。区切り文字列にしない（1 つの担当者は 1 つの代理店にだけ属する） | 台帳：`type`・`shape` |
| 8 | ID・金額は文字列で運ぶか | AG と数字 6 桁の文字列で運ぶ（先頭の 0 を落とさない） | 手書き |
| 9 | 無い・null・false・空配列の意味は | 無いときは代理店の請求ではない（契約者・社員・夜間の処理のトークン）。AGENCY_AT と、agst_ の sub の Txn-Token に無ければ、TTS・claim-svc・document-svc は拒否する。null・空の文字列は形の誤りとして拒否する | 台帳：`absent_semantics`・`on_missing` |
| 10 | 大文字小文字・空白・比較方法は | shirogane-as が代理店の登録の値をそのまま書き（大文字の AG）、受け手は完全一致で比べる。前後の空白は shirogane-as が落とす | 手書き |
| 11 | 誰が値を書けるか。自己申告と分けたか | shirogane-as が代理店の登録から書き（②）、TTS が登録を引き直して写す（④）。登録は代理店管理部だけが as-admin-api で書き、変更には別の社員の承認が要る（provenance: 管理者が設定した値）。代理店の IdP の assertion の値は使わない（代理店は自分の代理店コードを書けない） | 台帳：`authoritative_writer`・`provenance` |
| 12 | 名前と不変の ID を出し、ID で照合させるか | 代理店コード（不変の ID）だけを出す。代理店の名前は staff-console の画面にだけ出し、照合に使わない | 手書き |
| 13 | 上限は。超えたら失敗か、欠落か | 8 バイト（AG と 6 桁）。形に合わなければ発行を失敗させる | 台帳：`max_bytes`・`max_items`・`overflow_strategy` |
| 14 | 全リクエストに載せる価値があるか。宛先ごとに絞れるか | 代理店の口の AT（AGENCY_AT）と、そこから作る TXN_TOKEN にだけ載せる。契約者・社員の経路の Txn-Token には載せない。fraud-svc には届くが読まない（受け手の契約に入れていない） | 手書き |
| 15 | 付与するのは単一の発行者だけか | 段階ごとに 1 つ：AT は shirogane-as、Txn-Token は TTS（issuers は 2 つ）。受け手の claim-svc・document-svc は TTS の Txn-Token の値だけを読む | 台帳：`issuers`・`enforced_at` |
| 16 | 検証を共通ライブラリで提供するか | 共通の検証部品が形（^AG[0-9]{6}$）を確かめる。証券の取扱代理店との照合は、claim-svc の契約管理の仕組みの読み取りの関数 1 つにまとめる | 手書き |
| 17 | ヘッダーに移すとき、同名ヘッダーの偽装（大文字小文字・アンダースコアの変種・重複）を除去するか | ヘッダーに移さない。Txn-Token の中だけで運ぶ | 手書き |
| 18 | 未検証の値を流すモードは無いか | 無い。TTS は署名と cnf を確かめた AGENCY_AT からだけ読み、受け手は署名を確かめた Txn-Token からだけ読む | 手書き |
| 19 | 知らない受け手が無視しても安全か | 安全。無視した受け手は代理店の担当者の請求を絞れないが、代理店の担当者の Txn-Token を受けるのは claim-svc・document-svc（と、読まない fraud-svc）だけで、どちらも読む。新しい受け手を足すときは台帳の consumers に足してから受ける | 手書き |
| 20 | ログに残すか。値かハッシュか。個人情報か | 値のまま記録する。個人情報ではない（会社の番号） | 台帳：`log_policy`・`pii_category` |
| 21 | 委任なら act・承認 ID との関係は | 委任には使わない。代理店の担当者は、代理店の委託の契約に基づく代理店自身の権限で請求を出し、契約者からの委任（act）として扱わない（設計書の 2.1） | 手書き |
| 22 | 台帳に登録し、受け手を把握したか | 登録した。受け手は tts・claim-svc・document-svc | 台帳：`consumers` |
| 23 | 形式を変えるときの移行計画はあるか | 形式を変えるときは、新しい名前で並べて出し、3 つの受け手が両方を読めるようにしてから古い名前をやめる | 手書き |
| 24 | 改名・廃止の互換期間と並行発行は | 並行して出す期間は、AGENCY_AT の寿命（300 秒）と Txn-Token の寿命（300 秒）を過ぎるまで（受け手が先、発行者が後の順に変える） | 手書き |
| 25 | 発行前の確認手段と、受け手の条件のテストは | ステージングの shirogane-as に試験の代理店を 2 社登録し、AGENCY_AT の agency_code を確かめる。TTS の試験で、登録と違う値・無い値・止めた代理店で発行しないことを確かめ、claim-svc の試験で、ほかの代理店の証券の請求を 403 にすることを確かめる | 手書き |
