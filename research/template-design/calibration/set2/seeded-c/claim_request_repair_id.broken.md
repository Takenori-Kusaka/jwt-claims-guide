# 追加前の 25 問：`https://aoba-sumai.example/claims/` の `repair_id`

> **意図的に誤りを含む教材。設計に使わない**

- 対象：台帳の `C-repair-id`（claims.yaml）
- 判定：共有クレームにする（25 問すべてに答えた）

| # | 問い（スライド 142・143） | 回答 | 出どころ |
| --- | --- | --- | --- |
| 1 | 受け手はこのクレームで何を決めるか | agent-sts は修繕依頼の担当と委任の欄を確かめる鍵に、order-tool・contact-tool・lock-tool は要求の対象（下書き・連絡の相手・部屋）がこの修繕依頼のものかを照合する鍵に、payment-tool は監査ログの相関だけに（発注の修繕依頼と repair_id は照合しない）、approval-svc は承認の記録と照合する鍵に使う（usage は identifier、answers は q-txn） | 台帳：`usage`・`answers`・`enforced_at` |
| 2 | 寿命中に値が変わっても困らないか | ID は変わらない。担当の付け替え・委任の停止は値でなく修繕依頼の台帳の状態で、agent-sts が交換のたびに（担当は 3600 秒キャッシュする）、重要な操作のツールが aoba-pdp で呼び出しのたびに確かめる | 台帳：`volatility`・`on_revoke` |
| 3 | 既存の標準クレームで表せないか | 表せない。txn は 1 つの呼び出しの連鎖を指し、何日もかけて多くの呼び出しをまたぐ修繕依頼を指さない（prior_art_search） | 台帳：`prior_art_search` |
| 4 | 自組織の名前空間か。予約名と衝突しないか | 自組織の名前空間 https://aoba-sumai.example/claims/ の下 | 台帳：`namespace` |
| 5 | 「.」「/」入りの名前を全ての受け手のツールで参照できるか | 受け手は agent-sts・ツール 4 つ・approval-svc で、approval-svc のほかは組織の共通の検証部品で、approval-svc は承認の画面の Web の枠組みの検証で、完全一致のキーとして読む | 手書き |
| 6 | トップレベルか、組織のオブジェクトの下か | トップレベルに、名前空間の接頭辞つきの名前で置く（flat_prefix） | 台帳：`namespaces`・`shape` |
| 7 | 型は 1 つか。区切り文字列を避けたか | 文字列 1 つ（shape は single）。^RQ-[0-9]{8}$ | 台帳：`type`・`shape`・`allowed_values` |
| 8 | ID・金額は文字列で運ぶか | 文字列で運ぶ。金額は載せない | 台帳：`type` |
| 9 | 無い・null・false・空配列の意味は | 無ければ拒否する（委任・ツール・承認のトークンには必ず載る）。null・空文字は形式の誤りとして拒否 | 台帳：`on_missing` |
| 10 | 大文字小文字・空白・比較方法は | 修繕依頼の台帳が採番のときに大文字にそろえ、前後の空白を除く。受け手は完全一致で比べる。監査ログのハッシュの前にも同じ正規化をする | 台帳：`value_normalization` |
| 11 | 誰が値を書けるか。自己申告と分けたか | トークンに書くのは agent-sts だけ。委任とツールの交換では、修繕依頼の台帳で担当が sub で委任の欄が有効であることを確かめてから書き、エージェントの申告の修繕依頼は確かめに通らなければ載せない。2 段目の交換では REPAIR_DELEG_AT の値を写すだけ。APPROVAL_AT では、repair-console の要求の修繕依頼（画面で開いた修繕依頼）を、sub が担当か同じ課の上長であることを確かめてから書く（承認の記録の値は写さない）。トークンの外では、予約の記録の値を order-tool が予約のときに写す（作れるのは order-tool の DB アカウントだけ） | 台帳：`authoritative_writer`・`verification_method` |
| 12 | 名前と不変の ID を出し、ID で照合させるか | 物件の名前・部屋番号・入居者の名前は載せない。ID だけを出し、受け手は修繕依頼の台帳で引く | 手書き |
| 13 | 上限は。超えたら失敗か、欠落か | 11 バイトで固定（上限で固定。超えない値域） | 台帳：`max_bytes`・`overflow_strategy` |
| 14 | 全リクエストに載せる価値があるか。宛先ごとに絞れるか | 委任とツールと承認のトークンのすべてに要る（受け手は対象の照合か監査ログの相関に使う）。aoba-as の CONSOLE_AT・ID トークンには載せない | 台帳：`carried_in` |
| 15 | 付与するのは単一の発行者だけか | agent-sts だけ（issuers） | 台帳：`issuers` |
| 16 | 検証を共通ライブラリで提供するか | 形式の検査は共通の検証部品（approval-svc は承認の画面の Web の枠組み）。修繕依頼の台帳との照合は各受け手が行う | 手書き |
| 17 | ヘッダーに移すとき、同名ヘッダーの偽装（大文字小文字・アンダースコアの変種・重複）を除去するか | ヘッダーに移さない（入口を置かない） | 手書き |
| 18 | 未検証の値を流すモードは無いか | 無い。修繕依頼の台帳が応答しないときは、agent-sts は交換を拒否し、ツールは対象の照合ができないので要求を拒否する | 手書き |
| 19 | 知らない受け手が無視しても安全か | 安全ではないので、受け手を足すときは対象の照合を必須にしてから足す（今の受け手は payment-tool のほかは照合する） | 手書き |
| 20 | ログに残すか。値かハッシュか。個人情報か | 個人情報として扱う（修繕依頼の台帳と突き合わせると入居者が分かる）。監査ログには監査の共通部品の鍵つきのハッシュで残す（C-sub と同じ鍵） | 台帳：`log_policy`・`pii_category` |
| 21 | 委任なら act・承認 ID との関係は | 修繕依頼は委任の範囲（どの仕事を任せたか）で、act（誰が代わりにしているか）と別。承認 ID の記録は repair_id を持ち、受け手は両方が一致することを確かめる | 手書き |
| 22 | 台帳に登録し、受け手を把握したか | 登録した。トークンから読む受け手は agent-sts・order-tool・contact-tool・payment-tool・lock-tool・approval-svc。aoba-pdp は、予約の実行の問い合わせ（H13）で予約の記録の写しを受ける呼ばれる側で、トークンの検証部品を使わない（台帳の consumers と note） | 台帳：`consumers` |
| 23 | 形式を変えるときの移行計画はあるか | 修繕依頼の台帳の採番を変えるときは、受け手が新旧の両方の形式を受けるようになってから切り替える | 手書き |
| 24 | 改名・廃止の互換期間と並行発行は | ツールのトークンの受け入れの上限（330 秒）と配備の周期（2 週間）の長いほうより長く並行して出す | 手書き |
| 25 | 発行前の確認手段と、受け手の条件のテストは | agent-sts の結合試験で、担当でない修繕依頼・委任を止めた修繕依頼の交換が拒否されることを、ツールの結合試験で、別の修繕依頼の下書き・発注・部屋を指した要求が拒否されることを確かめる | 手書き |
