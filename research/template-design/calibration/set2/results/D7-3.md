## 4. 開いた問い 3 つ（辿った範囲と気づき）

### op-proof-holder

- **辿った範囲**
  - 持ち主の証明は mTLS の相手の証明書の拇印と `cnf` の x5t#S256 の照合で、tool と approval-svc が行います。
  - トークンを持つ者は repair-agent、visit-subagent、repair-console で、鍵を持つ者はそれぞれの wl-ca の証明書の持ち主です。
  - 証明書は 24 時間で、残り 8 時間で更新します。更新したら新しい証明書で交換し直したトークンだけを使います。トークンは 300 秒なので、束縛したトークンが古い証明書に残る時間は短いです。
- **気づき**
  - 1 段目と 2 段目の REPAIR_DELEG_AT は束縛されません。持ち主の確認は agent-sts の交換の口の mTLS と may_act の照合だけです。これは 3.1 の見送りで理由が書かれています。6. の UC2 の q-holder の行はこの点を書いていません（F-2）。
  - 鍵がエージェントの実行基盤の中にあるため、基盤が乗っ取られると鍵とトークンが一緒に漏れます。設計も「漏れるのはホスト乗っ取りのとき」と認めています。

### op-source-change

- **辿った出来事**：異動・退職によるロールの剥奪です。
- **辿った経路**：人事部の登録と、人事部のもう 1 人の承認による確定。その後 aoba-pdp が人事台帳を直接引き（60 秒キャッシュ）、agent-sts と各ツールの判断が変わります。hr-sync（5 分周期）は経路に入りません。
- **気づき**
  - 登録から確定までは人事部の手順書の 2 時間以内（月 1 回の報告）が約束で、REQ-08 の起点は確定です。
  - 2.1 の「退職の手続き中は退職日の前日まで入る」と、REQ-08 の「確定から 2 分」の関係が曖昧です（F-1）。
  - 修繕依頼の台帳の部屋・担当は、受付の画面と課長の画面だけが書き手で、DB 管理者の書き込みは使う前に止める規則があります。

### op-one-time

- **辿った範囲**：承認（発注 ID または承認自身に結ぶ条件つき更新）、解錠コード、予約。
- **並行の 2 件**：片方だけが成功します。
- **通信断のあとの再送**：同じ発注 ID・承認なら前の結果を返します。
- **approval-svc の障害**：拒否しますが、正しい 1 回は失われません。同じ ID で再試行できるからです。
- **解錠コードの送り直し**：n<3 の条件つき更新で最大 3 回です。コードは lock-svc が承認 ID ごとに 1 つだけ作るので、新しいコードは作りません。
- **確定できない発注**：order-tool が下書きの取り消しと承認の失効を同時に行い、新しい発注 ID で依頼し直します。
- **気づき**：2 回通る道は見つかりませんでした。
