## 手順 4：開いた問い 3 つ

**op-proof-holder**
- 辿った範囲：C-cnf の enforced_at、全トークン種別の holder と sender_constraint、M_sender_constraint の 4.、H2、C-client-id。
- ツールのトークンと APPROVAL_AT は、トークンの持ち主と鍵の持ち主が同じワークロードです。証明書の更新時の組の管理（aoba-agent-kit）も書いてあります。
- 気づき：CONSOLE_AT は束縛せず、agent-sts は「どのワークロードの mTLS でもよい」と宣言しています。
  - 交換で出る APPROVAL_AT の cnf は、要求した者の証明書になります。
  - approval-svc の enforced_at は、相手が repair-console の証明書かを見ていません。
  - 見ているのは、トークンの client_id が repair-console かどうかだけです（F-12）。

**op-source-change**
- 出来事：異動でロールが外れる。
- 辿った経路：人事システムの登録 → 人事部の 2 人目の承認で確定 → aoba-pdp（60 秒キャッシュ） → 重要な操作と agent-sts の scope の絞り込み。
- 約束がない区間は 3 つです。
  - 登録から確定まで。人事部の手順書は 2 時間以内と定めています。この設計は約束せず、月次の報告で確かめます（3.1）。
  - 人事の台帳の API が止まった間（F-05）。
  - 連絡ツールは、ロールが外れても止まりません（F-07）。また、修繕依頼の担当は課長が手作業で付け替えるまで残り、期限を約束する者がいません。

**op-one-time**
- 辿った範囲：承認の使用（条件つきの更新）、解錠コードの送り直し（回数の上限 3）、ログアウトトークンの jti、支払いの「依頼済み」。
- 承認の使用は、並行の 2 件・再送・approval-svc の障害のどれでも 1 回に収まり、正しい 1 回も失われません。
- 気づき：支払いの依頼だけが「確かめる → 送る → 依頼済みにする」の 3 段で、条件つきの更新になっていません（F-15）。
