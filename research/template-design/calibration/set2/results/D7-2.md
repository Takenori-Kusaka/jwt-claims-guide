## designs/target のレビュー結果

指摘は 2 件です。Major が 1 件（予約の発注の確定で、協力会社の取引が今も有効かを確かめていない）、Minor が 1 件（agent-sts の署名鍵の保管先の書き方が 2 か所で違う）です。Blocker はありません。優先 1 の 17 問への答えはすべて Yes で、No の答えから出た指摘はありません。F1 は q-long-running を調べる途中で、F2 は時間内に辿れなかった「さらに」の開いた問い op-key-custody に関わる読み物の中で見つけました。

### 段 1：性質の表の確かめ
sheet.md の 12 行を、図（2.）と要求（REQ-01〜13）に照らしました。全部合っています。
- **マルチテナント「当たらない」**：組織は 1 つで、テナントを表す値もテナントの切り替えもありません。妥当です。
- **DB の層まで運ぶ「当たらない」**：トークンで DB に接続する箇所がありません。ツールは自分の DB アカウントで接続します（2. のデータ層の行、9.1 の DB の接続の層）。妥当です。
- **補足（指摘にはしない）**：C-approval-ref は usage が identifier ですが、実際には操作を許すかどうかの判断に使っています（answers は q-authorized）。sheet の「組織独自の認可の行は無い」はこの書き方によるものです。この行は抜き取りに入っているので、答える問いは変わりません。

### 段 2：6. の「要る」問いと判断の木の比較
- **q-actor**（keep-sub-exchange）：受け手の enforced_at とホップの validates は、最も外側の act.sub だけで行為者を判断しています。入れ子の act は記録だけです。一致します。
- **q-peer**（peer-mtls）：mTLS の証明書（URI の SAN）で直接の相手を確かめています。一致します。
- **q-authorized**（rar-vs-custom）：scope で操作の種類、authorization_details と approval_ref で取引の承認と、分担が台帳に書いてあります。一致します。
- **q-txn**（txn-tctx）：Txn-Token を使わない理由（何日もかけて多くの呼び出しをまたぐ）が prior_art_search に書いてあります。一致します。
- **UC4 の予約の実行**：木の keep-sub-exchange（後で動く処理はワーカーが自分の ID で交換し直す）から外れていますが、3. と 3.1 に外した理由があります。ただし、確かめを agent-sts とは別に実装したため、確かめる項目が 1 つ抜けています（F1）。
- **UC2 の q-holder**（REPAIR_DELEG_AT を C-may-act で受ける）：may_act は「誰が交換してよいか」に答える仕組みです。それでも唯一の受け手の agent-sts で mTLS の相手と照合しているので、持ち主の確かめとして働きます。不一致にはしません。

### 段 4：開いた問い 3 つ
- **op-proof-holder**
  - 辿った範囲：ツール 4 つと approval-svc の cnf の照合、agent-sts での may_act と mTLS の照合、付録 D の M_sender_constraint の 4.（証明書の更新）。
  - 「トークンを持つ者」と「鍵を持つ者」は、どの箇所でも交換を求めたワークロードで同じです。証明書を更新しても、共通の部品が証明書とトークンを組で持ち、トークンは最悪 300 秒なので問題ありません。
  - 気づき：APPROVAL_AT の cnf が示すのは BFF（repair-console）で、承認した人そのものではありません。人との結びつきはセッションと CSRF のトークンに頼っています。中間の CA の鍵が漏れたときの穴は 3.1 で受け入れ済みです。
- **op-source-change**（出来事：異動で修繕課から外れる）
  - 辿った範囲：人事部の登録 → 2 人目の承認で確定 → aoba-pdp が人事の台帳を直接読む（キャッシュ 60 秒）→ 重要な操作は最悪 60 秒、下書き・連絡は最悪 390 秒で止まる。
  - hr-sync（5 分ごと）の遅れはこの経路に入りません。sub と社員番号の対応を書けるのは hr-sync だけです。
  - 誰も時間を約束していない区間は「登録から確定まで」だけで、3.1 に書いてあります（人事部の手順で 2 時間、月ごとの報告）。新しい穴はありません。
- **op-one-time**
  - 辿った範囲：承認、解錠コード、予約、ログアウトトークンの jti、認可コード。
  - 並行の 2 件は、条件つきの更新が片方だけ通します。通信が切れた後の再送は、同じ発注 ID・同じ承認には前の結果を返し、確定と発行は 1 回だけです。記録先が止まれば拒否します（止める側に倒す）。
  - 正しい 1 回の取りこぼし：使用済みの後に失敗しても同じ ID で再試行でき、確定できない発注は承認を失効させて新しい依頼に回します。2 回通る経路は見つかりませんでした。
