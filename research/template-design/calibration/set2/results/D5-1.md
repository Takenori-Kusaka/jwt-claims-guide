# designs/target のレビュー結果

指摘は 16 件です（Blocker 4、Major 10、Minor 2）。sheet.md の優先 1 の 17 問のうち、Yes は 6 問、No は 11 問でした。抜き取りの種は 12 で、抜き取った行は C-approval-ref・C-repair-id・C-authorization-details です。

## 段 1：性質の表の確かめ
sheet.md の 12 の性質の判定は、どれも図・要求・台帳と合っていました。
- 「当たらない」の 2 つは正しいです。マルチテナントは組織が 1 つです。DB の層は、order-tool・order-scheduler が自分の DB アカウントでつなぐので、トークンを運びません。
- 補足として、長時間・非同期の処理は ORDER_TOOL_AT のほかに CONTACT_TOOL_AT の long_running（返信を待つ WebSocket の購読、最大 2 日）にもあります。

## 段 2：判断の木との照合
6. で「要る」とした問いを、判断の木の節と比べました。
- q-actor（keep-sub-exchange）：受け手が許可に使うのは最も外側の act だけです（hops の validates・C-act の enforced_at）。
- q-peer（peer-mtls）：mTLS で確かめています。
- q-authorized（rar-vs-custom）：authorization_details を使っています。
- q-txn：Txn-Token の代わりに repair_id を使っています。TXN_TOKEN を却下した理由が書いてあります。
- UC4 で交換し直さない点：3. に既定から外した点として書いてあります。

不一致は指摘の F1・F2・F4・F5・F12・F13・F15 にまとめました。

## 段 4：開いた問い
- **op-proof-holder**
  - 辿った範囲：C-cnf、H5〜H8・H11・H12、M_sender_constraint の 1.・4.、4. の交換の条件。
  - 気づいたこと：ツールのトークンでは、トークンを持つ者と鍵を持つ者は同じワークロードです。APPROVAL_AT では、鍵を持つ者は「交換を求めた任意の wl-ca のワークロード」です。approval-svc は相手が repair-console かを確かめていません（F16）。証明書を更新した後の扱いは書いてあり、最悪 300 秒です。
- **op-source-change**
  - 辿った範囲：9.2 の「元のデータからの経路」、C-sub・C-staff-number、M_authz_pdp の 5.、REPAIR_DELEG_AT の revocation。出来事は「異動で担当を付け替える」と「人事の台帳での退職の確定」です。
  - 気づいたこと：誰も時間を約束していない区間が 3 つあります。
    - 担当の 3600 秒のキャッシュ（F9）
    - 人事の台帳の API が止まったとき、最大 24 時間古い結果を返すこと（F11）
    - agent-sts からの問い合わせだけ、ログイン名で引く経路（F13）
- **op-one-time**
  - 辿った範囲：P4 の 5.、M_token_validation の 6.、H7・H8。
  - 気づいたこと：承認の使用と解錠の送り直しは条件つきの更新で、並行の 2 件・再送・正しい 1 回を失わないことのどれにも答えています。支払いの依頼だけは「確かめてから送り、後で印を付ける」作りで、並行の 2 件が両方とも送れます（F7）。
