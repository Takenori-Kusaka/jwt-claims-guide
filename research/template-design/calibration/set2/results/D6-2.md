## レビュー結果：designs/target（しろがね損保、抜き取りの種 12）

**結論：** 指摘は 14 件です（Blocker 3・Major 7・Minor 4）。重い 3 件は次のとおりです。
- shirogane-as の管理の書き込み API が、網の中のどの部品からの書き込みも受けます。
- 保守の委託先の踏み台が、図にもカタログの回答にも載っていません。
- 代理店の請求の照会で、取扱代理店を照らしていません。

答えた範囲は、優先 1 の 16 問、足した dc-05、優先 2 の 9 問、開いた問い 3 つです。ファイルだけで判断しており、実物の挙動は確かめていません。

### 段 4：開いた問い（辿った範囲と気づいたこと）

**op-proof-holder**
- 辿った箇所：front-gw（H5）、TTS（H6）、shirogane-as のトークンの端点（H31）。cnf の行、AGENCY_AT の holder、M_sender_constraint の 2. と 4. を読みました。
- 箇所ごとに「トークンを持つ者」と「鍵を持つ者」を並べると、どれも代理店のサーバーで一致しています。
- TTS は、front-gw だけが書ける拇印のヘッダーと照らします。証明書を更新すると、前の証明書に束縛した AT は最大 300 秒で使えなくなります。
- PH_AT・EMPLOYEE_AT は束縛しません。その代わり、口に接続できるのが BFF の SVID だけなので、トークンを持つ者と接続の相手が一致します。
- 気づいたこと：CRL を取り直せない間は、失効した証明書を期限なしに受け続けます（F13）。

**op-source-change**
- 選んだ出来事：査定担当者の退職・異動。
- 辿った経路：人事の仕組みでの入力と承認 → 社員の台帳 → TTS（キャッシュ 60 秒）→ TXN_STAFF（330 秒）で、最悪 390 秒です。SSO のセッションは 60 秒ごとの確認で消えます。PAY_MSG_CTX は作り直しのときに役割を確かめ直します。受け付け済みの指示は有効のまま残ります（9.1 の明記）。
- 誰も時間を約束していない区間が 2 つあります。どちらも 3.1 で見送りとして書かれています。
  - 発効から台帳の更新まで。
  - 課の異動に伴う割り当ての付け替え（業務の手続きに任せる）。
- 図に無い書き込みの経路が 2 つありました。
  - shirogane-as の管理の API は網の中の誰でも書けます（F1）。
  - DB の管理者が直接直すと、元の sub のまま上書きされます（F9）。

**op-one-time**
- 「確かめる」と「使用済みにする」を 1 回の書き込み（または同じ取引）で行い、記録先が応えなければ拒む形になっているのは次のとおりです。
  - 認可コード（未使用から使用済みへの条件つきの書き込み）
  - 代理店の assertion の jti（一意の制約つきの書き込み）
  - nonce（取り出して消す）
  - セキュリティキーの登録の番号（鍵の登録と同じ取引）
  - 支払いの指示（(claim_id, assessment_ref) の一意の制約）
  - 実行と取り消し（支払いの行のロック）
- payment-worker が処理済みにするのは受け付けの後なので、再送しても正しい 1 件は失われません。
- 気づいたことは 2 つです。
  - 承認の記録が請求ごとで、後の支払いにも使い回されます。1 回だけの値になっていません（F4）。
  - assertion の jti を覚える時間の書き方では、30 秒の再送の窓が残る読み方ができます（F14）。
