## 開いた問い 3 つ（辿った範囲と気づき）

- **op-proof-holder**
  - 辿った範囲：C-cnf と、token_types の holder・sender_constraint、付録 D の M_sender_constraint の 4.。
  - 気づき：ツールのトークンでも APPROVAL_AT でも、トークンを持つ者と鍵を持つ者は交換を求めた同じワークロードで、そろっている。証明書を更新した後は、証明書とトークンを組で管理する。ただし CONSOLE_AT の交換はどのワークロードからでも受けるので、APPROVAL_AT が repair-console 以外の鍵に束縛されることがありうる（F10）。REPAIR_DELEG_AT は束縛せず、may_act の URI で照合する。
- **op-source-change**（退職と異動で辿った）
  - 辿った範囲：人事部の登録と 2 人目の承認による確定（2 時間以内。人事部の手順で、3.1 で見送り）、aoba-pdp が人事の台帳を直接読む経路（キャッシュ 60 秒）、ツールと agent-sts への届き方、9.2 の「元のデータからの経路」。
  - 気づき：
    - 人事の台帳の API が止まると、24 時間誰も約束していない区間ができる（F7）。
    - 担当の付け替えは、課長の画面から修繕依頼の台帳に書かれるが、agent-sts のキャッシュで 3600 秒の空白がある（F5）。
    - agent-sts はログイン名で aoba-pdp を引き、その対応に aoba-as の属性（hr-sync が書く）を使う（F9）。
- **op-one-time**
  - 辿った範囲：承認、解錠の送り直し、LOGIN_CODE、CONSOLE_LOGOUT の jti、連絡の下書きの ID。
  - 気づき：
    - 承認の消費は approval-svc の原子的な条件つきの更新で、発注 ID か承認自身に結ぶ。並行の 2 件は片方だけが成功し、結果が分からない後の再試行は同じ ID に前の結果を返す。approval-svc が止まれば拒否する。この 3 つの場面で 2 回通る経路も、正しい 1 回が失われる経路も見つけられなかった。
    - 送り直しは回を条件つきの更新で上げる（3 回まで）。LOGIN_CODE は 1 回限り、CONSOLE_LOGOUT は jti を 150 秒覚える。
    - ツールのトークンは replay_check が false だが、業務の ID で重複を防いでいるので問題はない。
    - 承認を「1 回だけ」にできていても、承認の中身が F2・F3 で崩れる点は別の問題。
