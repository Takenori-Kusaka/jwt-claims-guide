## レビューの結果：designs/target（あおば住まいサービス 修繕の手配、種 12）

**結論：** 指摘は 18 件で、内訳は Major 15 件・Minor 3 件です。lint の結果は error 0、warn 3 です。warn のうち H8 の scope（approvals:decide）に付いた理由は通りません。重大度は観点書の目安で付けた仮の値で、最後はレビュアーが決めます。

### 段 1：性質の表の確かめ
- 12 の性質の判定は、図（2. の範囲の図）と要求 REQ-01〜13 に照らして、すべて合っていました。
- マルチテナントは「当たらない」で正しいです。組織は 1 つで、テナントを表す値がありません。
- 「トークンの値を DB の層まで運ぶ」も「当たらない」で正しいです。order-tool と order-scheduler は自分の DB アカウントで接続し、トークンは DB に渡りません。
- 「当たらない」とされた性質が実際にある、という指摘はありません。

### 段 2：6. の「要る」と判断の木の節
- **q-actor と keep-sub-exchange：** 受け手は最も外側の act を使っており、合っています。
- **q-peer と peer-mtls：** ツールの側は合っています。H2 の agent-sts だけが、相手が repair-console かを CONSOLE_AT の client_id で見ています。peer-mtls の節は「client_id では代えられない」としているので、取り違えです（A1）。
- **q-authorized と rar-vs-custom：** authorization_details を宛先ごとに絞っている点は合っています。ただし H8 で、承認済みの記録を変える権限を scope（approvals:decide）としてエージェントに足しています（A2）。
- **q-still-valid と lifetime-by-situation：** 都度問い合わせる方式は選んでいます。それでも 3600 秒のキャッシュ、24 時間の古い結果、2 日開く WebSocket が要求の数値を超えます（A3・A4・A10）。

### 段 4：開いた問い
- **op-proof-holder**
  - 辿った範囲：C-cnf の enforced_at、ツールのトークン 4 種と APPROVAL_AT の holder・sender_constraint、M_sender_constraint の 4.、H2。
  - 気づいたこと：ツールのトークンは「持つ者＝鍵を持つ者（repair-agent）」で揃っています。APPROVAL_AT の cnf は「交換を求めた者」の証明書ですが、H2 は wl-ca の証明書を持つどのワークロードからの交換も受けます。そのため、approval-svc が確かめる鍵が repair-console の鍵だとは限りません（A1）。証明書を更新した後、古い組のまま動けるのは最悪 300 秒で、これは許容内です。
- **op-source-change**
  - 辿った出来事：異動でロールが外れる場合と、担当の付け替え。
  - 辿った範囲：人事の台帳の確定（2 人目の承認）から、aoba-pdp（60 秒キャッシュ）、ツールまで。
  - 気づいたこと：
    - 人事の台帳の API が応答しない間は、古い結果が最大 24 時間返ります（A3）。
    - 担当の付け替えは、agent-sts の 3600 秒キャッシュを通ります（A4）。
    - agent-sts から aoba-pdp への引き当ては preferred_username（ログイン名）を鍵にしていますが、この値を誰が書けるかは、どこにも書かれていません（A5）。
    - 連絡の 2 つの scope はロールで絞らないので、ロールを外しても連絡は止まりません（A10）。
- **op-one-time**
  - 辿った範囲：承認、解錠の送り直し、発注の確定、支払いの依頼、ログアウトトークンの jti。
  - 気づいたこと：承認・確定・送り直しは条件つきの更新を先に行うので、並行の 2 件でも再送でも 1 回になります。支払いの依頼だけは、「依頼済みでないか確かめる → 送る → 依頼済みにする」の順です。並行の 2 件と、送った後に落ちて再送する場合に、支払いが 2 回になります（A12）。
