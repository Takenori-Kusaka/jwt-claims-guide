## 4. 開いた問い（手順 4）

**op-proof-holder**
- 辿った範囲は、cnf の enforced_at（front-gw と TTS）、AGENCY_AT の holder と sender_constraint、H5・H6・H31、M_sender_constraint の 2.・4. です。
- 箇所ごとの「トークンを持つ者」と「鍵を持つ者」は次のとおりです。
  - AGENCY_AT を持つのは代理店のサーバーで、鍵を持つのも代理店のサーバー（代理店向け CA の証明書）です。
  - front-gw は TLS の相手の拇印と cnf を照合し、TTS は front-gw が書いたヘッダーの拇印と cnf を照合します。
  - ヘッダーは front-gw だけが書き、同名のものは捨てます。TTS は front-gw の SVID からの要求でだけ読みます。
- 証明書を更新すると、古い証明書に束縛した AT は最大 300 秒で使えなくなります。新しい assertion で取り直します。
- 気づいた点は 2 つです。
  - 失効は CRL の取り直し頼みで、取り直せない間は前の CRL で受け続けます（F-14）。
  - AGENCY_ASSERTION は束縛されていません。mTLS の client_id と証明書のサブジェクトの組が、その代わりです。
- 持ち主の取り違えは見つかりませんでした。

**op-source-change**
- 辿った出来事は「社員の退職・異動」「契約者の停止」「代理店の登録の停止」の 3 つです。
- 辿った範囲は、9.2「元のデータからの経路」、2.2（DB の直接の修正）、2. の呼び出し表、9.1 です。
- 社員の台帳は、人事の仕組み → 台帳 → TTS（60 秒のキャッシュ）→ Txn-Token（330 秒）の順に流れ、最悪 390 秒です。ただし人事部の入力から台帳の更新までは、約束した時間がありません。3.1 で人事部が受け入れる前提としているので、許容します。
- 異動の発効から割り当ての付け替えまでは、保険金部の手作業と毎日の突き合わせで、仕組みでは止まりません。これも 3.1 に書かれています。
- 契約者の停止は、TXN_PROXY に届きません（F-05）。
- 代理店の登録の書き込み経路は、図にある as-admin-api と DB の直接の修正のほかに、shirogane-as の管理 API が呼び出し元を限っていない点があります（F-02）。
- DB の直接の修正は、書いた者の列が元の操作のままなので、後から区別できません（F-08）。

**op-one-time**
- 辿った範囲は次のとおりです。
  - 代理店の assertion の jti
  - ログインの nonce
  - セキュリティキーの登録の番号
  - PAY_MSG_CTX の再配送
  - 承認の記録
  - 支払いの実行の取り消しとの競合
- 並行 2 件、再送、記録先の障害で辿りました。nonce・登録の番号・assertion の jti は、一意制約か条件つき書き込みで 1 回に収まっています。記録先が応えなければ拒むので、正しい 1 回は失われません。
- PAY_MSG_CTX は (claim_id, assessment_ref) の一意制約と版の規則で 1 件になります。実行と取り消しは、支払いの行のロックで直列になります。
- 気づいた点は 2 つです。
  - jti を覚える時間が、C-jti の「exp まで」と C-exp・9.1 の「iat から 90 秒」で食い違っています（F-13）。
  - 承認の記録は 1 回限りではなく、請求ごとに何度も使われます（F-03）。
