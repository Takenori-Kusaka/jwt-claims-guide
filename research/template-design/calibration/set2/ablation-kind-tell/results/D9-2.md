## designs/target のレビュー結果（種 12）

指摘は 5 件です（Major 2、Minor 3）。どちらの Major も「止めたい操作が止まらない」穴です。

- **1 件目**：発行済みの解錠コードは、lock-svc か錠の機器の網が止まると取り消せません。
- **2 件目**：予約の実行は、aoba-as の利用者の無効化では止まりません。

設計書は全体にとても厚く書かれています。問い 17 のうち 14 は Yes でした。

### 手順の結果

1. **性質の表**：12 の性質を、図（2.）・要求（REQ-01〜13）・6. と照らしました。12 件とも sheet.md のとおりです。「当たらない」とされた 2 つも合っています。
   - マルチテナント：組織は 1 つで、テナントの値がありません（catalog_answers の multitenant は No）。
   - DB の層：トークンで DB に接続していません（2. のデータ層の行、9.1 の DB の層）。
2. **判断の木と仕組みの比較**：6. の UC1〜UC4 で「要る」とした問いを、判断の木の節と比べました。
   - 合っているもの：
     - q-peer → peer-mtls：mTLS
     - q-authorized → rar-vs-custom：authorization_details を宛先ごとに 1 つの type に絞り、scope との使い分けを台帳に書いている
     - q-resource：aud は 1 つ
     - q-holder：cnf
     - q-actor：受け手は最も外側の act だけで照合し、enforced_at・validates も同じ
   - q-txn：txn-tctx の Txn-Token を使わず repair_id にしています。却下の理由（何日もまたぐ修繕依頼で、1 つの呼び出しの連鎖ではない）が通るので、不一致とはしません。
   - UC4（予約の実行）の q-sub・q-actor：keep-sub-exchange から外れています。外れること自体には理由があります。ただし、AS が交換のときに確かめる項目を写しきれていません（指摘 F2）。
3. **lint**：error は 0 です。warn は H5・H8 の L16 の 2 件で、どちらにも理由が書かれています。追加した authorization_details の根拠は承認の記録で、広がるのはその 1 件の分だけです。この理由は通ると判断しました。lint を通すために宣言を曲げた跡もありません。

### 開いた問い 3 つ

- **op-proof-holder**
  - 辿った範囲：鍵の持ち主を確かめる箇所を 4 つ並べました。
    - ツール 4 つ：持つ者・鍵を持つ者ともにエージェント
    - approval-svc：ともに repair-console
    - agent-sts の REPAIR_DELEG_AT：may_act の URI と mTLS の相手
    - agent-sts の CONSOLE_AT：repair-console
  - 気づき：どの箇所も、トークンを持つ者と鍵を持つ者は同じでした。証明書の更新は、M_sender_constraint の 4. で、証明書とトークンを組で管理する形で扱っています。
  - 残る点：受け手の許可リストが拇印でなく URI なので、wl-ca の中間の CA が漏れると破れます。ただしこれは 3.1 に書かれています。
- **op-source-change**
  - 辿った出来事：異動で修繕担当のロールが外れる。
  - 経路：人事部の登録 → 2 人目の承認で確定 → aoba-pdp が人事の台帳の API を引く（キャッシュ 60 秒） → 次の交換と、重要な操作の呼び出しのたびに止まる。下書き・連絡は最悪 390 秒です。
  - 気づき：図に無い書き込みの経路（DB の管理者の直接の書き込み）は、変更の記録の表で止める形で書かれています。登録から確定までは、誰も時間を約束していない区間ですが、人事部の手順（2 時間）として 3.1 に明記されています。
  - 新しく見つけたこと：aoba-as の側だけでの無効化は、予約の経路に届きません（F2）。
- **op-one-time**
  - 辿った範囲：承認、解錠コード、送り直しの回、連絡の下書き ID、ログアウトトークンの jti、認可コード。それぞれ並行の 2 件・結果不明の後の再送・記録先の障害で辿りました。
  - 気づき：消費はどれも条件つきの更新で、業務の ID（発注 ID・承認 ID）に結んでいます。同じ ID での再試行には前の結果を返すので、2 回は通らず、正しい 1 回も失いません。approval-svc が止まれば拒否します。指摘はありません。

さらに辿ってよい開いた問い（op-clock・op-key-custody・op-requirement-words）は、軽く辿っただけです。
