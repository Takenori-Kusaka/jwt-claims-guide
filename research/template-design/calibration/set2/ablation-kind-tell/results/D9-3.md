## 4. 開いた問い

### op-proof-holder

辿った範囲は、トークンを持つ者と鍵を持つ者を箇所ごとに並べることです。

- 交換の入口：client_id と may_act の URI を mTLS の相手と照合します。
- ツールと approval-svc：cnf の拇印を mTLS の相手と照合します。

気づいたこと：
- 鍵の持ち主（wl-ca の証明書）はトークンの持ち主と同じワークロードです。プロンプト注入で乗っ取られたエージェントは cnf では止まらず、止めるのは承認の結びつきと許可リストです。
- 証明書は 24 時間で、失効の確かめはありません。漏れたら登録から外すのに 30 分かかります。これは 3.1 に書いてあります。
- 証明書を更新すると拇印が変わりますが、トークンは 300 秒なので交換し直せば足ります。REPAIR_DELEG_AT は URI で照合するため、更新の影響を受けません。
- 同じワークロードの URI を複数のインスタンスで共有する場合に、証明書を分けるかが書かれていません。確認をお勧めします。

### op-source-change

事例は、退職と、異動でのロール剥奪です。

- 経路：人事の台帳に登録 → 人事部の 2 人目が承認して確定（起点）→ aoba-pdp が直接読む（60 秒キャッシュ）→ agent-sts の交換とツールの呼び出しで拒否。
- 並行して hr-sync が 5 分以内に aoba-as の利用者を無効化し、ログアウトトークンが BFF に届きます。
- 登録から確定までは、人事部の手順（2 時間以内、月次報告）に委ねています。

気づいたこと：
- 3.1 は 5 つの DB の直接書き込みを、変更の記録と毎日の突き合わせで扱っています。しかし**人事の台帳の直接書き込みは入っていません**。ここから上長・修繕担当・鍵の取り扱いのロールが導かれます（F-2）。

### op-one-time

辿った範囲は、承認、予約、解錠コードの再送、LOGIN_CODE、ログアウトの jti です。

- 承認の消費は、approval-svc の条件つき更新 1 回で完結します。
- 並行 2 件は片方だけが成功します。
- 通信が切れた後の再送には、同じ発注 ID で前の結果を返します。
- 解錠コードは承認 ID ごとに 1 つで、再送は回数を条件つきで上げます。
- 予約の実行は、落ちたら同じ発注 ID で次の回に再試行します。

気づいたこと：
- 承認を使用済みにした後で確定が結果不明のとき、トークン（300 秒）が切れた後の再試行が書かれていません（F-3 の次の項目、F-5）。
