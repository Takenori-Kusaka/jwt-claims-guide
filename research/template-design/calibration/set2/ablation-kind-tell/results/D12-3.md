## 手順 3：優先 1 の問いへの回答

### 抜き取った 3 行

- dc-05：Yes。amount は税込の円の 10 進文字列で、ID も文字列です。正規化と完全一致も決まっています。メンバーの型を受け手の schema では表さない件は、3.1 に代替の試験が書いてあります。ただし F-13 の軽微な食い違いがあります。
- q-value-vocabulary：該当なし。roles と groups は却下済みで、トークンに載りません。scope の語彙は固定されています。
- q-identifier-choice：No。agent-sts から aoba-pdp への問い合わせは、sub でなく `preferred_username`（ログイン名）で引いています。この値には claims.yaml の行がありません（F-08）。
- ap-1-7：No。担当を割り当てる課長が、自分を担当にして解錠を 1 人で承認できます。検出も事後の週次点検だけです（F-15）。
- q-freshness-mitigation：No。C-repair-id は担当の付け替えが 3930 秒で止まり、要求の 600 秒を超えます（F-05）。

### 経路の問い

- q-single-aud-resource：Yes。どの種別も aud は 1 つで、受け手は aud が自分 1 つだけであることを照合します。例外の経路は F-09 に記録しました。
- q-no-passthrough：No。H4 は、repair-agent に `https://*.aoba-sumai.example/mcp` の形の任意の宛先を許します（F-09）。
- q-step-up-path-coverage：No。approval-svc が見る auth_time は agent-sts が交換時刻を書いた値で、5 分以内の確認が空洞になっています（F-02）。
- ap-2-7：Yes。act の無い REPAIR_DELEG_AT は aud が agent-sts だけで、may_act の主体しか交換できません。ツールは aoba-as のトークンも REPAIR_DELEG_AT も受けません。APPROVAL_AT は act が無いのが仕様で、approval-svc が確かめます。
- q-authorize-service-and-user：No（Minor）。ツールは mTLS の相手と act と cnf を照合しています。しかし H2 は「どのワークロードでもよい」とし、approval-svc の承認の口には呼び出し元の許可リストが書かれていません（F-11）。
- q-agent-short-lived-no-rt：Yes。agent-sts は RT を出さず、REPAIR_DELEG_AT とツールのトークンは 300 秒で、refresh は「なし」です。

### 全体の問い

- q-outside-catalog：No。本番の approval-svc に X-Test-Now の口が残り、閉じる日が決まっていません（F-03）。
- q-object-level-authz：No。payment-tool は、支払う発注が token の repair_id の修繕依頼のものか照合しません（F-07）。
- q-approval-from-as：No。承認する人は、エージェントが書いた説明の文を見て承認します。実際の金額・協力会社は画面に出ません（F-01、F-10）。
- q-operator-act：No（Minor）。lock-svc の管理画面で当番が行う失効は、依頼した担当者の取り消しとして記録されます（F-12）。
- q-revocation-delivery：No。最悪が 600 秒を超える経路が 3 つあります。担当の付け替えで 3930 秒、人事 API 障害時に最大 24 時間、返信の購読は最大 2 日です（F-04、F-05、F-06）。
- q-dependency-outage：No。3.1 は「止める側に倒す」としていますが、aoba-pdp は人事 API が止まると古い結果を 24 時間返します（F-04）。

## 手順 4：開いた問い

### op-proof-holder

- 辿った範囲：cnf の enforced_at、C-client-id、H2・H3・H12、3.1 の送信者制約の行、M_sender_constraint の 4.、catalog の q-peer。
- 箇所ごとに、トークンを持つ者と鍵を持つ者を並べました。

| 箇所 | トークンを持つ者 | 鍵を持つ者 | 判定 |
| --- | --- | --- | --- |
| ツール 4 種 | repair-agent または visit-subagent | 交換を求めた者 | 同一で問題なし |
| APPROVAL_AT | repair-console のつもり | 交換を求めた任意のワークロード | 一致を保証していない |

- APPROVAL_AT の cnf は、交換を求めた mTLS の相手の証明書です。agent-sts は H2 で相手を限定していません。CONSOLE_AT は束縛のない bearer で、相手の確認を client_id（claim）に頼っています。これは判断の木 peer-mtls の取り違えの例にあたります（F-11）。
- 気づいた点：証明書の更新は共通部品が「証明書とトークンの組」で扱っています。その点は問題ありません。

### op-source-change

- 出来事は退職と異動です。
- 辿った経路：人事部の登録、2 人目の承認で確定、aoba-pdp が人事 API を読む（60 秒キャッシュ）、ツールの呼び出しごとの確認。hr-sync が aoba-as のセッションを消す経路は 5 分ごとで、判断の経路には入りません。
- 誰も時間を約束していない区間が 4 つありました。
  - 登録から確定まで最大 2 時間は、人事部の手順で、月次報告だけです。
  - 人事 API が止まったときは、24 時間古い結果を通します（F-04）。
  - agent-sts の担当キャッシュ 3600 秒（F-05）。
  - 連絡は、ロールでは止まりません。agent-sts が在籍を確かめる交換は止まりますが、開いたままの購読は止まりません（F-06）。
- 元データの書き手は、人事部 2 人、hr-sync、基盤チームの DB 管理者です。DB 管理者の直接書き込みは変更の記録の表で止める設計で、図にもあります。この点は問題ありません。

### op-one-time

- 承認の消費は、approval-svc の条件つきの更新（承認済み・未使用なら、発注 ID または承認自身に結んで使用済み）で行います。
- 並行の 2 件：片方だけが成功します。
- 通信が切れた後の再送：同じ発注 ID なら前の結果が返り、別の発注 ID は失敗します。
- 記録先の障害：approval-svc が止まれば拒否します。
- 使用済みになった後、確定が失敗した場合：同じ発注 ID で再試行します。それでも確定できない場合は、承認を失効させて新しい発注 ID で依頼し直します。正しい 1 回は失われません。
- 解錠コードの送り直しは、回数を条件つきの更新で上げてから送ります（最大 3 回）。2 回通る経路は見つかりませんでした。
- 気づいた点：lock-tool が使用済みにした後も、承認の `not_after` をエージェントが更新できます（F-10）。この更新は、1 回だけ使うという意味を弱めます。X-Test-Now による承認期限の操作も同様です（F-03）。
