# designs/target のレビュー結果（抜き取りの種：12）

13 件を指摘します。Blocker が 3 件、Major が 9 件、Minor が 1 件です。CI は error 0 で OK ですが、warn 3 件のうち H8 の scope の warn は、書き手の理由が通りません（F11）。

**読んだ範囲：** design.md の 1〜3、6、9.1・9.2、12、付録 B・D（P1、P4、M_authz_pdp の 3〜5）を読みました。YAML は claims.yaml の主な行、hops.yaml の全部、catalog_answers.yaml（lite_criteria・idp・outside_enumeration・questions・U29/U30）を読みました。スキーマは CONSOLE_AT と LOCK_TOOL_AT だけです。

**読んでいない範囲：** token_types.yaml の全体、design.md の 4・5・7・8・10・11、M_token_validation・M_sender_constraint の記入欄は通して読んでいません。

### 段 1：sheet.md の性質の表
図・要求・台帳に照らし、12 の性質はすべて表のとおりです。
- マルチテナントが「当たらない」のは正しいです。組織は 1 つで、テナントの値もありません。
- DB の層まで運ばないのも正しいです。ツールは自分の DB アカウントで接続します（2. の「データ層」の行）。
- 抜き取りの 3 行（C-approval-ref・C-repair-id・C-authorization-details）も、usage が authz か identifier の行です。

### 段 2：判断の木との突き合わせ（6. で「要る」とした問い）
- **q-peer**（peer-mtls）：
  - ツールでは合っています。最も外側の act.sub を、mTLS の相手の URI と照らしています。
  - H2 と H12 では、相手を通信の層でなく `client_id`（トークンの値）で見ています。木の「トークンのクレームでは代えられない」に反するので、F4 にしました。
- **q-authorized**（rar-vs-custom）：authorization_details と承認の記録は木のとおりです。ただし承認者が見る画面が、承認の中身に結びついていません（F9）。
- **q-sub と q-actor**（keep-sub-exchange）：
  - sub は保ち、act の最も外側だけで許可しているので、合っています。
  - 予約の実行は木から外れていますが、3. で理由を付けて外しています（H13・H14）。受け入れられる理由です。
- **q-txn**：Txn-Token は使っていません。代わりの repair_id は、prior_art_search で外した理由が通ります。ただし payment-tool だけが、repair_id で対象を照らしていません（F10）。
- **q-auth-strength**：6. に「要る」の行はありません（pending）。ただ、UC3 の q-authorized が acr・auth_time を使っており、その auth_time の作り方が問いに答えていません（F1）。

## 開いた問い 3 つ（辿った範囲と気づいたこと）
- **op-proof-holder**
  - 辿った範囲：C-cnf の enforced_at、H5〜H8・H11・H12、3.1 の wl-ca の行。
  - ツールのトークンでは、トークンを持つ者（エージェント）と鍵を持つ者（交換を求めた証明書）が一致します。
  - APPROVAL_AT は「交換を求めた者」の鍵に結ばれますが、H2 ではその者が repair-console に限られません。鍵の持ち主が、本来の持ち主と違いうるということです（F4）。
  - 証明書の更新（24 時間、残り 8 時間で更新）では、共通の部品が証明書とトークンを組にして交換し直すので、問題はありません。
  - REPAIR_DELEG_AT には cnf がありません。may_act と mTLS で代えており、これは 3.1 の見送りのとおりです。
- **op-source-change**
  - 異動でロールが外れる場合を辿りました。人事の台帳の確定（2 人目の承認。登録から最大 2 時間は 3.1 の見送り）→ aoba-pdp（60 秒キャッシュ）→ 重要な操作のツール（最悪 60 秒）と、agent-sts の scope の絞り直し（下書きは 390 秒）です。
  - 誰も時間を約束していない区間が 3 つありました。連絡はロールの剥奪では止まらないこと（F7）、人事の台帳の API が止まると 24 時間かかること（F8）、agent-sts の入力がログイン名で、その写しは hr-sync が 5 分ごとに書くこと（F5）です。
  - 担当の付け替えでは、agent-sts のキャッシュが 3600 秒です（F6）。
- **op-one-time**
  - 辿った範囲：承認の消費（条件つきの更新で発注 ID に結ぶ）、送り直しの回（n が 3 未満なら n+1 の条件つきの更新）、lock-svc の承認 ID ごとに 1 つのコード、通知の基盤の重複の鍵、予約の「予約→確定」の条件つきの更新。
  - 並行の 2 件は片方だけが通ります。結果不明の後の再送も同じ発注 ID・同じ回で 1 回になり、正しい 1 回も失われません。
  - ただし、approval-svc の期限の比べは X-Test-Now で時刻を変えられ、期限切れの承認を「期限内」として 1 回使わせられます（F2）。
