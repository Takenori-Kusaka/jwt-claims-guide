# レビュー結果：designs/target（しろがね損保、種 12）

指摘は 15 件です。Blocker 3 件、Major 9 件、Minor 3 件。中でも重いのは次の 5 件です。
- **F-01**：代理店の担当者が、claim_id を指定すれば他の代理店の請求を読めます。
- **F-02**：shirogane-as の管理の書き込みの API が、網の中のどのサービスからの書き込みも受けます。
- **F-04**：上長の承認が請求ごとの記録なので、承認していない後の支払いにも使われます。
- **F-05**：指示を受け付けた後にかけた保留が、支払いの実行を止めません（REQ-04 に反する）。
- **F-08**：2 本目のセキュリティキーをパスワードだけで足せるので、REQ-05 のハードウェアの鍵の要件が崩れます。

## 1. 性質の表の確かめ（段 1）
- 12 の性質は、図と要求に照らして、どれも当たり・当たらないが正しいと判断しました。
- 「長時間・非同期の処理がある」は、根拠に挙げた欄が違います。PH_AT の long_running は「長い処理には使わない」と書いています。当たる根拠は PAY_MSG_CTX の long_running と、H20・H21 の broker_connection です。結論は変わりません。
- 「操作ごとの承認」は、業務としてはあります（REQ-05 の高額の支払いの承認）。ただトークンの外にあり、authorization_details も承認の ID の行も無いので「当たらない」は定義どおりです。承認の問いは、委任の性質から出る q-approval-from-as で答えました（F-04）。
- 「マルチテナント No」は宣言どおりです。ただし代理店ごとの切り分けは、テナントに近い境界です。F-01 は q-tenant-data-match があれば拾えた種類の誤りです。
- lint の warn 8 件には、どれも通る理由があります。L1b は草案の名前です。L16 は aud が信頼ドメインで、scope と寿命は上流を超えていません。ただし H30 の寿命は宣言を曲げた疑いがあります（F-12）。

## 2. 判断の木との突き合わせ（段 2）
次の 5 か所が木の節と合いませんでした。
- **peer-mtls**：H29 と、shirogane-as の管理の書き込みの API。どちらも mTLS で相手を認証するだけで、相手の一覧と照らしていません。H29 は「TXN_STAFF を持っていること」で、頼んでよい相手かどうかの判断に代えています（F-02・F-03）。
- **rar-vs-custom**（UC5 の q-authorized）：承認の記録が請求の単位で、承認した操作（payment_id・金額）に結びついていません（F-04）。
- **lifetime-by-situation**：保留はすぐ効かせたい操作なのに、指示の受け付けの時点で 1 回確かめるだけです（F-05）。
- **keep-sub-exchange**：H19 で、要配慮の書類を assessment-svc 自身の権限で読みます（F-11）。
- **UC4 の q-actor「不要」**：payment-worker は中身を変えられない運び手で、q-req-wl と q-peer で別に記録しているので、指摘にはしませんでした。

## 4. 開いた問い（段 4）
- **op-proof-holder**
  - 辿った範囲：AGENCY_AT の cnf（front-gw・TTS）、H5・H6、PH_AT・EMPLOYEE_AT の口。
  - トークンの持ち手と鍵の持ち手は、代理店のサーバーと、claim-portal・staff-console の SVID でそれぞれ一致します。
  - 証明書を更新すると拇印が変わります。そのため発行済みの AGENCY_AT（最大 300 秒）は使えなくなりますが、許容できる範囲です。
  - 弱い点：代理店の登録は証明書を拇印でなくサブジェクトで照らします。そのサブジェクトは F-02 の経路で書き換えられます。加えて、F-14 の CRL の扱いがあります。
- **op-source-change**
  - 辿った出来事：上長の退職。人事の入力と承認で台帳が変わり、TTS のキャッシュ 60 秒と Txn-Token の 330 秒で、390 秒後に止まります。
  - 誰も時間を約束していない区間：発効から台帳の更新まで（3.1 の見送り）。
  - その上長が書いた承認の記録は有効のままで、F-04 によって同じ請求の後の支払いにも効き続けます。
  - 図に無い書き込みの経路：網の中の任意の SVID から shirogane-as への書き込み（F-02）、DB の直接の修正（F-10）、パスワードだけでの鍵の追加（F-08）。
- **op-one-time**
  - 辿った値：鍵の登録の番号、assertion の jti、PAY_MSG_CTX と指示の重複の判定。
  - 登録の番号は条件つきの 1 回の書き込みで、並行の 2 件は 1 件だけ通ります。jti は (iss, jti) の一意の制約を 90 秒覚えます（60＋ずれ 30 を覆う）。どちらも問題ありません。
  - PAY_MSG_CTX は 1 回だけの値ではありません。重複の判定は申告の assessment_ref に頼っています。F-03 の経路で版を進めれば、実行の後に新しい指示を通せます。それが F-04 で既存の承認に乗ります。
  - 再送のときは、(claim_id, assessment_ref) の一意の制約で正しい 1 件が残ります。

さらにの 3 問（op-clock・op-key-custody・op-requirement-words）は辿っていません。
