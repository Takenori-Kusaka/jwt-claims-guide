## 段 2：6. の「要る」の問いと判断の木

- **合うもの**
  - q-sub・q-actor は keep-sub-exchange に合います。sub は保たれ、判断は最も外側の act だけで、mTLS の相手と照らします。
  - q-peer は peer-mtls、q-authorized は rar-vs-custom に合います。scope と authorization_details の役割分担も enforced_at に書かれています。
  - q-txn は repair_id で答えています。Txn-Token を却下した理由は台帳の prior_art にあります。
  - UC4 で交換し直さないことは、3. と 3.1 に、木の既定から外れる点として理由つきで書かれています。
- **ずれるもの**：UC2 の q-holder を C-may-act で答えている点と、C-roles の代わりに C-scope を挙げている点です（F2・F3）。

## 段 4：開いた問いで辿った範囲

- **op-proof-holder**
  - 辿った範囲：C-cnf の enforced_at、各種別の holder と sender_constraint、H5〜H8・H11・H12、3.1 の証明書の行。
  - 気づき：束縛したトークンでは、どの箇所でも「トークンを持つ者」と「鍵を持つ者」が同じでした（ツールのトークンは交換を求めたエージェント、APPROVAL_AT は repair-console）。証明書の更新時は、共通の部品が証明書とトークンを組で扱います。
  - 束縛していない REPAIR_DELEG_AT は、may_act の照合を拇印でなく URI で行います。そのため中間の CA の鍵が漏れると開きますが、これは 3.1 に書かれています（F2 の背景）。
- **op-source-change**
  - 辿った出来事：退職と担当の付け替え。
  - 退職：人事の台帳で 2 人目が承認して確定 → aoba-pdp が直接読む（キャッシュ 60 秒）→ 重要な操作のツールと approval-svc が呼び出しのたびに確かめる、と辿れました。登録から確定までは 3.1 で人事部の手順（2 時間）に任されています。
  - 担当の付け替え：課長が画面で行い、台帳に追記だけで残ります。
  - 気づき：当番のロールの元である「勤務の予定」は、書き手と承認の手順がどこにも書かれていません（F5）。
- **op-one-time**
  - 辿った値：承認、LOGIN_CODE、CONSOLE_LOGOUT の jti、解錠コードの送り直しの回。
  - 並行の 2 件は条件つきの更新で片方だけが通ります。再送は同じ発注 ID や承認 ID なら前の結果を返し、記録先が止まれば拒否します。「使用済み・未確定」を扱う手順もあるので、正しい 1 回も失われません。指摘はありません。
- **（さらに）op-clock**：別々の時計で書かれた時刻を比べる箇所が 2 種類あり、時計のずれの扱いが書かれていません（F4）。
