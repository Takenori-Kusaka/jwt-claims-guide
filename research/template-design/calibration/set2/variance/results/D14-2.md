# JWT クレーム設計書のレビュー：designs/target

## 結論

指摘は 12 件です（Major 4、Minor 8、Blocker 0）。sheet.md の優先 1 の 16 問のうち **No は 3 問**（ap-1-7・q-identifier-choice・q-dependency-outage）でした。開いた問いでは op-one-time が No です。

対策を急ぐべきなのは次の 2 件です。

- **F-01（二重払い）**：払い直しのつもりで出した新しい版の指示が、古い版の実行の後に別の支払いとして通りうる
- **F-02（社員の台帳の障害）**：台帳が止まると取り消しも保留もできなくなるのに、夜間の支払いの実行だけは続く

CI の結果は error 0・warn 9 で、warn にはどれも理由が付いていました。理由の書き方の不備は F-06 にまとめています。

- 抜き取りの種は 12、抜き取った行は C-agency-code・C-client-id・C-act です。問いが名指すので C-scope（ロールの代わりに使う認可の値）と C-sub（上流の識別子）を足しました
- 読まずに台帳の側で代えた節：設計書の 4.・5.・7.・8.・10.・11.
- 暗号・製品の挙動・委任の深さについては答えていません

## 手順 4：開いた問い

**op-proof-holder（辿った範囲：AGENCY_AT の cnf、H31・H5・H6、M_sender_constraint の 4.）**
- 鍵を確かめる箇所は 3 つで、どこでも「トークンを持つ者」と「鍵を持つ者」は代理店の同じサーバーでした。発行のときは shirogane-as が H31 の mTLS の証明書に束縛し、front-gw が TLS の拇印と照らし、TTS は front-gw の SPIFFE ID からだけ拇印のヘッダーを読みます
- 証明書を更新すると、古い証明書に束縛した AT は最大 300 秒で使えなくなります
- 残る限界は、CRL を取り直せない間に失効した証明書を最長 3600 秒受けることです（3.1 に書いてある）
- PH_AT・EMPLOYEE_AT の代わりの守り（口に接続できる SVID）の持ち主も、トークンを持つ BFF と同じでした
- 問題は見つかりませんでした

**op-source-change（出来事：査定担当者の退職）**
- 人事部が入力し、責任者が承認すると社員の台帳が変わります。そこから TTS（キャッシュ 60 秒）、TXN_STAFF（330 秒）、SSO_SESSION（60 秒）の順に効きます
- キューで待っている PAY_MSG_CTX は、作り直しのときに TTS が拒み、期限の後に滞留のキューに移ります。その後、上長が割り当てを替え、新しい担当者が新しい版で確定します
- 誰も時間を約束していない区間が 3 つありました
  1. 発効から台帳の更新まで（3.1 で見送り。人事の規程で 1 時間）
  2. 滞留から確定し直すまで（業務の手続き）
  3. 課の異動（毎日の突き合わせに頼る）
- さらに、人事の仕組み自体の管理者が、書き手として数えられていません（F-03）

**op-one-time（辿った値：AUTH_CODE、assertion の jti、nonce、登録の番号、指示、実行）**
- 指示より前の値は、どれも確かめと使用済みの書き込みを 1 回で行い、記録先が応えなければ拒みます。並行の 2 件と通信が切れた後の再送でも、2 回は通りません
- 指示は (claim_id, assessment_ref) の一意の制約、実行は行のロックで 1 回になります
- **穴は版の規則と再配送の組み合わせです**（F-01）。正しい 1 回は、滞留と確定し直しで取り戻せます

さらに辿れた範囲：
- op-key-custody：TTS の鍵が漏れたとき、キューの中の PAY_MSG_CTX がどうなるかまで書いてありました。問題は見つかりませんでした
- op-clock：IVR と代理店の IdP の時計は 12. に挙がっていて、新しい気づきはありません
- op-requirement-words：辿っていません
