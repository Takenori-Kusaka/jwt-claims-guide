指摘は 15 件です（Blocker 4・Major 10・Minor 1）。抜き取りの種は 12、抜き取った行は C-approval-ref・C-repair-id・C-authorization-details です。

**読んだ範囲：** design.md の 1.〜6.・9.2・12.・付録 B、付録 D の P4 の 4.・5. と M_sender_constraint の 4.、claims.yaml の C-iss〜C-approval-ref、hops.yaml の全部、token_types.yaml の該当する欄、catalog_answers.yaml の該当する欄です。design.md の 7.・8.・9.1・10.・11. と付録 D の残りは通して読んでいません。

## 手順ごとの確認

**段 1：性質の表。** 12 項目すべて、図と要求に照らして正しいと確かめました。
- マルチテナントは「当たらない」で正しいです。組織は 1 つで、テナントの値がありません。
- DB の層は「当たらない」で正しいです。ツールは自分の DB アカウントで接続し、db_connection のホップがありません。
- 長時間の処理には、ORDER_TOOL_AT のほかに CONTACT_TOOL_AT の long_running もあります（F09）。

**段 2：判断の木。**
- q-sub・q-actor（keep-sub-exchange）は合っています。UC4 で交換しないのは 3.1 に理由があり、受け入れます。
- q-txn は Txn-Token の代わりに repair_id を使っています。prior_art_search に理由があり、受け入れます。
- q-holder（cnf）・q-resource（aud）・q-via（監査ログ）は合っています。
- ずれていたのは 2 つです。
  - q-peer（peer-mtls）：approval-svc がトークンの client_id で相手を決めています（F12）。
  - q-authorized（rar-vs-custom）：承認の中身を scope や、エージェントが書いた文で扱っています（F03・F04）。

**lint の warn（3 件）。**
- H5・H8 の authorization_details の 2 件は、理由が通ります。承認の記録が別の権限の元になっていて、広がるのはその 1 件の分だけです。
- H8 の scope approvals:decide の 1 件は、理由が通りません（F04）。

## 開いた問い（辿った範囲と気づいたこと）

- **op-proof-holder：** ツールでは、トークンを持つ者も鍵を持つ者も、交換を求めたエージェントで同じです。APPROVAL_AT では、トークンを持つのが repair-console で、鍵は交換を求めた者の証明書です。ただし交換を求められるのは wl-ca のどのワークロードでもよく、repair-console に限られていません（F12）。証明書の更新は aoba-agent-kit が証明書とトークンを組で持つので、cnf の食い違いは起きません。
- **op-source-change：** 異動を例に辿りました。人事部の登録から 2 人目の承認まで（最大 2 時間。3.1 で見送り）→ aoba-pdp が人事の台帳を引く（60 秒のキャッシュ）→ ツールと agent-sts、の順です。誰も時間を約束していない区間が 3 つありました。
  - 人事の台帳の API が止まった間の 24 時間（F06）
  - 担当のキャッシュの 3600 秒（F07）
  - 連絡がロールの剥奪で止まらないこと（F08）

  引くキーがログイン名であることも、この経路で見つけました（F11）。
- **op-one-time：** 承認の消費、並行の 2 件、通信が切れた後の再送、記録先の障害を辿りました。どれも条件つきの更新・同じ発注 ID での再試行・止める側に倒す、で 2 回通らず、正しい 1 回も失われません。解錠コードの送り直しの回の上限（3 回）も同じ仕組みで守られています。気づいたことは 2 つです。
  - X-Test-Now で承認の期限の比べを動かせます（F02）。
  - 発行済みのコードを止めるのは、毎日 3 時の同期に頼っています（F10）。
