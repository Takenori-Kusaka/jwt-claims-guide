# designs/target のレビュー結果（しろがね損保の設計書）

レビューの結論として、問いのうち 11 問が No で、指摘は 14 件になりました（Blocker 4・Major 8・Minor 2）。sheet.md の性質の表にも誤りが 2 つあります。ファイルはこのフォルダの中だけを読み、何も書いていません。

## 段 1：sheet.md の性質の表を、図と要求に照らして確かめた結果

- **操作ごとの承認がある［当たらない］は誤り**です。REQ-05 の「上長の承認」と、payment-svc の承認の記録（H23）は、操作ごとの承認そのものです。これを指摘 F-11 にし、出していなかった dc-05 も足して答えました（答えは Yes）。
- **長時間・非同期の処理がある［当たる］は、結論は正しいのですが根拠が違います**。PH_AT の long_running の欄は「長い処理には使わない」と書いています。実際に当たる根拠は、PAY_MSG_CTX（H20・H21）と U13 です。
- **マルチテナント［当たらない］は、宣言としては受け入れます**。ただし代理店は別の会社なので、代理店ごとにデータを分ける問いは q-object-level-authz で見ました（F-01）。
- ほかの行は、図・台帳・要求と合っていました。

## 段 2：6. で「要る」とした問いを、判断の木の節と比べた結果

ほとんどの行は、節が選ぶ仕組みと合っていました（q-sub と sub、q-txn と txn・tctx、q-peer と mTLS の SPIFFE ID、q-holder と cnf）。食い違ったのは次の 3 か所です。

- **UC2 の q-authorized**：agency_code があるかだけで照会を許しています（F-01）。節は carry-or-query で、持ち主はデータの側で照らすべきです。
- **UC5 の q-authorized**：承認の記録が請求ごとで、支払いごとに結びついていません（F-03）。節は rar-vs-custom です。
- **UC4 の q-peer（H29）**：TXN_STAFF を持っていることを、PAY_MSG_CTX を頼んでよい相手の代わりにしています（F-04）。節は peer-mtls です。

UC4 の q-actor を「不要」とした点は、req_wl と q-peer で別に答えており、payment-worker は値を変えられない運び手なので、妥当と判断しました。

## 段 4：開いた問い 3 つを辿った範囲と、気づいたこと

**op-proof-holder（鍵を持つ者とトークンを持つ者）**
- 代理店の口は、トークンを持つ者も鍵を持つ者も代理店のサーバーで、一致していました。front-gw が x5t#S256 を照らし、TTS は front-gw の書いた拇印と照らします。
- 契約者の口・社員の口は、PH_AT・EMPLOYEE_AT を持つ claim-portal・staff-console と、front-gw が受ける SVID が同じ部品で、一致していました。
- 証明書を更新すると拇印が変わります。その後は古い AT が front-gw で拒まれ、新しい AT（300 秒）に替わるので問題はありません。
- 気づいた点は、CRL を取り直せない間の受け入れに上限が無いことです（F-10）。

**op-source-change（元のデータが変わってから受け手の判断が変わるまで）**
- 「役割が外れる」を辿りました。人事の仕組みで入力・承認 → 社員の台帳 → TTS のキャッシュ 60 秒 → Txn-Token 330 秒で、最悪 390 秒です。REQ-03 の 600 秒に収まります。発効から台帳の更新までは、3.1 で見送りとして受け入れています。
- 「代理店コードが変わる」を辿りました。9.2 は書き手を H26（2 人の操作）だけとしていますが、2. の表では shirogane-as の管理の書き込みの API が、網の中のどの SVID からでも書き込みを受けます（F-02）。
- 図に無い書き込みの経路が 2 つありました。保守の踏み台から網に入る経路（F-07）と、DB の直接の修正（F-08）です。
- 承認の記録は、承認した人が退職・異動しても、その請求の後の支払いに使われ続けます（F-03）。

**op-one-time（1 回だけ使える値）**
- 次の 4 つは、並行の 2 件・再送・記録先の障害のどれでも 2 回は通りませんでした。
  - 鍵の登録の番号：同じ取引の中の条件つきの書き込み
  - assertion の jti：一意の制約で、記録先が応えなければ拒む
  - nonce：取り出して消す 1 回の操作
  - 支払いの実行：支払いの行のロックと payment_id の一意の制約
- 2 回通りうるのは PAY_MSG_CTX です。H29 は頼み直しで何回でも出せ、assessment_ref は頼む側の申告です。実行の後に新しい版を作れば、2 回目の指示が通ります（F-12）。
- 正しい 1 回が失われる経路は見つかりませんでした。H21 は失敗しても再配送に任せ、期限を過ぎたものは滞留のキューに移します。
- PAY_MSG_CTX の subject_token の型（独自の URN）は、12. のとおり専門家に回す候補です。
