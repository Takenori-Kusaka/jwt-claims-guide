## K1 アクセストークン／IDトークンの中身と使い分け

**該当箇所**
- 2.4「サンプルアプリケーションへのログイン方法」p.23–26（IDトークンとアクセストークンの実例 JSON、クレーム解説）
- 3.2「OIDCによるユーザーの認証」p.35–38、3.3「アクセストークンへのJWTの活用」p.38–40
- 4.4「ユーザーの認証」p.50–52（トークンレスポンスの各フィールド）、4.5「IDトークン」p.52–58、4.6「UserInfoエンドポイントの呼び出し」p.58–60
- 5.3「アクセストークンの取得」p.67–71（aud / realm_access / resource_access / scope）
- 6.3.1〜6.3.3 p.94–98（サーバーサイドでは ID トークンで HTTP セッションを確立）

**要旨（言い換え）**
- OAuth 2.0 はアクセストークンの形式を決めておらず、アプリから見ると「不透明（Opaque）」なものとされる。一方 OIDC の ID トークンは JWT と形式が決まっているので、クライアントはクレームを直接読める（p.35, 38）。
- Keycloak は相互運用性と性能のために、アクセストークンも最初から JWT（JWS）で発行している。これでリソースサーバーはトークンを自分で読めるので、イントロスペクションや UserInfo を毎回呼ばなくてよく、レイテンシーも Keycloak の負荷も下がる（p.38–39）。
- ID トークンは RP（アプリ）がユーザーの身元を確認し、ログインセッションを作るためのもの。aud には RP 自身のクライアント ID が入る。アクセストークンは別サービスへ渡すもので、aud には呼び出し先のリソースサーバーが入る（訳注 p.54、p.70）。サーバーサイドアプリ／BFF は ID トークンでセッションを作り、外部 API を呼ぶときだけアクセストークンを使う（p.94–98）。
- 主要クレームの解説：exp/iat/auth_time/jti/aud/azp/sub/iss（p.24, 53–54）。アクセストークン固有のものとして allowed-origins・realm_access・resource_access・scope がある（p.25–26, 70–71）。
- **ユーザーを識別するキーには sub を使い、preferred_username やメールは使わない**。ユーザー名やメールは後で変わったり別人に付け替えられたりするため（p.24, 54）。
- UserInfo は OIDC フローで得たアクセストークン（scope に openid を含む）でしか呼べない。返す内容はマッパーで別途制御できる（p.58–60）。
- ID トークンも短命にしておき、更新にはリフレッシュトークンを使う。リフレッシュトークンは Keycloak しか検証できない（p.54）。

**引用**：「ユーザーのキーには常にsubクレームを使用してください」（p.24）

## K2 カスタム属性・ロール・グループをトークンに入れる（プロトコルマッパー／クライアントスコープ）と入れすぎの注意

**該当箇所**
- 2.4 p.26–27（picture 属性をトークンに追加する例）
- 4.5.2「カスタム属性の追加」p.56–58、4.5.3「IDトークンにロールを追加する」p.58、4.6 p.59–60（Hardcoded claim をクライアント直下のマッパーで UserInfo に追加）
- 5.5.2 p.79–81（ロールスコープ、クライアントスコープ経由でロールを入れる）
- 8.3.1「グループメンバーシップのトークンへのマッピング」p.147–152、8.5 p.153–154、8.2 p.146
- 10.1.5「ユーザー属性の管理」p.188
- 解答 8章 Q1・Q3・Q4 p.316

**要旨**
- ユーザー属性を作っただけではトークンに出てこない。**プロトコルマッパーを用意して初めてクレームになる**（p.56, 188）。
- クライアントスコープは「再利用できるクレームの束」。**Default** に入れたスコープは常に付与され、**Optional** に入れたスコープはクライアントが scope パラメーターで要求したときだけ付く。必要なときに必要な情報だけを求められる（p.56–57）。
- マッパーはクライアントに直接付けることも、クライアントスコープに付けることもできる（p.59–60）。マッパーの種類は User Attribute（クレーム名、JSON 型、ID トークン／アクセストークン／UserInfo に載せるかを指定）、Hardcoded claim、Group Membership、Audience など。
- ロールは既定ではアクセストークンにだけ入り、ID トークンには入らない（roles スコープの realm roles マッパーで切り替えられる）。グループは既定ではどのトークンにも入らないので、Group Membership マッパーが要る。グループはフルパス（例：/human resource/manager）で出力される（p.58, 146–152）。
- **入れすぎの注意**：ロールの設計次第でトークンのサイズが変わる。トークンには、クライアントや呼び出し先サービスがその場で認可判断するのに必要な最小限のロールだけを入れるのが理想（p.146）。トークンを小さくするには、必要最小限だけを載せて残りを UserInfo／イントロスペクションから取る方法や、Full Scope Allowed を切ってクライアントに関係する情報だけにする方法がある。ただし前者は Keycloak への追加リクエストが毎回発生する（解答 p.316）。
- クレームの形は変えられる。realm_access／resource_access 以外の場所にロールを出すことはよく行われる（解答 p.316）。認証中に集めた情報は、カスタムオーセンティケーターでセッションノートに保存し、マッパーでトークンに写せる（解答 p.316）。

**引用**：「本番環境ではすべてのロールを含めるべきではありません」（p.79）

## K3 aud・スコープ・ロールでアクセストークンを絞る

**該当箇所**
- 5.5「アクセストークンに付与されるアクセス権限の制限」p.75–76
- 5.5.1「Audienceを利用した…制限」p.76–77
- 5.5.2「ロールを使用した…制限」p.77–81
- 5.5.3「スコープを利用した…制限」p.81–83
- 解答 5章 Q2 p.314

**要旨**
- アクセストークンはアプリからサービスへ渡っていくので、権限を絞っておかないと、ユーザーがアクセスできるものすべてにそのトークンで届いてしまう。絞り方は **Audience・ロール・スコープ** の3つ（p.75–76、解答 p.314）。
- **Audience**：リソースサーバーは自分の識別子が aud に含まれているかを確認し、なければ拒否する。aud に追加する方法は2つ。Audience マッパーで明示的に足す（クライアント直下でもクライアントスコープ経由でもよい）か、他クライアントのクライアントロールがスコープに入ることで自動的に足されるか（p.76–77, 79）。aud に account が入っているのは後者の仕組みによる（p.77）。
- **ロール**：トークンに入るロールは「ユーザーが持つロール」と「クライアントが使ってよいロール」の**積集合**（図5.10、p.78）。既定では Full Scope Allowed が ON で、ユーザーの全ロールが入る。これは始めやすくするための設定であり、本番では OFF にして必要なロールだけをロールスコープに足す（p.79）。ロールはクライアントスコープ経由で持たせることもでき、Optional にしておけば要求されたときだけ入る（p.80–81）。
- 「スコープ」という言葉は3つの意味で使われていて紛らわしい。クライアントのロールスコープ（Scope タブ）、クライアントが使えるクライアントスコープ（Client Scopes タブ）、そしてクライアントスコープ自身が持つロールスコープ（p.80）。
- **スコープ**：OAuth 2.0 で権限を絞る標準の仕組み。Keycloak ではクライアントスコープとして作る。マッパーもロールも持たない空のスコープでもよい（p.81）。スコープの数は少なく保ち、利用者が同意画面で意味を理解できる表現にする（p.81）。**スコープ名は組織内で一意にし、サービス名や URL を接頭辞に付ける**（例：albums:view、https://api.acme.org/...）。標準の命名規則はないので Google や GitHub を参考にするとよい（p.81–82）。閲覧は Default、作成・削除は Optional に分けて、必要になったときに追加で認可を求める（インクリメンタル認可、p.82–83）。

**引用**：「スコープは通常、組織内のすべてのサービスにおいて一意であるべき」（p.81）

## K4 トークンの検証（署名・iss・aud・有効期限、イントロスペクションとの使い分け）

**該当箇所**
- 3.3 p.39–40（JWKS 取得、alg=none、アルゴリズム混同）
- 5.6「アクセストークンの検証」p.84–86
- 12.3 p.242、12.3.1 p.244–245（ローカル検証とセッション失効のずれ）
- 14.5.2 p.295、14.5.3 p.298（署名アルゴリズム、HMAC にするとイントロスペクションが必須になる）
- 7.10「独自の統合を行わないようにする」p.141

**要旨**
- 検証の方法は2つ。**イントロスペクションエンドポイント**を呼ぶか、**JWT を自分で検証**するか（p.84）。
- イントロスペクションは一番簡単で、Keycloak 以外の認可サーバーにも使える。トークンを「情報への参照」として扱える。その代わり、待ち時間が増え、認可サーバーの負荷も増える。対策として検証結果をキャッシュする手があるが、キャッシュ期間は数分程度の短さにする（p.84）。
- 自分で検証する場合に必要な手順：JWKS から公開鍵を取得する → 署名を検証する → 有効期限が切れていないか確認する → **発行者（iss）・Audience・タイプ**を確認する → アプリに必要なその他のクレームを確認する（p.86）。誤実装しやすいので、JWT とトークンの中身を十分理解してから取りかかる（p.85–86）。
- 既知の落とし穴：alg=none を受け入れてしまうこと、RSA 公開鍵を HMAC の共通鍵として使われてしまうこと。対策は、none を拒否すること、鍵を決まったアルゴリズムと用途にだけ使うこと、ヘッダーの値を鵜呑みにしないこと（p.39–40, 295）。信頼できるライブラリーが使えないなら、イントロスペクションの方が安全（p.40）。
- **ローカル検証の限界**：ローカル検証では、有効期限内であれば、セッションが無効化された後のトークンでも有効と判断してしまう。それが許されない要件なら、オーバーヘッドを払ってでもイントロスペクションを使う（p.242, 244）。
- 署名鍵を HMAC にすれば、全アプリにイントロスペクションを強制できる（p.298 とその訳注）。
- 自作の統合コードは避け、広く使われているライブラリーやフレームワークを使う（p.141）。

**引用**：「アクセストークンの発行者、Audience、タイプを確認する」（p.86）

## K5 認可戦略（RBAC / GBAC / OAuth スコープ / ABAC / Authorization Services）とトークンに載せるか都度判定するか

**該当箇所**
- 8.1「認可」p.144、8.2「RBACの使用」p.145–146、8.3「GBACの使用」p.146–152、8.4「OAuth 2.0スコープの使用」p.152–153、8.5「ABACの使用」p.153–154、8.6「中央集権型認可サーバーとしてのKeycloakの使用」p.154–155、8.7 p.155–156
- 解答 8章 p.316

**要旨**
- 認可判断に必要なのは、ユーザーが誰か、そのユーザーにどんなデータが紐づくか、リソースにどんな制約があるか、の3つ。Keycloak はトークンにユーザーと認証コンテキストの情報を入れ、アプリはクレームの読み方を変えることで RBAC や ABAC などを選べる（p.144）。
- パターンは2つ。アプリの中で判定する方式と、判定を外部サービスに任せる方式。どちらか一方に決める必要はなく、併用してよい（p.144、解答 p.316）。
- **RBAC**：レルムロールは組織内での役割を表し、どのクライアントでも同じ意味を持つ。クライアントロールの意味はそのクライアント次第（p.145、解答 p.316）。ロールの数が爆発しないように気をつけ、細かい権限をロールで表現しない（p.145）。複合ロールは性能面と管理面で注意が要る。複数のロールを渡したいときは、グループにロールを割り当てるやり方の方が自然（p.145–146）。
- **GBAC**：グループはユーザーを整理するための仕組みで、ロールとは役割が違う。階層を持ち、パスとしてトークンに出せる（p.146–147）。
- **OAuth スコープ**：利用者の同意だけを根拠にした認可。サードパーティーのアプリに委譲する場面に向く。スコープは「クライアントから」システムを守り、RBAC は「ユーザーから」システムを守る、という違いがある（p.152）。社内（エンタープライズ）のクライアントは同意を求めない設定が既定で、権限は管理者が与えたロール・グループ・属性で決まる（p.153）。
- **ABAC**：トークン内の任意のクレームや認証コンテキストを使って判定する。最も柔軟で細かい認可ができるが、実装と管理は簡単ではない（p.153–154）。
- **中央集権型（Authorization Services）**：`hasRole("manager")` のように判定ロジックをコードに書くと、要件が変わるたびに再デプロイが必要になる。`canAccess(リソース)` の形にして判定を外に出せば、ポリシーを変えるだけで済む（p.154–155）。外部判定には問い合わせの往復が増えるという問題があるが、Keycloak は権限を詰めたトークンをローカルで検証する方式と、インクリメンタル認可でこれに対処している（p.155）。
- まとめると、トークンはローカルで検証してもイントロスペクションで検証してもよく、そのクレームを RBAC・GBAC・ABAC・スコープのどれに使うかは要件次第（p.155–156）。

**引用**：「システム内のきめ細かな認可にロールを使用しないでください」（p.145）

## K6 有効期限・リフレッシュトークン・ローテーション・失効・セッション

**該当箇所**
- 4.5 p.54–56（リフレッシュ時に新しいリフレッシュトークンへ差し替える理由）、4.7「ユーザーのログアウト」p.60–63
- 6.3.4 p.99（SPA 向けの緩和策：短いリフレッシュトークンとローテーション）
- 12.2「セッションの管理」p.233–242、12.3「トークンの管理」p.242–250（12.3.1 p.243–245、12.3.2 p.245–247、12.3.3 p.247–248、12.3.4 p.248–250）
- 14.1.3 p.283–286（鍵ローテーション）、14.5.3 p.298–299
- 解答 12章 p.319

**要旨**
- セッションは2段構え。**ユーザー（SSO）セッション**と、その下にクライアントごとの**クライアントセッション**がある。設定項目は SSO Session Idle/Max と Client Session Idle/Max。既定値は Idle 30分、Max 10時間（p.234–237）。
- **ID トークンとアクセストークンの有効期間はどちらも Access Token Lifespan で決まり、既定は5分**。クライアントごとに上書きできる（p.243–244）。値はできるだけ短くしたいが、短すぎるとリフレッシュが増えて性能に響く（p.244–245）。
- リフレッシュトークンの有効期間は Client Session Max（未設定なら SSO Session Max）で決まり、トークンはクライアントセッションに紐づく。コンフィデンシャルクライアントなら長めでよいが、パブリッククライアントは短くする（p.245–246）。
- **ローテーション**：Revoke Refresh Token を ON にすると、使用済みのリフレッシュトークンが無効になる。Refresh Token Max Reuse の既定は0、つまり1回しか使えない。漏洩したトークンの悪用を早く見つけられる（p.247–248）。この機能は既定では OFF（p.56）。リフレッシュのたびに返ってくる新しいリフレッシュトークンを使うこと。鍵のローテーションやセッションのアイドル期限があるので、古いものは失敗することがある（p.55–56）。
- **失効の方法**：not-before ポリシー（指定時刻より前に発行されたトークンを一律に無効化する。セッション自体は残る）、セッションの無効化、RFC 7009 のトークン無効化エンドポイント（p.248–250）。ローカルで検証するアプリにはすぐには伝わらない（p.249）。
- ログアウトの基本は「アプリのセッションとトークンを短命にしておく」こと。すぐにログアウトさせたいなら OIDC Back-Channel Logout を使う。Session Management（iframe）や Front-Channel Logout は、ブラウザーがサードパーティー Cookie を制限するようになったため当てにならない（p.60–63）。
- クライアントクレデンシャルズではリフレッシュトークンもユーザー／クライアントセッションも作られず、必要なら再認証して取り直す（解答 p.319）。
- 署名鍵は月1回程度のローテーションを推奨。古い鍵はしばらく Passive にして検証だけに使う（p.283–284）。

**引用**：「トークンの有効期間と無効化については、常に明確な戦略を検討する必要があります」（p.242）

## K7 サービス間呼び出し・クライアントクレデンシャル・サービスアカウント・トークン伝搬

**該当箇所**
- 3.1 p.32–33（フローの選び方）
- 6.5「REST APIとサービスのセキュリティー保護」p.105–107
- 6.3.3「仲介REST APIを使用するSPA」p.97–98（BFF）
- 10.3 p.199（IdP トークンの保存とトークンエクスチェンジ、軽く触れる程度）
- 解答 12章 Q4 p.319

**要旨**
- アプリが**自分の権限で**リソースにアクセスするとき（アプリ自身がリソースオーナーのとき）はクライアントクレデンシャルズ。ユーザーの代わりなら認可コード（＋PKCE）（p.32）。
- マイクロサービスでは、受け取ったアクセストークンを下流のサービスにもそのまま渡せば、ユーザーの認証コンテキストを端から端まで伝えられる（図6.11、p.105）。
- サービスアカウント：confidential クライアントで Standard Flow／Direct Access Grants を OFF、Service Accounts を ON にし、`grant_type=client_credentials` でトークンを取る（p.105–107）。
- Bearer トークンは REST 以外にも、gRPC・WebSocket・SASL で使える（p.107）。
- BFF（仲介 REST API）にすれば、トークン（特にリフレッシュトークン）をブラウザーに置かずに済む（p.97–98）。
- トークンエクスチェンジは「外部 IdP から得て保存したトークンを取り出す機能」として名前が出るだけで、RFC 8693 による委譲やダウンスコープの説明はない（p.199）。
- **補足（デッキ側の判断）**：本書は同じトークンをそのまま下流へ渡す例を示すだけで、aud の検証（K3）とどう両立させるか、ホップごとにトークンを交換するかには触れていない。デッキでこれを扱うなら 26.x の公式ドキュメント（Standard Token Exchange）を根拠にし、本書を根拠にしない。

**引用**：「すべてのサービスが同じ認証コンテキストを使用する」（p.105）

## K8 マルチテナント（レルム、組織）

**該当箇所**
- 1.4.1.1「レルムの作成と設定」p.11
- 4.3「ディスカバリーエンドポイント」p.45–46（発行者 URL の /realms/{name}）
- 10.3.1 p.195–199（別レルムを外部 IdP に見立てた連携）

**要旨**
- レルムはテナントに相当するもので、ほかのレルムから完全に分かれており、設定・アプリ・ユーザーをそれぞれ独自に持つ。例として、社員と社内アプリ用のレルム、顧客と外部アプリ用のレルムを分ける構成が挙げられている（p.11）。
- 発行者（iss）の URL に含まれる `/realms/{name}` がレルムを区別する部分。したがって **iss はレルムごとに異なる**（p.46）。
- 1つのレルムの中でテナントを分ける機能（Organizations）の説明はない。

**引用**：「レルムとはテナントのようなものです」（p.11）

## K9 ID 連携・ブローカー（外部 IdP からの属性取り込みとマッピング）

**該当箇所**
- 10.2「LDAPやActive Directoryとの連携」p.189–194（10.2.1 LDAPマッパー p.191–192、10.2.2 グループ p.192–194、10.2.3 ロール p.194）
- 10.3「サードパーティーのIdPとの統合」p.194–199、10.4「ソーシャルIdPとの統合」p.199–200
- 13.5 p.276（User Storage SPI）
- 解答 10章 Q3 p.318

**要旨**
- ユーザーフェデレーション（LDAP など）とアイデンティティーブローカリング（OIDC／SAML の IdP）の2本立て。ブローカー経由で入ってきたユーザーもそのレルムのユーザーになり、レルムのセキュリティー設定が適用される（p.189, 195）。
- LDAP の場合は、インポートの有無と編集モード（READ_ONLY / WRITABLE / UNSYNCED）を最初に決める。グループやロールは LDAP マッパーで取り込む。ロールは既定でレルムロールとして作られ、クライアントロールにすることもできる（p.190–194）。
- 外部 IdP が発行したトークンの内容から、Keycloak 側のユーザーを作成・更新する（p.198–199）。IdP のトークンを保存しておくこともできる。初回ログイン時の認証フローを別に定義して追加情報を集めることもできる（p.199）。
- **IdP マッパー**を使えば、初回認証のときに特定のユーザー属性やロールを設定でき、ユーザーの作られ方を調整できる（解答 p.318）。ただし本文ではマッパーの種類（Attribute Importer など）や同期モードについては詳しく書かれていない。
- デッキへの示唆：外部 IdP のクレームはいったん Keycloak のユーザー属性やロールに取り込み、それからプロトコルマッパーで社内標準のクレーム名に変えて発行する、という2段のマッピングになる。この構成は本書の記述（p.199、p.188、解答 p.318）と矛盾しない。

**引用**：なし

## K10 セキュリティーのベストプラクティス（14章、補章クライアントポリシー）

**該当箇所**
- 14.1 p.281–287（TLS、ホスト名の固定、鍵ローテーション、定期的なアップデート、Vault、FW／WAF）
- 14.2 p.288–289（DB）、14.4 p.291–293（アカウント、個人情報）
- 14.5.2「OAuth 2.0とOIDCのベストプラクティス」p.295–296、14.5.3「Keycloakクライアントの設定」p.296–299
- 6.3 p.92–100、6.4 p.101–104
- 日本語版補章「クライアントポリシーによるセキュリティー保護」p.301–310

**要旨**
- 通信はすべて HTTPS（できれば TLS 1.3）。ホスト名は固定する（Host ヘッダー攻撃への対策）（p.282–283）。Keycloak には LTS がないので、継続的にアップデートする（p.286）。
- **個人情報（PII）について**：保存するものは絶対に必要なものに限る。**アプリに見せるユーザー情報も絞る**。DB を守る。各国の法律を理解する（p.293）。トークンに載せるクレームを最小限にする根拠として使える。
- クライアント設定：サードパーティーやネイティブアプリでは Consent Required を ON。資格情報を安全に保管できるなら confidential。Implicit と ROPC は非推奨。リダイレクト URI は完全一致にし、ワイルドカードは避ける（p.297–298）。署名アルゴリズムは既定が RSA で、可能なら ECDSA が望ましい（p.298）。ユーザーセッションは長く、リフレッシュトークンは短く（1時間以下）、という組み合わせにできる（p.298–299）。
- どの種類のアプリでも認可コード＋PKCE を使い、ログイン画面はアプリに埋め込まない（iframe も WebView も不可）（p.92–93, 101）。
- OAuth は state や PKCE が任意のままだと既知の脆弱性を抱える。JWT の none も同様。OAuth 2.1 や FAPI を参照する（p.295–296）。
- **補章**：クライアントポリシーは、設定ミス（ワイルドカードのリダイレクト URI、PKCE の設定漏れ、Consent の OFF など）を、登録時や設定変更時に検出したり自動で直したりする。リクエスト時にも state や PKCE の有無をチェックできる。適用対象は条件（例：クライアントロール）で絞り込める。用意されているプロファイルは FAPI 1.0 Baseline／Advanced と FAPI-CIBA（p.301–310）。
- 外部ストアへの鍵の保存はできる。HSM は当時未対応で、拡張で実装する必要があった（p.286）。

**引用**：「アプリケーションに公開するユーザー情報を制限する」（p.293）

## K11 その他、独自クレーム設計に効く記述

- **社内／社外アプリで同意の要否を分ける**（6.2 p.90–92、8.4 p.153）：社内アプリは同意なし。管理者がロールやグループで権限を与える。社外アプリは同意必須。クレーム設計では、スコープ（同意）とロール（管理者が付与）を混ぜないことの根拠になる。
- **認証コンテキストのクレーム化**（8.5 p.153、解答 8章 Q3 p.316）：認証中に集めた情報は、セッションノートとマッパーを使ってトークンに載せられる。acr、ステップアップ認証（18.0 で対応、訳注 p.231）とあわせて、「どう認証されたか」をクレームで伝える設計につながる。
- **クレームの JSON 型を指定する**（4.5.2 p.57）：User Attribute マッパーでは Claim JSON Type（String など）を選ぶ。型を揃えることが組織標準化のポイントになる。
- **評価ツール**（8.3.1 p.151）：クライアントの Client Scopes → Evaluate で、特定ユーザー向けに生成されるトークンをプレビューできる。ハンズオンでの確認手順に使える。
- **トークンのスコープで返すクレームを決める**（2.4 p.26）：scope はトークンに含めるクレームを決めると同時に、バックエンドがどの API にアクセスできるかを決めるのにも使われる。
- **SPI による拡張**（13.5 p.276、解答 13章 p.319–320）：プロトコルマッパーは SPI で自作できる（スクリプトによるマッパーも含む）。公開 SPI は互換性維持の対象だが、非公開 SPI は対象外。
- **統合アーキテクチャー**（7.2 p.112–113、7.9 p.139–140）：アプリに組み込む方式と、プロキシーや API ゲートウェイで処理する方式がある。ゲートウェイでトークンを検証し、HTTP ヘッダーでアプリに情報を渡す構成も本書の想定の範囲内。
- **アダプターは最後の手段**（解答 7章 Q2 p.315）：まず標準の OIDC ライブラリーを検討する。

## このデッキが本書に準拠していると言える主張（17件）

1. **ユーザーの識別子は sub を使い、preferred_username やメールをキーにしない**（2.4 p.24、4.5 p.54）
2. **ID トークンは RP が認証とセッション確立に使うもの、アクセストークンは API に渡すもので、aud の意味が違う**（4.5 訳注 p.54、5.3 p.70、6.3.1 p.94–95）
3. **Keycloak のアクセストークンは JWT なので、リソースサーバーは都度問い合わせずにクレームを読める**（3.3 p.38–39）
4. **カスタム属性は属性を作るだけではトークンに出ず、プロトコルマッパーが必要**（4.5.2 p.56–57、10.1.5 p.188）
5. **クレームはクライアントスコープ単位で再利用し、Default／Optional で常時付与か要求時付与かを分ける**（4.5.2 p.56–57、5.5.3 p.82）
6. **トークンには、その場の認可判断に必要な最小限のクレームとロールだけを入れる**（8.2 p.146、解答 8章 Q1 p.316）
7. **本番では Full Scope Allowed を OFF にし、クライアントが使えるロールを絞る（トークン内のロール＝ユーザーのロール ∩ クライアントに許可されたロール）**（5.5.2 p.78–79）
8. **アクセストークンは aud・ロール・スコープの3つで絞り、リソースサーバーは自分が aud に含まれているかを検証する**（5.5 p.75–76、5.5.1 p.76–77、解答 5章 Q2 p.314）
9. **スコープ名は組織内で一意にし、サービス名や URL の接頭辞を付ける**（5.5.3 p.81–82）
10. **JWT の検証は署名（JWKS）・有効期限・iss・aud・typ の確認が必須で、alg=none やアルゴリズム混同を防ぐ**（3.3 p.39–40、5.6 p.86、14.5.2 p.295）
11. **即時失効が必要な場面ではローカル検証ではなくイントロスペクションを使う。ローカル検証はセッション失効を反映しない**（5.6 p.84、12.3 p.242、12.3.1 p.244）
12. **細かい権限をロールで表現しない（ロール爆発を避ける）。複数ロールを渡すならグループにロールを割り当てる**（8.2 p.145–146）
13. **レルムロールは組織全体で同じ意味、クライアントロールはそのクライアント固有の意味として使い分ける**（8.2 p.145、解答 8章 Q2 p.316）
14. **OAuth スコープは同意（委譲）に基づく認可で、RBAC や ABAC とは何から守るかが違う。社内アプリの権限は管理者が付与するロール・グループ・属性で決める**（8.4 p.152–153、6.2 p.90–92）
15. **頻繁に変わる・細かい・文脈に依存する認可は、トークンに焼き込まず外部で判定する（中央集権型認可）**（8.5 p.154、8.6 p.154–155）
16. **アクセストークンは短命（既定5分）、リフレッシュトークンはセッションに紐づけ、パブリッククライアントでは短くしてローテーションする**（12.3.1 p.243–244、12.3.2 p.245–246、12.3.3 p.247–248、6.3.4 p.99）
17. **アプリに渡すユーザー情報（PII）は最小限にする**（14.4 p.293）

（補助的に言える主張：サービス間ではトークンを伝搬して認証コンテキストをそのまま引き継げる（6.5 p.105）、サービス自身の権限ではクライアントクレデンシャルズ＋サービスアカウントを使う（3.1 p.32、6.5 p.105–107）、レルムは完全に分離されたテナントで iss もレルムごとに異なる（1.4.1.1 p.11、4.3 p.46）、クライアントポリシーで PKCE などの必須化を強制できる（補章 p.301–310）。）
