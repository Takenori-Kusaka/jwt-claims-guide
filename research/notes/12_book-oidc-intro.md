## 2. 論点ごとの記述（独自クレーム・トークンの中身・RS の確認項目・記述がない点）

### 2.1 独自クレームについて
- 独自クレームに直接触れるのは2か所だけ。(a) クレームは独自に決めることもできる（p.62）。(b) IdP によっては独自の scope を定義できる（p.74–75）。
- 設計に関わる唯一の論点は、権限情報をトークンに入れると IdP にロックインされる、という 4.3 NOTE（p.68）。代わりに Client／RS 側で管理するか、権限サーバーに問い合わせる選択肢を示し、権限情報の複雑さに応じて手段を選ぶ、とだけ結んでいる。デッキ Part 4 の「変わりやすい権限は都度問い合わせる」と方向は同じだが、本書はもっと控えめな書き方をしている。
- Keycloak の実例では、realm_access・resource_access・allowed-origins といった**ベンダー固有のクレーム**がそのまま出てくる（p.64–65）。ただし本書はこれらを「独自クレーム」とは呼ばず、名前空間の問題としても扱っていない。

### 2.2 アクセストークン・ID トークンのクレームの中身
- アクセストークン（表4.1 p.62）：iss、sub、azp、aud、exp、iat、jti。含まれるものは IdP で変わる。
- ID トークン（表4.2 p.67）：iss、sub、aud=Client ID、exp、iat、auth_time、nonce、jti、acr、name、email、profile。
- イントロスペクション応答（表6.1 p.88）：必須は active だけ。client_id・scope・iss・exp は任意。
- UserInfo 応答（p.92）：sub、name、given_name、family_name、preferred_username、email、picture。
- client credentials の応答（p.207–208）：access_token のみ。expires_in は 60、refresh_expires_in は 0、scope は "email profile"。ID トークンもリフレッシュトークンもない。

### 2.3 RS が確認すべきクレーム（本書の立場）
- **署名**（IdP の公開鍵、jwks_uri はディスカバリーから取得）：p.66, 86。
- **aud**：自分を表す値かどうか。署名だけでは他クライアント向けのトークンの流用を防げない（13.8.1 p.227、13.9.6 p.229、9.4 p.130）。
- **exp**：Spring の検証動作として記載（p.139）。
- **iss**：Spring の issuer-uri の設定として登場（p.130）。iss の照合を RS の要件として明言しているのは、ID トークン（p.80）と Mix-Up 対策（p.224）の文脈だけ。
- **sub**：認可の判断ではなく、データを引くキーとして使う（p.133）。
- **scope**：RS のアクセス制御に使える（p.75）。サンプルは scope を確認していない。
- **記述がないもの**：typ（`at+jwt`）の確認、nbf、alg の固定（許可リスト）、client_id／azp の確認、acr による段階的な認可、必須クレームが欠けたときの扱い、時刻のずれ（clock skew）、鍵のローテーションへの追随。

### 2.4 本書に記述がないこと（デッキで他の根拠を使うべき点）
- クレーム名の3区分・IANA 登録簿・名前空間・型・サイズ・前方互換（Part 2、Part 4）
- ヘッダの攻撃（alg=none、混同、kid／jku／x5u）と RFC 8725 の中身（Part 1）
- amr、act／may_act、cnf、authorization_details、verified_claims、テナント（tid など）、ペアワイズ sub（Part 2）
- Entra／Auth0／Okta／Cognito の各論（Part 3）。表1.2 で製品名が出るだけ（p.19）
- トークン交換（RFC 8693）、Transaction Tokens、下流で aud・scope を絞ること、ヘッダへの転記と信頼境界（Part 6）
- 夜間バッチ（client credentials）のトークンとユーザーのトークンを、同じ RS でどう見分けるか（12.4 は API サーバーの実装が 9.4 節と同じだとして説明を省いている。p.206）
- DB 層（Part 7）、CAE・Shared Signals・RFC 7009（Part 8）、ログ・SD-JWT・JWE（Part 9）、AI エージェント（Part 10）、ガバナンス（Part 11）

## 4. 「このデッキが本書に準拠していると言える主張」

1. **ID トークンは Client（RP）が認証結果を知るためのもので、RS には送らない。アクセストークンは RS が受け取るもの。ID トークンを API の認可に流用するのは、特別な理由がない限り避ける。** — 4.3 と同節 NOTE、4.5（p.67–69）
2. **アクセストークンの形式は参照型（オパーク）と自己完結型（JWT）に分かれ、ID トークンは常に JWT。** — 4.2、4.3（p.60, 67）
3. **オパークはイントロスペクションで即時に失効を反映できるが、IdP への負荷と IdP 停止時の影響を受ける。JWT はその逆で、失効が有効期限まで反映されない。** — 4.2.3、6.2.1、6.2.2（p.66–67, 86–88）
4. **イントロスペクション応答で必須なのは active だけで、他のメンバーは任意。** — 6.2.2 表6.1（p.88）
5. **RS は IdP の公開鍵（ディスカバリーの jwks_uri から取得）で署名を検証する。** — 4.2.2「JWTの検証」、8.3（p.66, 112–114）
6. **署名の検証だけでは不十分で、RS は aud が自分を指しているかを必ず確認する。他クライアント向けのトークンの流用を防ぐため。** — 13.8、13.8.1、13.9.6（p.225–227, 229）
7. **さらに強い対策は sender-constrained トークン（DPoP、mTLS）。** — 13.8.1、13.9.6、付録C.5（p.227, 229, 249）
8. **アクセストークンにどのクレームが入るかは IdP によって違う。だから受け手は特定の IdP の形に依存しすぎない。** — 4.2.2 表4.1 の直後（p.62）、9.4 ❹ の注記（p.133）
9. **ユーザーに紐づくデータは sub で引く。preferred_username は IdP によっては含まれないので、キーにしない。** — 9.4 ❹❺（p.133）
10. **scope はユーザーではなくクライアントに許すことを表し、RS のアクセス制御に使える。IdP によっては独自の scope を定義できる。** — 5.2.1（p.74–75）
11. **権限をトークンに入れると IdP にロックインされるおそれがある。権限サーバーに都度問い合わせる選択肢もあり、権限の複雑さに応じて選ぶ。** — 4.3 NOTE「ユーザーの権限情報」（p.68）
12. **トークンに焼き込んだユーザー情報は古くなる。最新の情報は UserInfo などで取り直す。** — 6.4（p.91）
13. **UserInfo の sub が ID トークンの sub と一致するか確かめる（トークン置換への対策）。** — 6.4.2（p.92）
14. **ユーザーが関わらない処理（バッチなど）は client credentials フローを使う。ID トークンもリフレッシュトークンも出ず、期限が切れたら取り直す。** — 1.7.5、3.6、3.8、12.5（p.17–18, 53–54, 56–57, 208–209）
15. **BFF ではトークンをサーバー側のセッションに置き、ブラウザ（JavaScript）に渡さない。XSS による漏洩を減らし、コンフィデンシャルクライアントとして認証できる。代わりに構成と運用のコストが増える。** — 1.7.3、3.8、10.1、10.4（p.15–16, 57, 144, 155–157）
16. **アクセストークンの有効期間は短くする。ただし OIDC 関連の仕様に具体的な推奨値はなく、性能と IdP 停止時の影響との兼ね合いで決める。** — 13.9.7（p.229）
17. **リフレッシュトークンは寿命が長いので漏洩の影響が大きい。ローテーションで影響を抑え、ローテーションしても有効期限は延ばさない。** — 6.3.3（p.90–91）
18. **インプリシットフローと ROPC は新しく採用しない（RFC 9700 で非推奨、OAuth 2.1 で削除）。PKCE は常に使う。** — 3.4、3.7、3.8、5.7、13.9.3（p.50–57, 80–81, 228）
19. **高いセキュリティが要るなら FAPI 2.0（コンフィデンシャルクライアントのみ、sender-constrained トークン、response_type=code）を検討する。** — 13.7 NOTE、13.9.9（p.224–225, 230）
20. **複数の IdP を受け入れる場合は、iss（RFC 9207）で発行元を照合する。Mix-Up は PKCE では防げない。** — 13.7.1 と NOTE、13.9.8（p.223–224, 229–230）

（準拠を主張しないもの：typ・alg・kid の攻撃、名前空間・型・サイズ、トークン交換・伝搬、リフレッシュトークンのローテーションをめぐる FAPI 2.0 との違い、30分という具体値。いずれも本書には記述がないか、根拠が弱い。）
