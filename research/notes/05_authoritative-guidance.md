# 05. 権威ある機関のガイダンス（トークン・クレーム・フェデレーション・エージェント）

調査日: 2026-11-17（「2026年11月時点で最新」の確認日）
目的: デッキで「本資料の内容は国際的に権威のある機関のガイダンスと整合している」と書けるよう、根拠になる文書・節番号・要求事項を一次資料から確認する。
対象範囲: 主題は**複数サービスで共有する独自（アプリ定義）クレームの設計**、つまり属性の命名、出どころ、鮮度、最小化、監査、ガバナンス。標準 OIDC クレームは背景として扱う。

## 凡例

- **ティア**
  - **S** = 政府の標準・国際標準化団体（NIST、デジタル庁、IPA、NISC/国家サイバー統括室、CISA/DHS、ISO/IEC）
  - **A** = 国際的に認知された非営利団体（OWASP、OpenID Foundation、CoSAI、CSA）
  - **B** = 業界で定評のある組織（Thoughtworks）
- **[未検証]** = 一次資料の本文で確認できなかった項目。デッキで引用する前に再確認が必要。
- 要求の強さは原文の表記に合わせる: SHALL/MUST →「〜しなければならない」、SHOULD →「〜すべき」、MAY →「〜してよい」。
- 確認方法
  - NIST SP 800-63C-4/63B-4 は pages.nist.gov の HTML 版を取得した。節番号は HTML の `data-section` 属性と見出し階層から算出し、本文中の相互参照（例: 「Sec. 3.15」「Sec. 4.11.1」）と一致することを確かめた。
  - その他の PDF は原本を取得してテキスト化し、該当箇所を読んだ。

## 1. NIST（米国国立標準技術研究所）— ティア S

### 1-1. NIST SP 800-63C-4 *Digital Identity Guidelines: Federation and Assertions*

- **発行**: NIST, 2025年7月（CSRC の履歴では Final は 07/31/25）。**Final**。SP 800-63C（2020-03-02）を置き換え。DOI: https://doi.org/10.6028/NIST.SP.800-63c-4
- **URL**: https://pages.nist.gov/800-63-4/sp800-63c.html ／ https://csrc.nist.gov/pubs/sp/800/63/c/4/final
- **日本語訳**: 公式訳は **[未検証]**（NIST 側に掲載はない）。
- **補足**: CSRC の Planning Note（2026-10-06）で SP 800-63-4 の Implementation Resource Hub の公開が告知されている。
- **関連する節と要求事項**
  - **§2.2 FAL1**
    - IdP は承認済み暗号でアサーションに署名しなければならない。RP は、想定した IdP に紐づく検証鍵で署名を検証しなければならない。
    - アサーションは特定の RP（または RP の集合）にオーディエンス制限しなければならない。RP は自分が対象に含まれることを検証しなければならない。
    - RP はリプレイ防止を実施しなければならない（同じアサーションを二度受理しない）。
    - フェデレーション識別子には平文の個人情報（ユーザー名、メールアドレス、社員番号など）を入れるべきでない。
  - **§2.3 FAL2**
    - アサーション注入攻撃から強く保護しなければならない。トランザクションは RP から開始しなければならない。
    - オーディエンスは単一の RP に限らなければならない。
    - フェデレーション識別子に平文の個人情報を入れてはならない。
  - **§2.4 FAL3**: アサーションに加えて、主体が認証器を管理していることを RP が検証しなければならない（holder-of-key アサーションまたはバウンド認証器）。
  - **§2.5 xAL の要求と処理**
    - IdP は、結果として得られた xAL を（要求を満たせなかった場合も含めて）必ずアサーション内に示さなければならない。
    - RP は機能ごとに受け入れ可能な最低 IAL/AAL/FAL を決め、アクセスを許可する前に満たされていることを確認しなければならない。
  - **§3.4 フェデレーション識別子**
    - フェデレーション識別子は「サブジェクト識別子＋発行者識別子」の論理的な組み合わせである。RP は、発行した IdP を考慮せずにサブジェクト識別子を処理してはならない。
    - フェデレーション識別子は加入者ごとに一意で、RP 側では単一の加入者に対応付けなければならない。
  - **§3.4.1.2 PPI の生成**: ペアワイズ仮名識別子には識別情報を含めてはならない。推測不能な十分なエントロピーを持たなければならない。
  - **§3.6 / §3.6.1 / §3.6.2 鍵と識別子の管理**
    - 鍵情報は認証済みの保護チャネルで交換しなければならない。対称鍵はフェデレーション参加者のペアごとに固有でなければならない。
    - 識別子にワイルドカードを使ってはならない（例: `*.example.com`）。
    - 鍵ローテーションの手順はトラストアグリーメントで定め、認証済みの保護チャネルで行わなければならない。
    - 署名鍵は安全に保管しなければならない（FIPS 140 に準拠）。
  - **§3.9 RP の認証済みセッション**: RP がセッションを作ってよいのは、次の条件をすべて満たしたときに限られる。
    - 有効なアサーションを検証した。
    - アサーションが想定した IdP から来ている。
    - 発行した IdP が、フェデレーション識別子に示された IdP と一致する。
    - アサーションが RP 側のアカウントに関連付けられている。
  - **§3.10 プライバシー要件**: IdP と RP は、システムの機能を果たすのに必要な**最小限のデータだけ**をやり取りしなければならない。RP 間での追跡を防ぐため、PPI などの技術的手段を使うべきである。
  - **§3.11.1 アサーション注入攻撃からの保護**: 対策例として次が挙がっている。
    - バックチャネルでの提示
    - RP が生成した nonce を署名の対象に含める
    - RP が IdP に対して認証する
    - IdP 起点のフローを禁止する
  - **§3.12 属性（Identity Attributes）**
    - 属性は、IdP が直接提示する（非バンドル）か、CSP が署名したバンドルに入れるかのどちらかでなければならない。
    - 属性は、アサーションに入れて署名の対象にするか、保護された identity API で提供するかのどちらかでなければならない。
    - トラストアグリーメントは、属性の検証手順と情報源を記した CSP の実施規程を参照しなければならない。
  - **§3.12.1 属性バンドル**: RP は、バンドル固有の署名と、外側の容器（アサーション全体）の署名の両方を検証しなければならない。
  - **§3.12.2 派生属性値**: 派生属性値（例: 成年かどうかの真偽値）は、元の属性値を要求者に開示してはならない。
  - **§3.12.3 Identity API**
    - identity API は送信者制約付きのアクセスを要求すべきである。
    - API へのアクセス期間はトラストアグリーメントで時間を限定しなければならない。
    - API にアクセスできたことを、RP セッションを確立する根拠にしてはならない。
  - **§3.13 アサーションの保護**
    - §3.13.1: アサーションは一意に識別できなければならない。
    - §3.13.2: 署名はアサーション全体（識別子、発行者、オーディエンス、サブジェクト、有効時間枠）を覆わなければならない。
    - §3.13.4: すべての RP は、オーディエンスに自分の識別子が含まれることを確認しなければならない。単一オーディエンスにすべきであり、FAL2 以上では必須。
  - **§3.14 / §3.15 bearer と holder-of-key**
    - bearer アサーションは、提示されただけで本人の証明として扱われる。そのため窃取されるとなりすましに使われる。
    - holder-of-key アサーションは、RP が独立に検証できる認証器の識別子を含まなければならない。その認証器はフィッシング耐性を持たなければならない。
  - **§4.6.4 属性の同期**
    - IdP は、毎回属性を押し付けるのではなく、属性が更新されたことを RP に通知すべきである。
    - 例示: アサーションの有効期間が5分なら、identity API は30分有効にする。
    - アカウント停止や RP へのアクセス取り消しは RP に通知すべきである。
  - **§4.7 再認証とセッション**
    - アサーションの有効期間を RP セッションの長さと混同しない。
    - IdP は直近の認証時刻に関する情報を RP に伝えなければならない。
    - identity API にアクセスできることを、セッションの確立や延長に使ってはならない。
  - **§4.9 アサーションの内容（汎用 IdP）**
    - 必須要素: 発行者識別子、オーディエンス識別子、発行時刻、有効時間枠、アサーション識別子、認証時刻、署名（検証鍵 ID を含む）。フェデレーション識別子を使う場合はサブジェクト識別子も必須。
    - FAL2 以上では nonce が必須。
    - 加入者の認証秘密（パスワードなど）を含めてはならない。
    - **RP の検証項目**: 署名、発行者、時刻、オーディエンス、nonce、取引条件（xAL）、リプレイ。
    - サブジェクト識別子を IdP をまたいで一意だとみなしてはならない。
    - 有効時間枠は処理に必要な最小限とし、RP セッションの制限に使ってはならない。
  - **§4.11.1 バックチャネル提示**: アサーション参照（例: 認可コード）について、次の要件が並んでいる。
    - 単一の RP に限定する。
    - 一回限りの使用にする。
    - 時間を限定し、**5分以内とすべき**である。
    - RP の認証を伴う。
    - 推測できないものにする。
  - **§9.1 FAL と主要プロトコルの対応（非規範）**: FAL3 では holder-of-key に加えて、API アクセスに送信者制約付きアクセストークンを使う例が挙がっている。

### 1-2. NIST SP 800-63B-4 *Digital Identity Guidelines: Authentication and Authenticator Management*

- **発行**: NIST, 2025年7月。**Final**。
- **URL**: https://pages.nist.gov/800-63-4/sp800-63b.html ／ https://csrc.nist.gov/pubs/sp/800/63/b/4/final
- **関連する節と要求事項**
  - **§2.2.3 AAL2 の再認証**: 全体タイムアウトは **24時間以内**とすべきである。非活動タイムアウトは **1時間以内**とすべきである。
  - **§2.3.3 AAL3 の再認証**: 全体タイムアウトは **12時間以内**でなければならない。非活動タイムアウトは **15分以内**とすべきである。
  - **§5.1.2 アクセストークン**
    - RP は、他のシグナルがない限り、アクセストークンがあることを利用者がその場にいる証拠と解釈してはならない。
    - アクセストークンやリフレッシュトークンは、認証セッションの終了後も長く有効でありうる。
  - **§5.2 再認証**: フェデレーションでは、再認証の要件を満たしたかどうかの最終判断は RP が下す（詳細は 63C §4.7 を参照）。

### 1-3. NIST IR 8587 *Protecting Tokens and Assertions from Forgery, Theft, and Misuse: Implementation Recommendations for Agencies and Cloud Service Providers*（★今回の最重要の新出文書）

- **発行**: NIST（CISA と共著）, **2026年9月**。**Final**。初期公開ドラフトは 2025-12-22、コメント期限は 2026-01-30。
- **URL**: https://csrc.nist.gov/pubs/ir/8587/final ／ https://nvlpubs.nist.gov/nistpubs/ir/2026/NIST.IR.8587.pdf
- **位置付け**: SP 800-53 の管理策 IA-13 とその強化項目を解説する実装推奨。準拠は任意だが、OMB などの方針で義務化されうる。
- **関連する節と要求事項**
  - **§1.1.1 AI と AI エージェント**: エージェントが署名付きトークンでシステム、データ、ツール、API にアクセスする場合にも、本ガイドラインを適用すべきである。
  - **§4.1.4 認可システムとゼロトラスト**
    - 権限をより細かく動的に定義できる形（例: ABAC）でトークンを実装しなければならない（MUST）。
    - 認可判断はトークンが有効かどうかだけで下すべきでなく、提示された文脈も考慮すべきである（SHOULD NOT）。
    - トークンの有効性は、人間と非人間の ID のプロビジョニング、プロビジョニング解除、権限付与と整合させなければならない（MUST）。
  - **§5.2.1.1 アサーションとトークンの内容**
    - CSP と機関は、トークンの種類ごとに**必須データ要素を文書化しなければならない**。
    - 最低限含める要素: 発行者、サブジェクトまたはクライアント識別子、オーディエンス、発行時刻、有効期間、識別子または nonce、認証時刻、署名（MUST）。
    - OAuth のアクセストークンには scope を含めるべきである。細粒度の権限には RAR（Rich Authorization Requests）を活用できる。
  - **§5.2.1.2 鍵のスコープと用途**
    - 署名鍵は、合理的な範囲で最も小さい単位（例: **単一テナント**）にスコープしなければならない。環境（開発、テスト、本番）ごとにも分けなければならない。
    - 鍵は定めたスコープの外で使えてはならない。署名鍵を他の目的に使ってはならない。
    - RP とリソースサーバーは、アクセスを許可する前にトークンのスコープ、有効性、出どころ、完全性を確認しなければならない（MUST）。
  - **§5.3.1.1 リフレッシュと有効期間**
    - アクセストークンと ID トークンには、定義された短い寿命がなければならない。期限切れのトークンは拒否しなければならない（MUST）。
    - 有効期間は **1時間以内とすべき**である（SHOULD）。
    - 対話セッション向けのリフレッシュトークンは、SP 800-63B-4 の再認証期間を超えるべきでない。
    - 非人間（ワークロード）向けのリフレッシュトークンは、できるだけ短くすべきである。
  - **§5.3.1.2 失効**
    - 侵害が疑われるトークンに関連するリフレッシュトークンは、再認証なしに受け入れてはならない（MUST not）。
    - 失効状態は、イントロスペクション、Token Status List、共有シグナルなどで RP に伝えるべきである。
    - 失効を受け取った RP はトークンを拒否し、セッションを終了しなければならない（MUST）。
    - SSF/CAEP によるセッション失効シグナルを実装すべきである。
  - **§5.3.1.3 オーディエンス制限**
    - すべてのトークンに明示的なオーディエンスを含めなければならない。オーディエンスが欠けている、または誤っているトークンは拒否しなければならない（MUST）。
    - 拒否したときは即座にセキュリティアラートを出すべきである。
    - トークンのスコープは、意図した操作に必要な最小限に限らなければならない（MUST）。
  - **§5.3.1.4 セッション監視**
    - トークンの使用パターンを監視しなければならない（MUST）。
    - トークン（またはその背後の ID）と、企業全体での行為とを相関できるようにすべきである。
    - 使用データは SIEM で取り込める形式で提供しなければならない（MUST）。
  - **§5.3.1.5 トークンの保護**: トークンをログ、CI/CD、成果物に露出させてはならない（MUST）。
  - **§5.3.1.6 ワークロードの保護**
    - 非人間の ID は、狭いスコープの短命トークンを使わなければならない（MUST）。
    - 可能な限り送信者制約（mTLS、DPoP）を使うべきである（SHOULD）。
    - SPIFFE/SVID の活用を推奨している。
  - **§5.3.1.7 ロギング**
    - トークン関連のイベントは改ざん耐性のあるログに残さなければならない（MUST）。
    - **トークンそのもの、およびトークンに含まれる PII をログに保存してはならない**（MUST NOT）。
    - 推奨するログ要素（表6）: トークン種別、発行者、scope、クライアントまたはユーザー（ハッシュなどで難読化）、オーディエンス、イベント。
- **注意**
  - 本文中の相互参照に「Sec. 4.3.1.1」「4.3.1.2」とあるが、実際の節番号は 5.3.1.x である（原文の不整合）。
  - 表の番号（表4/5/6）にも本文とのずれがある。
  - デッキでは**目次上の節番号（5.x）**で引用する。

### 1-4. NIST SP 800-162 *Guide to Attribute Based Access Control (ABAC) Definition and Considerations*

- **発行**: NIST, 2014年1月（2019-08-02 時点の更新を含む）。**Final**。
- **URL**: https://csrc.nist.gov/pubs/sp/800/162/upd2/final
- **独自クレーム（属性）の設計に直結する節と要求事項**
  - **§2.4.2 エンタープライズ ABAC における属性管理**
    - 属性は、名前、定義、許容値、スキーマを与えて主体と客体に関連付ける必要がある。主体属性は権限を持つ機関（authority）のもとで発行、保管、管理する。
    - 組織をまたぐ属性は、所在の特定、取得、公開、検証、更新、失効の対象になる。
    - 組織は属性の名前と値を正規化するか、同義語の対応表を維持しなければならない。これは**中央の権限主体が管理すべき**である。
    - 属性についての属性（メタ属性）という概念がある。
  - **§3.1.3.2 属性アーキテクチャ**: 属性のスキーマと許容値を全参加者に公開しなければならない。
  - **§3.1.3.3 主体属性**
    - クリアランスのような属性は、権限を持つ機関だけが付与、主張できるようにする（本人が変更できないようにする）。
    - 属性の一覧と権威ある情報源を「属性実施規程（Attribute Practice Statement, APS）」で定めてよい。
  - **§3.2.1.3 属性の合意と理解**
    - 属性の提供者は、属性値の定義と意味を文書化し、使い方の指針を示さなければならない。
    - 属性によっては、他の属性と組み合わせて初めて意味を持つ（例: 役職は組織の文脈とセットで解釈する）。
  - **§3.2.1.6 属性のプライバシー**: 属性の共有は PII の露出や集約のリスクを高める。トラストアグリーメントで取り扱いを定めるべきである。許可・拒否のパターンから属性が推測されうるため、アクセスログも保護すべきである。
  - **§3.2.2.6 属性ソースの選定**: 権威ある情報源を明確に特定すべきである。
  - **§3.2.2.10 属性管理**: 属性の完全性、許容値、整合性、**変更履歴を検証できる来歴（provenance）の仕組み**を組み込むべきである。
  - **§3.2.2.12 / §3.2.3.2 合意済み属性と組織間マッピング**: ポリシーの作成者が各自で属性を作るとポリシー同士の相互運用性が失われる。事前に合意した属性を使う。
  - **§3.3.1 属性のキャッシュ**: **鮮度とセキュリティのトレードオフ**がある。更新頻度の低い属性は安全性が下がる。権限の変更は次の更新まで反映されない。
  - **§3.3.2 属性ソースの最小化**: 属性ソースの数を減らすと、性能と管理の両面で利点がある。
  - **§3.3.3 インターフェース仕様**: 変更があるときは、すべての依拠当事者に事前に通知する。
  - **§3.4.1 品質データの可用性**: 属性値の追加、更新、削除は、訓練を受けた権限者が行い、定期的に監査すべきである。

### 1-5. NIST IR 8112 *Attribute Metadata: A Proposed Schema for Evaluating Federated Attributes*

- **発行**: NIST, 2018年1月。**Final**。
- **URL**: https://csrc.nist.gov/pubs/ir/8112/final
- **補足**: SP 800-63C-4 §4.9 が、属性メタデータの例としてこの文書を参照している。
- **関連する節と要求事項**
  - **§3.1 属性スキーマのメタデータ**: 説明、許容値、形式、検証頻度、データ処理。独自クレームのレジストリに持たせる項目の雛形として使える。
  - **§3.2.1 メタデータの5分類**: 来歴（Provenance）、正確性（Accuracy）、鮮度（Currency）、プライバシー（Privacy）、分類（Classification）。合計15要素。

### 1-6. NIST SP 800-228 *Guidelines for API Protection for Cloud-Native Systems*

- **発行**: NIST, 2025年6月。**Final**。

**JSON Web Token Cheat Sheet**

- **Considerations / Claims**
  - `exp`/`nbf` を検証し、`iss`/`aud` を確認する。
  - `auth_time`/`acr`/`amr` を、認証の新しさと強度の判断に使う。
  - `roles`/`groups`/`scope` は認可の入力として扱う。その際、**別の発行者からの詐称**に注意する。
- **Public-key Signatures / MAC**: 推奨アルゴリズムは EdDSA、ES*、PS*。RS* は「推奨しない」。MAC の秘密は発行者とオーディエンスの組ごとに分ける。
- **Threats**
  - `alg:none` を受け付けない。鍵種別の混同を防ぐ。トークンヘッダーで指定された鍵を信用しない。
  - `iss` は許可リストで完全一致させる。検証鍵は、検証済みの発行者の鍵セットからだけ選ぶ（複数の鍵セットを混ぜない）。
  - 明示的な `typ`（例: `at+jwt`）で、トークン間の取り違えを防ぐ。
- **Revocation / Replay**: `status` クレーム（Token Status List）を使う。失効リストは `jti`+`iss` をキーにする（生のトークンやそのハッシュをキーにしない）。
- **Token Confidentiality**: 署名付き JWT は機密ではない。機微データは入れないか、参照トークンを使う。署名のない JWE のクレームで認可しない。

**OAuth2 Cheat Sheet**

- **Token Replay Prevention**: DPoP（RFC 9449）、mTLS（RFC 8705）、PoP トークンを使うべき場面を整理している。
- **Access Token Privilege Restriction**: 権限を最小限にする。オーディエンスは単一のリソースサーバーに限定するのが望ましい。リソースサーバーは毎回のリクエストで検証する。`scope` と `authorization_details` で制限する。
- RFC 9700 を参照している。

**Identity Propagation Patterns Cheat Sheet**

- **External Identity Propagation**: 転送を可能にするためだけにオーディエンスを広げない。
- **Simple Service-Level Forwarding**: 既定では推奨しない。アプリケーションのサービスを ID の発行者にしない。
- **Token Exchange**: 受信者ごとに異なるオーディエンスや明示的な委任が必要な場合に推奨する。STS がサービスを認証し、権限を絞る。
- **Protocol-Agnostic**: 境界で外部の資格情報を検証し、正規化した内部アサーションを発行する。発行と検証の権限は分ける。
- **Privacy**: 受信者が必要とする属性だけを入れる。適宜、仮名識別子を使う。ユーザーと代理で動くサービスの区別を保つ。
- **禁止事項**: ID トークンを API のアクセストークンとして使わない。

**Workload Identity Federation Cheat Sheet**

- `iss`/`aud`/`sub` を固定する。ワイルドカードを避ける。
- 独自クレームがクラウド側のポリシー条件として実際に強制できるかを確認する（**トークンにクレームが含まれていても、信頼ポリシーで使えるとは限らない**）。
- 名前ではなく変わらない ID を使う。本番と非本番で信頼ルールを分ける。

  - **§2.6 Authorization**: 言語モデルは非決定的に振る舞うため、エージェントでは最小権限が特に重要になる。
  - **§2.8 Identity for AI Agents**
    - 動的クライアント登録で得たクライアント ID だけでは、ワークロード ID として不十分である。SPIFFE/SPIRE による短命で自動ローテーションされる ID が選択肢になる。
    - エージェントの ID には、モデル、バージョン、能力といったメタデータが必要である。
  - **§2.11 監査性のギャップを埋める**
    - エージェントの API 呼び出しがユーザー本人の行為と区別できない形で記録される問題を指摘している。
    - トークンには人間の主体とエージェントの両方の識別子を含めるべきだとしている。JWT の `act` クレームを例に挙げている。
  - **§3.2 委任認可と推移的信頼**
    - なりすましをやめて OBO（代理）に移行し、`sub`（委任したユーザー）と `act` または `azp`（エージェント）の2つの ID を持つトークンを使う。
    - 多段の委任では、各段階で権限を縮小する（scope attenuation）。中央集権型なら Token Exchange（RFC 8693）、分散型なら Biscuits や Macaroons を使う。
    - 失効は未解決の課題である。SSF、IPSIE、OpenID Provider Commands に触れている。
    - 実行回数による制約を提案している。SCIM DELETE と SSF によるプロビジョニング解除にも触れている。
