## 2. JWT クレームと検証について本書が具体的に述べていること

### 2.1 標準クレーム
- RFC 7519 の7つを「予約済みクレーム」と呼び、iss＝発行した認可サーバー、sub＝トークンの主体（全クレームはこの主体にだけ当てはまる）、aud＝アクセスを与える API、exp/nbf/iat/jti を説明（p.194–195）。
- 必須ではないが、業界で通じるので入れるのがベストプラクティス。標準ライブラリやゲートウェイがそのまま扱えるという相互運用性の理由（p.195）。
- ID トークンには auth_time・acr（保証レベル、ISO/IEC 29115・RFC 6711）・amr（RFC 8176 の値）・azp に加え name・email 等が入る（p.218）。
- aud の意味：API ごとに異なる aud にしないと、顧客用トークンで管理者 API を呼べてしまう（ライドシェアの例、p.109）。管理者用ログインは別クライアント＋別 audience で行う例（p.255–257）。

### 2.2 カスタムクレームとクレームによる認可
- カスタムクレームでロール・グループ・組織などの属性を表せる。代表例は RBAC のためのロール（p.195）。
- RBAC の一般解は「IdP がロールを把握してアクセストークンに入れ、API が毎回照合」。Auth0 の permissions、Entra の roles/groups（p.219–220、p.122）。
- エンドポイント一覧型の細かい permissions（例 `GET:/admin/api/users`）は可能だが、運用負荷・情報露出・サイズの3つの欠点がある（p.220–221）。
- ABAC はトークンに載せず sub から DB の属性を引く（p.221–223）。
- **オブジェクト単位の判定はトークンでは完結しない**：BOLA の修正は DB クエリに `owner == sub` を足すこと（p.102–103）。組織／プロジェクト境界も要求者の所属を DB で引いて条件に加える（p.119–120）。
- コード上の形：FastAPI の依存性注入でトークンを検証し、クレームの dict をハンドラに渡し、業務ロジック層で追加のアクセス制御を行う（p.250–252）。

### 2.3 トークンに入れてはいけないもの
- 氏名・メールなどの機密性の高い利用者データ、個人を特定できる情報（p.195、p.230）。
- 理由：アクセストークンは全リクエストに載り、盗聴・XSS・CORS 設定ミスで盗まれうる（p.196）。
- 2.3.2 でも「JWT に個人情報や機密情報を含めるべきではない」と再掲（p.057）。
- 細かい権限一覧は内部構成を攻撃者に見せる（p.221）。
- どうしても機密クレームが必要なら JWE（p.197–199）。

### 2.4 検証の手順・ライブラリ
- 全体像（図3.9 p.074）：署名を検証 → ヘッダー（alg が正しい値か）を検証 → 全クレーム（aud・iss・権限・期限）を期待値と照合。
- ベストプラクティス（8.3 末尾 p.238–239、要約）：
  1. PS256・EdDSA など強いアルゴリズムに対応し、利用者の多いライブラリを選ぶ。
  2. アルゴリズム混同攻撃に弱くないか、McLean の例で自らテストする。
  3. RS256 を使うなら Bleichenbacher 攻撃への耐性を確認し、鍵は2048ビット以上・十分な公開指数。
  4. 許可する alg を検証関数にハードコード（none／nonE 対策）。
  5. iss・aud を含む可能な限り全クレームを検証。ライブラリが対応しない検証は自前のアサーションで足す。
- IdP 発行トークン：ディスカバリ → jwks_uri → ヘッダーの kid で JWK を選択 → 署名検証（PyJWKClient、p.246–249）。
- 検証はすべてのリクエストで、ミドルウェアで行う（p.258 まとめ）。
- ライブラリ：Python では PyJWT・python-jose・JWCrypto を紹介。JWCrypto は柔軟な分、aud を明示しないと検証しない（p.108–110）。

### 2.5 ゲートウェイ vs サービスでの検証
- ゲートウェイがあればトークン検証機能を使うべき。ただし (a) ゲートウェイも故障しうるのでコード側にも確実な代替を、(b) **独自クレームを含むトークンはゲートウェイで検証しきれないことがある**、(c) すべての API がゲートウェイを通るとは限らない（p.250 NOTE）。
- ゲートウェイが担うのはアクセス制御の第1段（認証済みか）。ロール・資源単位の判断は後段（図9.7 p.265–266）。
- ゲートウェイと WAF は BOLA を防げない。過信しない（p.058 警告）。

### 2.6 内部トークン・サービス間
- 本書に「内部トークン」「トークン交換」「ゲートウェイで再発行」の記述はない。
- 述べているのは原則のみ：内部 API も外部 API と同じく認証・認可で守る（p.082–084）、内部サービスから来たデータも検証する（p.079–080）、マイクロサービス間はクライアントクレデンシャル（p.207）、mTLS は社内サーバー間で一般的（p.191）。

### 2.7 監査ログと主体の記録
- 監査証跡の定義：誰が・いつ・どこで・何をしたかの時系列記録。インフラ側は CloudTrail 等で別途保持（p.307）。
- スパン属性 `user.sub` にトークンの sub を入れ、リクエスト本文と結びつける（p.317）。メトリクスにも sub を属性として付け、発信元（IP・端末指紋・ユーザー ID）で異常を絞り込む（p.326）。
- PII・カード番号はスキーマ上で特定して、ログに出す前に除外／マスク。ログが規制の適用範囲に入り、扱いにくくなり、漏洩リスクも上がるため（p.321）。
- 否認防止が必要な分野（金融・医療・法務）では「誰のアカウントで行われたか」だけでなく「本人が行ったか」を示すために FAPI メッセージ署名を使う（p.301–302）。

## 4. 「このデッキが本書に準拠していると言える主張」

1. 認可は「トークンが有効か」と「その主体が要求された資源・操作を許されているか」の2段で、両方を毎リクエスト行う（7.1 p.191–192）。
2. JWT の検証では署名だけでなく、ヘッダーの alg と iss・aud・exp を含む全クレームを期待値と照合する（3.2 図3.9 p.074、8.3 p.238–239）。
3. 受け入れる署名アルゴリズムは検証側で固定し、トークンの alg を信用しない（alg none／nonE／アルゴリズム混同対策）（8.3 p.236, 239、10.4 p.293）。
4. aud を検証しないと、ある API 向けのトークンで別の API（管理者 API 等）を呼べてしまう（4.5 p.108–110）。
5. ID トークンをアクセストークンとして API の認可に使ってはならない（7.2.1 p.193、2.3.2 p.057、付録A.3 p.354）。
6. JWT（JWS）は誰でも読めるので、氏名・メール等の個人情報や機密データをクレームに入れない。必要な属性は UserInfo 等で都度取得し、どうしても秘匿が要るなら JWE（7.2.2 p.195–199、8.2 p.230）。
7. 利用者の識別子は sub に任せ、カスタムクレームはロール・グループ・組織など認可に必要な属性に絞る（7.2.2 p.195）。
8. 細かい権限をトークンに詰め込むと、更新漏れ・内部構成の露出・トークン肥大（ヘッダー上限超過）を招く。長い一覧はロールへ集約する兆候（7.7 p.220–221）。
9. 変わりやすい属性はトークンに載せず、sub をキーに都度 DB／ポリシーで判定する方式（ABAC）は、認可サーバー側で権限を最新に保つ負担を減らすが、モデルを明確にしないと複雑化する（7.7 p.221–223）。
10. オブジェクト単位の認可（BOLA 対策）はトークンのクレームだけでは完結せず、データ取得時に所有者や所属を照合する必要がある（4.3 p.101–103、4.6.2 p.119–120）。
11. ロールで機能を分けるなら全 API・全操作で毎回ロールを確認し、不足時は 403（存在を隠すなら 404）を返す。管理者 API を隠すことは防御にならない（4.7–4.8 p.120–124）。
12. 利用者が付けられるリクエストヘッダー（例 X-User-Role）でロールを判断する設計は攻撃ベクトルになる（1.4 p.033–034、3.2 p.073）。
13. API ゲートウェイでのトークン検証は有用だが、それだけに頼らず各サービスでも検証できるようにする。独自クレームはゲートウェイで検証しきれないことがあり、ゲートウェイを通らない経路もある（8.5 NOTE p.250）。
14. ゲートウェイや WAF はオブジェクト単位の認可不備（BOLA）を防げない（2.3.4 p.058）。
15. 「内部 API だから認証不要」は成り立たない。ネットワーク分離は補助であり、内部 API・サービス間通信にもゼロトラストで認証・認可を適用する（3.2 p.071–075、3.4 p.082–084）。
16. 送信者制約トークン（mTLS の cnf.x5t#S256、DPoP の cnf.jkt）で盗まれたトークンの再利用を防げる。機密性の高い API では使うべき（7.5 p.210–216、付録A.3 p.354）。
17. リフレッシュトークンはローテーション（1回限り）か送信者制約で守り、寿命に普遍的な数値基準はないので要件で決める。FAPI 2.0 はコンフィデンシャルクライアント前提でローテーションを求めない（7.4.5 p.209–210、10.4 p.293）。
18. トークンや資格情報を URL に載せると、ブラウザ履歴・アクセスログ・HAR ファイルから漏れる（4.4 p.106）。
19. 監査ログには「誰が（sub）・いつ・どこで・何を」を残し、PII や機密項目はスキーマ上で特定して記録前に除外／マスクする（11.1 p.307、11.4–11.5 p.317, 321）。※本書のコード例のようにヘッダー全体（トークン）を記録する点は準拠対象から外す。
20. API セキュリティは単独チームの仕事ではなく、軽量な文書化された標準・関係者の参加・リンターやファザーによる自動化で組織的に治める（2.4 p.058–059、2.5 p.060–062）。
